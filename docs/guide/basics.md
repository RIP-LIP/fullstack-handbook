# 基础概念

> 目标：搞清楚端口、HTTP、JSON、以及「代码跑在哪台机器上」。读完这四件事，「项目启动」里每一行输出你都能解释。

「项目启动」那篇会让你把两个服务跑起来，然后在浏览器里看到一条请求。如果你不知道那条请求是怎么来的，出错时就只能照着抄，改一处坏两处。

这一章不写代码，只解释四件事。**这四件事是后面所有章节的地基。**

## 1. 代码跑在哪台机器上

这是全栈最容易搞混的一点，先说清楚。

一个「全栈应用」其实由几段代码组成，**它们跑在不同的机器上**：

```
┌─────────────────────────────────────┐
│  浏览器（你的电脑）                    │
│   · HTML  CSS  JavaScript            │
│   · 你的数据在这台机器上可见           │
└──────────────┬──────────────────────┘
               │  HTTP 请求
               ▼
┌─────────────────────────────────────┐
│  后端服务器（另一台机器）              │
│   · Node.js / Express                │
│   · 负责校验、查数据库、返回结果       │
└──────────────┬──────────────────────┘
               │  SQL
               ▼
┌─────────────────────────────────────┐
│  数据库                               │
│   · 本教程是 SQLite，一个文件           │
└─────────────────────────────────────┘
```

**关键点：你在浏览器里按 F12 看到的 Network 面板，只能看到前端发出的请求，看不到后端内部发生了什么。** 后端的报错在后端终端里。

这就是为什么「浏览器控制台没报错，但页面白屏」是可能的——错误发生在你看不见的那台机器上。

### 为什么不能全放前端

「那就全写在浏览器里不就完了？」不行，有两类事浏览器做不到：

1. **数据存在哪。** 浏览器里的数据是**每台电脑各自一份**。你在 A 电脑加的任务，B 电脑看不到。数据要共享，就必须有一台大家都访问得到的机器。
2. **秘密不能放前端。** 任何发到浏览器的东西，用户按 F12 都能看到。数据库密码、支付密钥放前端等于公开发布。

所以「前后端分开」不是设计者喜欢折腾，是有硬性原因的。

## 2. 端口：机器上的门牌号

一台机器上可以同时跑很多程序。**端口就是给每个程序分配的号码**，请求带上号码，才知道该交给谁。

```
http://localhost:3001/api/health
            ────
            端口号
```

| 你看到的地址 | 意思 |
| --- | --- |
| `localhost` | 「本机」，就是你这台电脑 |
| `3001` | 找 3001 号端口上的那个程序 |
| `/api/health` | 交给它之后，要走的具体路径 |

本教程用两个固定端口：

| 端口 | 谁在上面 |
| --- | --- |
| `5173` | 前端（Vite 开发服务器） |
| `3001` | 后端（Express） |

::: danger 端口被占用会怎样
如果 3001 上已经有别的程序在跑，你的后端就起不来，报错类似 `EADDRINUSE`。

这是**很常见**的卡点，因为 3001 这种端口容易被别的软件抢。处理方法在 [项目启动 › 常见误区](/guide/ch01#_9-常见误区)。
:::

## 3. HTTP：浏览器和后端的说话方式

浏览器和后端之间的对话遵循 HTTP。**你需要认识这几个词**，因为报错信息里全是它们。

### 一次请求由四部分组成

```bash
POST /api/tasks HTTP/1.1
Content-Type: application/json

{"title":"买牛奶"}
└──── ③ 请求体：要传的数据
└──── ② 请求头：关于这次请求的说明
└──── ① 请求行：要干什么、去哪
```

### 状态码：后端的回答

这是**最需要记住**的东西。状态码是三位数字，表示这次请求的结果：

| 状态码 | 意思 | 什么时候看到 |
| --- | --- | --- |
| `200` | 成功 | 一切正常 |
| `201` | 创建成功 | 刚加了一条新数据 |
| `204` | 成功但没内容 | 删掉了，前端不需要再拿数据 |
| `400` | **你发的东西有问题** | 数据格式错、校验不过 |
| `404` | 找不到 | 路径写错，或者那条数据没了 |
| `500` | **后端自己崩了** | 代码有 bug、数据库挂了 |

**`400` 和 `500` 的区别是排错时的分水岭：**

| 状态码 | 问题在谁身上 | 你该看哪 |
| --- | --- | --- |
| `400` | 你的请求 | 发了什么数据过去，对照接口文档 |
| `500` | 后端代码 | 后端终端的日志 |

很多教程不区分这两个，读者拿到 500 就去查后端，其实是自己 JSON 写错了。

::: warning 200 不代表一定成功
有些后端会返回 `200` 但响应体里装的是一句错误信息。所以**先看状态码，再看内容**。
:::

## 4. JSON：前后端交换数据的格式

后端查完数据库，要把它交给前端。格式就是 JSON。

```json
{
  "id": 1,
  "title": "买牛奶",
  "done": false,
  "createdAt": "2026-10-02T07:17:26.684Z"
}
```

**JSON 的规则很短：**

| 规则 | 对错 |
| --- | --- |
| 字段名和字符串值要用双引号 `"` | ✅ `"title": "买牛奶"` |
| 用**逗号**分隔，**最后一个后面没有逗号** | ✅ `{"a":1, "b":2}` |
| 花括号 `{}` 是对象，方括号 `[]` 是数组 | ✅ |
| 布尔值写 `true` / `false`，**不加引号** | ✅ `{"done": false}` |
| 数字不加引号 | ✅ `{"id": 1}` |

### 最常见的三个 JSON 错误

```
❌ {"title": '买牛奶'}     用了单引号
❌ {"title": "买牛奶",}    最后一个字段后面多了逗号
❌ {title: "买牛奶"}       字段名没加引号
```

**在 Windows 的 PowerShell 里还有一个坑**，这个坑不是 JSON 本身的问题：

```powershell
# 这样发出去的 body 是坏的，双引号被 PowerShell 吃掉了
curl.exe -d '{"title":"买牛奶"}' http://localhost:3001/api/tasks
```

绕法是写进文件再发：

```powershell
Set-Content -Path t.json -Value '{"title":"买牛奶"}' -Encoding UTF8 -NoNewline
curl.exe -X POST http://localhost:3001/api/tasks --data-binary "@t.json" -H "Content-Type: application/json"
```

本教程的速查表里专门列了这一条。macOS、Linux、Git Bash 没有这个问题。

## 这四件事怎么用

回头看「项目启动」要做的事，现在应该能解释清楚了：

| 「项目启动」的动作 | 用到了哪一条 |
| --- | --- |
| 开两个终端起两个服务 | 端口：两个程序要用不同号码 |
| 浏览器请求 5173 而不是 3001 | 端口 + 代码跑在哪：前端在浏览器，后端在另一台机器 |
| `curl -i` 看到状态行 | HTTP：状态码是后端的回答 |
| 看到 `400 VALIDATION_FAILED` | HTTP：数据不对是你自己的问题 |
| 看到 `INVALID_JSON` | JSON：请求体格式坏了 |
| 控制台报 CORS | HTTP：跨源规则，浏览器在替你把关 |
