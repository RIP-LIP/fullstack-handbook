# 数据存储

> 目标：加的任务能存进数据库、重启不丢，并且**前后端用同一份校验规则**。全程 40 分钟。

「项目启动」那篇做完后端只会回一句 `ok`。这篇给它加四个接口，数据落到 SQLite 里。

**这一章真正想教你的不是那四个接口**——那部分两小时就能会。真正值钱的是第三小节：**为什么校验规则要写在一个文件里，而不是前后端各写一份。**

## 1. 怎么把代码从这一章拿到手

```bash
git checkout v0.2
npm install
```

确认后端还在跑（没跑的话 `npm run dev:api`）。

## 2. 先看要得到什么

这一章做完，四个接口可用：

| 方法 | 路径 | 作用 | 成功返回 |
| --- | --- | --- | --- |
| GET | `/api/tasks` | 列出所有任务 | `200` |
| POST | `/api/tasks` | 新建 | `201` |
| PATCH | `/api/tasks/:id` | 改标题或完成状态 | `200` |
| DELETE | `/api/tasks/:id` | 删掉 | `204` |

## 3. 为什么用 SQLite，以及换成 Postgres 要改什么

**选 SQLite 是因为它零安装成本。** 它是个文件，不是需要装、配置、开服务、设密码的数据库系统。读者装完 Node 就能往下走。

代价是并发写入能力弱。**这个代价什么时候变得不可接受，讲换数据库那篇会讲。**

先看建表语句（`apps/api/src/db.ts`）：

```sql
CREATE TABLE IF NOT EXISTS tasks (
  id         INTEGER PRIMARY KEY AUTOINCREMENT,
  title      TEXT    NOT NULL,
  done       INTEGER NOT NULL DEFAULT 0,
  created_at TEXT    NOT NULL
)
```

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | INTEGER | 主键，`AUTOINCREMENT` 让数据库自动发号 |
| `title` | TEXT | 任务标题 |
| `done` | INTEGER | SQLite 没有布尔值，用 `0` / `1` |
| `created_at` | TEXT | 存 ISO 字符串，方便排序 |

::: warning 别手动建表
表由后端启动时自动创建，代码在 `apps/api/src/db.ts`。你不需要执行任何 SQL 命令，**起后端就够了**。
:::

### 换成 PostgreSQL 要改什么

这是本章的一个知识点。真正要改的不是「SQL 语句」，是这几处：

| 要改的地方 | 原因 |
| --- | --- |
| `AUTOINCREMENT` → `SERIAL` 或 `IDENTITY` | 语法不同 |
| 连接方式 | SQLite 是**同步**的，Postgres 要异步（`await`） |
| 连接池 | SQLite 单文件，Postgres 是网络服务，需要限制并发连接数 |
| 日期类型 | Postgres 有真正的 `TIMESTAMP`，不用存字符串 |

**注意第一行**：代码从同步变异步，影响的不只是那几行 SQL，调用它的每个函数都要跟着 `await`。这就是为什么换数据库不是改个连接字符串那么简单。

## 4. 一份校验，两端共用

这是本章的核心。

### 先看问题长什么样

假设你在**前端**写了校验「标题不能为空」，在**后端**也写了同样的规则。看起来没问题，直到某天有人改了后端的规则：

```ts
// 前端：最多 50 字
title: max(50)

// 后端：最多 200 字（需求变了，只改了后端）
title: max(200)
```

现在：**前端拦住的输入，后端其实允许**。用户在前端输了 100 字被拦住，但换成 `curl` 就能存进去。数据从别的口子进来了。

**这就是「校验写两处必然漂移」的意思。**

### 解法：放进共享包

新建一个包 `packages/shared`，前后端都从这里 import：

```ts
// packages/shared/src/index.ts
import { z } from 'zod'

/** 创建任务时的输入 */
export const CreateTaskInput = z.object({
  title: z.string().trim().min(1, '标题不能为空').max(200, '标题最多 200 个字符'),
})

/** 修改任务时的输入，所有字段可选 */
export const UpdateTaskInput = z.object({
  title: z.string().trim().min(1, '标题不能为空').max(200, '标题最多 200 个字符').optional(),
  done: z.boolean().optional(),
})
```

`z` 是 [Zod](https://zod.dev)，专门做「描述数据长什么样」的库。

**后端用它做真正的拦截：**

```ts
// apps/api/src/routes/tasks.ts
import { CreateTaskInput } from '@fullstack/shared'

tasksRouter.post('/tasks', (req, res) => {
  const parsed = CreateTaskInput.safeParse(req.body)
  if (!parsed.success) {
    throw new HttpError(400, 'VALIDATION_FAILED', '输入不符合要求', flatten(parsed.error))
  }
  // parsed.data 就是校验通过的干净数据
})
```

**前端用同一份做即时反馈：**

```ts
// apps/web/src/components/TaskForm.tsx
import { CreateTaskInput as schema } from '@fullstack/shared'

const parsed = schema.safeParse({ title })
if (!parsed.success) {
  setFieldError(parsed.error.issues[0]?.message)  // 提示用户
}
```

改 `max(200)` 为 `max(50)`，**只改 `packages/shared` 一个文件，前后端同时生效**。

::: danger 前端校验不是安全边界
上面前端那段代码，读者可以直接在控制台里绕过。它存在的意义是**体验**——用户打完字立刻看到「标题不能为空」，不用等一次网络往返。

**安全边界在后端。** 前端校验是改善体验，后端校验是保证正确性，两者都要有，但只有后者是必须的。
:::

## 5. 哪些是这个项目特有的，哪些是通用的

任务清单只是载体。这一节明确切一下，换一个项目时你要重写什么、可以直接拿走什么。

| 上面出现的东西 | 换个项目要改吗 | 说明 |
| --- | --- | :-: |
| `tasks` 这张表的**字段** | 改 | 换成你自己的字段。这是最不值钱也最容易改的部分 |
| `/api/tasks` 这个**路径** | 改 | 路径是你定的，跟着资源名走 |
| 四个接口的**方法**（`GET` / `POST` / `PATCH` / `DELETE`） | 不改 | 资源的增删改查永远是这四个 |
| **`INTEGER PRIMARY KEY AUTOINCREMENT` 主键** | 不改 | 任何关系型数据库都有自增主键 |
| **`IF NOT EXISTS` 建表** | 不改 | 迁移的雏形就在这 |
| `created_at` 存 ISO 字符串 | 抄思路 | Postgres 要换成 `TIMESTAMP` |
| **校验规则写在一个文件里** | 不改 | **这是本章最值钱的一条** |
| **错误响应统一成一个形状** | 不改 | 本项目用 `{ error: { code, message, fields? } }`，换形状也要统一 |
| **`PATCH` 只更新传了的字段** | 不改 | 任何「局部更新」都这样 |
| **SQLite 没有 boolean，要转换** | 换库后不用 | 换 Postgres 就没这问题 |

**能直接拿走的是右边那六行。** 表结构和路径是每秒钟都要重写的东西，规则不是。

如果你现在要做一个完全不同的东西——读书笔记、记账、拼单——那么你会发现：

- `title` / `note` 换成你的字段
- 「勾完成」换成你的状态字段，或者干脆没有
- **剩下的全部一样**

这就是把一个例子学透和把一个例子抄完的区别。

## 6. 验证

### 加一条

```bash
curl -X POST http://localhost:3001/api/tasks \
  -H "Content-Type: application/json" \
  -d '{"title":"买牛奶"}'
```

::: request
```bash
curl -X POST http://localhost:3001/api/tasks \
  -H "Content-Type: application/json" \
  -d '{"title":"买牛奶"}'
```

```http
HTTP/1.1 201 Created
Content-Type: application/json

{"id":1,"title":"买牛奶","done":false,"createdAt":"2026-10-02T07:17:26.684Z"}
```
:::

看到 `201` 和一条带 `id` 的数据就成了。`id` 是数据库自动发的。

### 故意发个空标题

这一步是验证共享校验**真的生效**：

::: request
```bash
curl -X POST http://localhost:3001/api/tasks \
  -H "Content-Type: application/json" \
  -d '{"title":"   "}'
```

```http
HTTP/1.1 400 Bad Request
Content-Type: application/json

{"error":{"code":"VALIDATION_FAILED","message":"输入不符合要求","fields":{"title":"标题不能为空"}}}
```
:::

注意 `"   "` 是三个空格，不是空字符串。`.trim()` 会把空格去掉，然后触发「不能为空」。**如果只写 `min(1)` 不写 `trim()`，用户输入几个空格就能存进去**——这是新手很容易漏的一步。

### 剩下三个接口

```bash
# 列出
curl http://localhost:3001/api/tasks

# 勾完成
curl -X PATCH http://localhost:3001/api/tasks/1 \
  -H "Content-Type: application/json" -d '{"done":true}'

# 删除（不可恢复）
curl -X DELETE http://localhost:3001/api/tasks/1
```

删除后再删一次，会得到 `404`：

```json
{"error":{"code":"TASK_NOT_FOUND","message":"任务 1 不存在"}}
```

### 确认数据真的落盘了

停掉后端（`Ctrl+C`），再起一次，然后：

```bash
curl http://localhost:3001/api/tasks
```

数据还在，说明存进了文件而不是内存。

## 7. 常见误区

::: details 「前端已经校验过了，后端不用再校验」

**这是本章最想让你记住的一条。**

前端校验可以用 `curl` 绕过——`curl` 不经过你的前端代码，它直接跟后端说话。任何校验只要不在后端，就不是校验。

实测一下（在**另一个终端**，不要用浏览器的地址栏）：

```bash
curl -X POST http://localhost:3001/api/tasks \
  -H "Content-Type: application/json" -d '{"title":"   "}'
```

后端照样返回 `400`。这条规则在**服务端**，跟你有没有在界面上点按钮无关。
:::

::: details 「数据丢了 / 页面空了」

按顺序查：

```bash
# 1. 数据库文件在不在
dir apps\api\data
```

应该有 `app.db` 和几个 `-wal` / `-shm` 文件（正常，SQLite 的工作文件）。

```bash
# 2. 后端起没起
curl -i http://localhost:3001/api/health
```

```bash
# 3. 表建了没。后端启动日志里如果没有 SQL 报错就是建好了
```

想彻底重来：

```bash
npm run db:reset
```

**这会删掉整个数据库文件**，下次启动后端自动重建。不可恢复。
:::

::: details 「请求体不是合法的 JSON」

三种原因：

1. **PowerShell 吃了双引号**（最常见）。见速查表，用 `--data-binary "@文件"` 绕
2. JSON 本身写错了，比如单引号、多余逗号
3. 中文编码问题，加 `-H "Content-Type: application/json; charset=utf-8"`
:::

## 8. 隐性规则

- **SQLite 没有 boolean 字段。** 表里存 `0` / `1`，读出来时要转。忘了转换，前端的复选框会永远显示未勾选。
- **`PATCH` 只更新传了的字段。** 传 `{"title":"新标题"}` 不应该把 `done` 重置成 `false`。代码里用 `??` 兜住没传的字段。
- **所有错误响应形状必须统一。** 本项目固定是 `{ error: { code, message, fields? } }`。前端只要写一个解析函数，不用为每种错误单独处理。
- **`IF NOT EXISTS` 让建表可以每次启动都跑。** 真正的「迁移」在这里还很简单——等表结构要改的时候才需要版本表。
- **数据库文件不要提交到 git。** `.gitignore` 里已经加了 `apps/api/data/`。每个读者自己生成一份。
