# 第1章 跑起来，看懂一次请求

> 目标：把前端和后端同时跑起来，让浏览器里的一次点击真的能拿到后端的数据。全程 25 分钟，不写业务逻辑。

这一章代码是「空的」——后端只回一句 `ok`，前端只显示这句话。这是故意的。全栈入门最容易卡住的地方从来不是业务逻辑，是**链路**：两个服务怎么各自起来、怎么互相找到、请求卡在哪一环。所以这一章不写功能，只把链路打通并看懂。

## 1. 一个应用，两台服务器

任务清单这类应用天然分两半：

```
浏览器 ──HTTP──► 后端 ──SQL──► 数据库
   ▲
   └──────HTML/JS/CSS────────┘
```

浏览器里的代码（HTML/JS/CSS）跑在**用户的机器**上。后端代码跑在**一台单独的机器**上，它的工作是接收请求、拿数据、返回结果。

所以「跑起来」意味着跑起来两个东西，不是跑一个。这也是新手最常见的困惑来源：明明装好了一个项目，为什么还有个东西没起来。

## 2. clone 和安装

```bash
git clone https://github.com/RIP-LIP/fullstack-todo-app.git
cd fullstack-todo-app
npm install
```

`npm install` 之后项目里会多出 `node_modules/` 目录，装的是项目依赖的全部第三方代码。这一步会下载几百个包，第一次慢是正常的。

装完你应该能看到这个结构：

```bash
# 看目录结构
dir
```

```
apps\      api（后端）  web（前端）
packages\  shared（两端共用的类型和校验）
```

`packages/shared` 这个目录在第2章才用上，现在知道有这么个地方就行。

::: tip 为什么不用 pnpm
两个服务加一个共享包，一共三个目录。用 npm 自带的 workspaces 就能管起来，不值得为这个规模引入一个新工具。
:::

## 3. 起后端

打开**第一个终端**，在项目根目录：

```bash
npm run dev:api
```

你应该看到：

```text
[api] 已启动 → http://localhost:3001
[api] 试一下：curl -i http://localhost:3001/api/health
```

看到 `已启动` 就成功了。

这个终端**不要关**。关掉窗口等于杀掉后端，前端会立刻开始报错。

## 4. 先用 curl 确认后端是活的

在**第二个终端**（或者浏览器还没开的时候）：

```bash
curl -i http://localhost:3001/api/health
```

`-i` 的意思是「把响应头也打出来」。输出长这样：

::: request
```bash
curl -i http://localhost:3001/api/health
```

```http
HTTP/1.1 200 OK
Content-Type: application/json; charset=utf-8
Content-Length: 27

{"ok":true,"service":"api"}
```
:::

逐行拆开：

| 这一行 | 意思 |
| --- | --- |
| `HTTP/1.1 200 OK` | 状态行。`200` 表示成功。`404` 是路径不对，`500` 是服务端自己出错 |
| `Content-Type: application/json` | 响应体是 JSON，前端会按 JSON 解析 |
| `Content-Length: 27` | 响应体有 27 个字节 |
| `{"ok":true,...}` | 真正的内容 |

**先看状态码再看内容**，这是读接口响应该有的顺序。先看内容容易漏掉一个「200 里面装着一段错误信息」的情况。

::: tip 为什么先 curl 一下
多绕一步换来的是：出问题时你知道该怀疑谁。curl 能通说明后端活着，问题在前端；curl 就不通，问题在后端。这一步省掉的话，你会在浏览器控制台里盯着一个红色的 `Failed to fetch` 猜半天。
:::

## 5. 起前端

开**第三个终端**：

```bash
npm run dev:web
```

你应该看到：

```text
VITE v5.4.21  ready in 1663 ms

➜  Local:   http://localhost:5173/
```

浏览器打开 `http://localhost:5173`，页面中央显示「任务清单」和一个输入框。

现在三个终端是这样：

| 终端 | 跑什么 | 关掉的后果 |
| --- | --- | --- |
| 1 | `npm run dev:api` | 前端报连不上后端 |
| 2 | 随便敲 curl，无所谓 | 没影响 |
| 3 | `npm run dev:web` | 浏览器打不开页面 |

## 6. 一次请求穿过了什么

在浏览器里打开开发者工具（F12），切到 Network 面板，刷新页面。你会看到一条请求：

```
GET http://localhost:5173/api/health    200
```

**注意端口是 5173，不是 3001。** 前端并没有直接去找后端。

发生了什么：

```
浏览器 ──► localhost:5173/api/health
              │
              │ Vite 开发服务器（代理）
              ▼
          localhost:3001/api/health
```

前端的代码里写的是相对路径 `/api/health`，指向它自己所在的 5173。Vite 开发服务器收到这个请求，发现路径以 `/api` 开头，就转发给 3001。

这带来一个很实际的好处：**在浏览器看来，这从头到尾都是同源的普通请求**，没有跨域那回事。

## 7. 如果不做代理会怎样

假设你没有配这个代理，前端代码写成绝对地址：

```ts
// 反面示例，不要这么写
fetch('http://localhost:3001/api/health')
```

浏览器会先发一个 `OPTIONS` 预检请求，问后端「我能不能访问你」。后端没回应这个预检，浏览器就**在真正请求发出之前**拦下来了。

表现是控制台里一条红色报错，`Network` 面板里那条 `GET` 是灰的或者干脆没有：

```
Access to fetch at 'http://localhost:3001/api/health' from origin
'http://localhost:5173' has been blocked by CORS policy
```

**分不清 CORS 和路径写错是新手的高频卡点。** 记一个判据：

| Network 面板里的表现 | 多半是 |
| --- | --- |
| 有一条红色请求，状态是 500/404 | 后端的问题，去看后端终端的输出 |
| 没有任何请求记录，状态栏显示 CORS | 代理没配，或者前端写了跨域的绝对地址 |
| 有一条 `OPTIONS` 之后失败 | 跨域，同上 |

代理的配置在 `apps/web/vite.config.ts`：

```ts
export default defineConfig({
  plugins: [react()],
  server: {
    port: 5173,
    proxy: {
      '/api': {
        target: 'http://localhost:3001',
        changeOrigin: true,
      },
    },
  },
})
```

## 8. 两个隐性规则

### 前端连 5173，不是 3001

前端的代码里写 `/api/xxx` 就行，永远不要写 `http://localhost:3001`。这不是风格问题：写死了绝对地址，线上部署时一定会出问题，因为线上没有 3001 这个东西。

### 后端挂了，前端拿到的是网络错误，不是 500

这两件事在浏览器里长得完全不一样：

| 情况 | 前端 `fetch` 的表现 | 控制台 |
| --- | --- | --- |
| 后端返回 500 | 正常拿到响应，状态码 500 | Network 里有这条请求，红色 |
| 后端进程没跑 | `fetch` 直接抛异常 | Network 里**没有**这条请求 |

第二种情况里 `fetch` 是「根本没发出去」，不是「发出去了被拒绝」。所以判断的时候要分开写：

```ts
try {
  res = await fetch('/api/health')
} catch (err) {
  // 这里只可能是「没发出去」：后端没起、代理没配、地址打错
  throw new RequestError(0, 'NETWORK_ERROR', '连不上后端')
}
```

第3章会用到这个区分。

::: danger `npm run dev:api` 的窗口不能关
很多人以为终端里的报错和自己无关。关掉它，等于杀掉后端进程，页面上所有操作立刻失败，浏览器控制台还只会告诉你一句信息量很低的 `Failed to fetch`。
:::

## 9. 常见误区

::: details 「接口返回 404 就是路由写错了」

**不一定是。** 404 有三种来源，症状看起来一样：

1. 路径真的写错了（`/api/healths` 拼错）
2. 代理没配，请求打到了 Vite 自己，Vite 找不到这个路径
3. 后端起来了，但启动的端口和代理指向的不一致

按这个顺序排查：

```bash
# 1. 直连后端。通了说明后端和路由都没问题，问题在前端或代理
curl -i http://localhost:3001/api/health

# 2. 走代理。通了说明代理也正常
curl -i http://localhost:5173/api/health
```

两步的结果对照一下：

| 直连 3001 | 走 5173 | 结论 |
| --- | --- | --- |
| 200 | 200 | 都正常 |
| 200 | 404 | 代理没配对，查 `vite.config.ts` |
| 404 | 404 | 路由写错了，查路径 |
| 连不上 | 连不上 | 后端根本没起来，看终端 |

:::

::: details 「端口被占用了」

换个端口就行，但**三处必须一起改**，只改一处会得到更难查的问题：

1. `apps/api/src/index.ts` 的 `PORT ?? 3001`
2. `apps/web/vite.config.ts` 的 `target` 和 `port`
3. 教程正文里所有出现 3001 / 5173 的地方

查谁占了端口：

```bash
# Windows
netstat -ano | findstr :5173
```

::: tip 端口改了之后浏览器缓存了旧的代理
Vite 改了配置文件有时不会自动重启。如果改完行为没变，按 `Ctrl+C` 停掉前端再重新 `npm run dev:web`。
:::

## 10. 隐性规则

- **`server.port: 5173` 写在配置里，不是靠运气撞上的。** 端口冲突时 Vite 会自动 +1，然后你就得去改代理配置了。写死省事。
- **开发期和生产期是两回事。** 代理只在 `npm run dev` 时存在，`npm run build` 产出的静态文件里没有它，部署时的转发是另一套机制。第 6 章会真正遇到这个区别。
- **`tsx watch` 意味着后端代码改完自动重启。** 但你如果是 `Ctrl+C` 停的、忘了重新 `npm run dev:api`，改代码是不会生效的。这时候看一眼后端终端，它还开着吗。
