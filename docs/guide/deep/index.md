# 后端往下走

主线那三篇用任务清单把一个应用跑通了：一个进程、一张表、一个页面。那套东西的边界在哪，[前端交互](/guide/ch03)最后一节说过——界面和数据对齐了，界面之下的事一件没碰。

从单表到多表开始，后端的问题才出现。表之间有了引用，改一个数据结构会让另一个变非法；一次操作要同时改两张表，中途失败会留下不一致；两个人同时下单，库存会算错。

这一组用一个订单/库存的载体讲这些。**载体是编的**——没有真实业务，没有真实用户，四张表只是为了在默认设置下真的把上述问题复现出来。订单和库存选它是因为这些失败在这个领域里是自明的，不用额外解释「为什么这两张表有关系」。

这一组从单进程、一个进程一条连接开始，把那些假设逐个打破：
多个表、多个版本的代码并存、一次操作改多张表、真会并发的数据库、同一个请求来两次。
**六篇读完，剩下的假设只有一个——谁在操作。**

| 篇 | 标题 | 你会看到什么 |
| --- | --- | --- |
| [数据模型](/guide/deep/ch04) | 删一个已经被订单引用的商品，返回的是 500 | 约束冲突是业务语义，不是数据库异常 |
| [迁移](/guide/deep/ch05) | 改了建表语句，老库启动后列还是老的 | 给数据库也记一份版本 |
| [零停机变更](/guide/deep/ch06) | 改了个列名，老代码的响应里那个字段整个消失了 | 新旧两个版本怎么同时对着一个库 |
| [事务](/guide/deep/ch07) | 建订单失败之后，库存也少了 3 件 | 一次操作要同时改三张表，中途失败不能留下半套数据 |
| [换 PostgreSQL](/guide/deep/ch08) | 两个请求都抢到了最后一件库存，库存只扣了一件 | 换一个真会并发的数据库，业务代码一行不改 |
| [幂等](/guide/deep/ch09) | 同一个请求发两次，建了两笔订单，库存扣了两次 | 让唯一约束当判据，失败时不留下半截状态 |

## 代码

配套代码在 **[fullstack-backend](https://github.com/RIP-LIP/fullstack-backend)**，和主线是**两个独立仓库**：领域不同、端口不同（这里用 3002），可以同时开着跑。

每篇一个 git tag，`git checkout` 到任意一篇的起点：

```bash
git clone https://github.com/RIP-LIP/fullstack-backend
cd fullstack-backend
npm install
```

切到某一篇：

```bash
git checkout v1.0
npm install
npm run dev:api
```

`verify-tag.mjs` 能证明任何一个 tag 都能被别人独立跑起来——它把 tag 导出到临时目录、装依赖、跑测试、起服务探健康，跑不通就退出 1：

```bash
node scripts/verify-tag.mjs v1.0
```

**这条命令会改动一个临时目录，也会在本机短暂占一个端口**，不碰你当前工作区。

## 和主线的关系

不是「进阶版主线」，是**另一条轴**。两条线讲的东西几乎没有重叠：

| | 主线（任务清单） | 这一组（订单/库存） |
| --- | --- | --- |
| 表的数量 | 一张 | 四张，彼此有引用 |
| 主要矛盾 | 前后端怎么对齐 | 多张表之间怎么不出错 |
| 到了这一组之后 | 跑得通 | 换字段时新旧代码怎么共存 |
| 端口 | 3001 | 3002 |
| 什么时候读 | 第一次做全栈 | 已经能跑通单表应用 |

主线没读完就来这一组，ch04 的外键会显得突然。没做过主线的话，先把[数据存储](/guide/ch02)看完。

同样，这一组也不替代主线——它全程没有界面。
