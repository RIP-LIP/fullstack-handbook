# 事务

> 目标：建一笔订单要同时改三张表，中途失败三张表都不变。做完你会发现，**上一章给你的 `transaction` 其实是假的**，这一章把它修好。全程 90 分钟。

前面三章解决的都是「改一次」：改列、改结构、改字段。这一章的方向不一样——
**一次操作要同时改多张表**。

载体上这两张表建了但一直没用过（`orders` / `order_items`），
所以这一章先把建订单的路径写出来。

## 1. 怎么把代码拿到手

```bash
git checkout v1.3
npm install
npm run dev:api
```

```bash
curl -i http://localhost:3002/api/health
```

```
HTTP/1.1 200 OK
Content-Type: application/json; charset=utf-8

{"ok":true,"service":"api"}
```

建一笔订单要动三张表：

| 步骤 | 表 | 语句 |
| --- | --- | --- |
| 1 | `orders` | `INSERT` 一行，状态 `pending` |
| 2 | `order_items` | 每件商品 `INSERT` 一行，存**下单时的价格快照** |
| 3 | `products` | `UPDATE stock = stock - n` |

## 2. 失败：不用事务，三张表对不上

不加任何保护，把三步依次执行，在第 4 步让库存不足。脚本在**内存库**里跑，
建表建完就扔，**不碰你的开发数据**：

```bash
node scripts/probe.mjs notx
```

```
第 1 步：orders 建好了，id = 1
第 2 步：甲的库存扣了 3，changes = 1
第 3 步：order_items 写了 1 行
第 4 步：乙库存不足，changes = 0  <- 这一步失败了

=== 现在库里是什么状态（只读）===
订单 1 存在: true
它的明细行数: 1 （这一单要 2 行）
甲的库存: 7 （下单前 10，这一单要买 3 件）
甲的库存和订单对得上吗: 对得上
```

**订单存在，明细缺一行。** 客户端拿到的是一个「看起来成功」的订单，
点进去发现少了一件商品。

注意那个处理顺序：**先扣库存，扣成功才写明细**。所以乙扣不动的时候，
它那一行明细根本不会被写进去，订单就此缺一行。
把这两步反过来（先写明细再扣），你会得到另一种更难查的结果——
明细是全的，但有一件商品没扣库存，账面上看不出任何异常。

这类不一致最难查的原因不是它错得多，而是**它错得不像错的**：
订单状态是 `pending`（合法的），金额是整数（合法的），外键都满足（合法的）。
没有任何一条检查会报警。只有等仓库真去发货时才发现少了一单。

::: danger 不一致不会自己暴露
第 4 步的失败**没有抛异常**。`UPDATE ... WHERE stock >= 50` 匹配不到行，
语句成功执行，0 行受影响。程序继续往下走，看起来一切正常。

所以「加一个事务」的动机不是「防止程序崩溃」，是**让部分成功这件事不可能发生**。
:::

## 3. 但你现在这个事务是假的

上一篇的 `db.transaction` 是这样的：

```ts
async transaction<T>(fn: (tx: Db) => Promise<T>): Promise<T> {
  raw.exec('BEGIN')
  try {
    const result = await fn(db)      // <- await 期间事件循环会跑别的请求
    raw.exec('COMMIT')
    return result
  } catch (err) {
    raw.exec('ROLLBACK')
    throw err
  }
}
```

`BEGIN` 和 `COMMIT` 是对的，缺的是它们中间那段时间的保护。
`await fn(db)` 把控制权交回事件循环，而事件循环会继续处理**其他请求**。

### 实测：别的请求的写入被卷进了这个事务

这个场景在 `apps/api/test/transaction.test.ts` 里，它就是这一章的回归守卫。
单独跑它（**测试跑在临时库上，不碰你的开发数据**）：

```bash
npx tsx --test --test-name-pattern="并发请求的写入不会被事务回滚吞掉" apps/api/test/transaction.test.ts
```

```
✔ 并发请求的写入不会被事务回滚吞掉 (347.288ms)
ℹ tests 1
ℹ suites 0
ℹ pass 1
ℹ fail 0
```

它构造的就是上面那一场：事务体里 `await` 一个定时器（让出事件循环），
另一个请求在这个窗口里往同一条连接写库，事务随后抛错。

**没有那道门的时候，这条断言会挂。** 挂的是 `concurrent.n === 1`：
另一个请求写的那一行跟着回滚消失了，`changes` 变成 0——
**而那个请求拿到的是成功，日志里没有任何异常。**

这不是「事务偶尔失效」，是**事务连自己的边界在哪都不知道**：
`BEGIN` 之后到 `COMMIT` 之间的所有语句都属于这个事务，不管是谁发的。

### 什么时候会出事：让出了事件循环

不是所有 `await` 都危险。完整对照（两种实现 × 两种事务体）：

| 实现 | 事务体里 await 什么 | 另一个请求的结果 | 它写的行 |
| --- | --- | --- | --- |
| 没有门 | 只 await 同步查询 | `fulfilled` | 还在 |
| 没有门 | **await 定时器** | `fulfilled` | **没了** |
| 加了门 | 只 await 同步查询 | `fulfilled` | 还在 |
| 加了门 | await 定时器 | `fulfilled` | 还在 |

**第二行是唯一的故障点。** 这张表不是推测，是四行分别跑出来的，
造法就两处改动：

| 表格里的行 | 怎么造 |
| --- | --- |
| 「没有门」 | `db/sqlite.ts` 里把 `withConnection` 的 `while (busy && ...)` 那三行去掉 |
| 「只 await 同步查询」 | 测试里 `await new Promise((r) => setTimeout(r, 40))` 换成 `await Promise.resolve()` |

只去掉门、保留定时器，再跑上面那条命令，**它会挂**（下面这段是本机实跑）：

```
✖ 并发请求的写入不会被事务回滚吞掉 (415.5924ms)
ℹ tests 1
ℹ pass 0
ℹ fail 1

test at apps\api\test\transaction.test.ts:75:1
✖ 并发请求的写入不会被事务回滚吞掉 (415.5924ms)
  AssertionError [ERR_ASSERTION]: 事务窗口里那个请求的写入必须存活，不能跟着回滚消失

  0 !== 1
```

`0 !== 1` 就是「那一行没了」。

两处**同时**改（去掉门 + 把定时器换成 `Promise.resolve()`）反而是绿的——
这正是表格第一行。改坏代码时一次只改一处，两处一起改你测到的是另一种组合。

为什么第一种情况没事：

`await` 一个已经 resolve 的 Promise，产生的只是**微任务**。
微任务队列会被一次性排空，而 Node 要处理下一个 HTTP 请求需要**宏任务**。
所以「只 await 数据库查询」的链路上，事件循环根本没有机会插进来跑别的请求。

一旦 await 的是定时器、真实的网络 IO、或者任何要等事件循环的东西，
宏任务就会插进来，另一个请求的 `await db.query(...)` 就执行在这个事务里。

::: warning `migrate.ts` 已经踩在同一个坑上
迁移器里是 `await db.transaction(async (tx) => { await migration.up(tx) })`。
今天它没出事，**是因为所有迁移的 `up` 都只 await 数据库查询**——
微任务链，插不进来。

只要有一个迁移的 `up` 里出现了真实 IO（读一个文件、发一个请求），
它就会在迁移执行期间把别的请求卷进来。改迁移时这一点要盯着。
:::

## 4. 修它：连接只归一个事务

三处改动，都在 `apps/api/src/db/sqlite.ts`。

### 一、标记「这段异步代码属于这个事务」

```ts
import { AsyncLocalStorage } from 'node:async_hooks'

const txOwner = new AsyncLocalStorage<true>()
let busy = false
const waiters: Array<() => void> = []
```

**为什么必须用 `AsyncLocalStorage`，不能用普通变量**：
判断「这个 query 是不是事务自己的」时，代码**不在栈上**——
中间隔着一个已经 await 出去的 Promise。调用栈那套判断在这里是失效的。
`AsyncLocalStorage` 存的是**异步上下文**，事务体里 await 出去的每一段
异步代码都带着同一个标记，外面的请求拿不到。

### 二、拿连接要走门

```ts
async function withConnection<T>(fn: () => T): Promise<T> {
  while (busy && txOwner.getStore() !== true) {
    await new Promise<void>((resolve) => waiters.push(resolve))
  }
  return fn()
}
```

`query` 和 `one` 全部改走它。条件是「**不是这个事务的主人**」：

- 主人在事务里 → 直接执行
- 别人在事务开着的时候来 → 排队，等事务结束

`query` / `one` 变成：

```ts
async query<T>(sql: string, params: readonly Param[] = []): Promise<T[]> {
  return withConnection(() => raw.prepare(sql).all(...params) as unknown as T[])
},
```

### 三、事务本身

```ts
async transaction<T>(fn: (tx: Db) => Promise<T>): Promise<T> {
  // 嵌套判据是「我自己是不是已经在事务体里」，不是 busy。
  // busy 为 true 也可能只是另一个请求开着事务，那种情况该排队。
  if (txOwner.getStore() === true) throw new NestedTransactionError()

  while (busy) {
    await new Promise<void>((resolve) => waiters.push(resolve))
  }
  busy = true
  raw.exec('BEGIN')

  try {
    const result = await txOwner.run(true, () => fn(db))
    raw.exec('COMMIT')
    return result
  } catch (err) {
    try {
      raw.exec('ROLLBACK')
    } catch (rollbackErr) {
      console.error('[db] 回滚失败，事务状态可能已经不对了：', rollbackErr)
    }
    throw err
  } finally {
    busy = false
    for (const wake of waiters.splice(0)) wake()
  }
}
```

三处细节，每一个都对应一个具体的坑：

| 写法 | 不这么写会怎样 |
| --- | --- |
| 嵌套判据用 `txOwner` 而不是 `busy` | 用 `busy` 的话，**并发的两个请求**会互相被报成「嵌套事务」，一个成功一个无故失败 |
| `catch` 里 `ROLLBACK` 单独 try/catch | 回滚失败会**顶替**原始错误（见下） |
| 释放队列写在 `finally` | 放错位置的话回滚路径下队列永远不释放，**后面所有请求卡死**，服务假死 |

### 回滚失败顶替错误，是另一种疼

没有活动事务时 `ROLLBACK` 自己会抛：

```bash
node scripts/probe.mjs rollback
```

```
空 ROLLBACK -> cannot rollback - no transaction is active
COMMIT 后 ROLLBACK -> cannot rollback - no transaction is active
```

如果不单独 try/catch，这句 SQLite 报错会**顶替掉**业务错误：
调用方原本的 409 `OUT_OF_STOCK` 变成 500 `INTERNAL_ERROR`，
真正的原因只留在日志里——正是前面几章一直在消灭的那种失败。

所以上面那段 `catch` 里保留原始错误，回滚的错另外打日志。

### 嵌套事务原来不是守卫

改之前那版是这么写的：`BEGIN` 直接执行，嵌套时报错来自 SQLite：

```bash
node scripts/probe.mjs nested
```

```
嵌套 BEGIN -> cannot start a transaction within a transaction
```

**报错来自数据库，不是代码。** 区别在于这句话对读代码的人没有意义，
而且它会经过错误处理变成 500——而「你把事务边界画错了」是应该在开发期
就看清的问题。现在换成项目自己的 `NestedTransactionError`。

### 修好之后

第 3 节那张表的后两行变了：

| 实现 | 事务体里 await 什么 | 另一个请求的结果 | 它写的行 |
| --- | --- | --- | --- |
| 没有门 | **await 定时器** | `fulfilled` | **没了** |
| 加了门 | await 定时器 | `fulfilled` | 还在 |

代价是**事务期间别人要排队**。这就是为什么事务体必须短：

- **里面绝不能做 IO。** 发邮件、调第三方、发消息，任何一个都会把事务从
  毫秒拖到秒，而这段时间整条连接被别人排着队。
- **别在里面等需要这条连接的东西。** 那是死锁。

## 5. 状态机：CHECK 管得住值，管不住转移

`001_init.ts` 里那条约束：

```sql
status TEXT NOT NULL CHECK (status IN ('pending', 'paid', 'shipped', 'completed', 'cancelled'))
```

它管住的是**这一列的值**。它管不住转移，**在内存库里跑，不碰你的开发数据**：

```bash
node scripts/probe.mjs check
```

```
=== CHECK 只管值域，不管转移 ===
造了一个 cancelled 的订单，id = 3
库里所有合法值: [{"status":"cancelled"},{"status":"completed"},{"status":"pending"}]
UPDATE 把它从 cancelled 改成 paid：changes = 1   <- 库接受了
现在它是什么状态: paid

改成 refunded -> ERR_SQLITE_ERROR | CHECK 拦住了值域之外的
```

**一个 cancelled 的订单被直接改成 paid，库照收不误。**
`refunded` 会被拦住，因为那不在枚举里。**值域和转移是两件事**，
`CHECK` 只能管前者。

### 转移表

`apps/api/src/order-state.ts`：

| 从 | 可以到 |
| --- | --- |
| `pending` | `paid`、`cancelled` |
| `paid` | `shipped`、`cancelled` |
| `shipped` | `completed` |
| `completed` | （终态） |
| `cancelled` | （终态） |

规则写在路由外面，因为它是纯逻辑——二十来条规则一秒钟能跑几千遍，
放在路由里就只能靠发请求来碰。

## 6. 扣库存：为什么不能先查后写

教科书写法是「先 SELECT 一下看够不够，够就 UPDATE」：

```ts
// 错的
const p = await tx.one('SELECT stock FROM products WHERE id = ?', [id])
if (p.stock < qty) throw new HttpError(409, 'OUT_OF_STOCK', '库存不足')
await tx.query('UPDATE products SET stock = stock - ? WHERE id = ?', [qty, id])
```

`SELECT` 和 `UPDATE` 之间有时间差。这段代码在事务里，而事务期间
**别的请求在门外排队**（第 4 节那道门）——所以在这个单连接的项目里它其实是安全的。

**但它只在有门的时候安全。** 门是这一章才加的；换成连接池、换成多进程、
换成 PostgreSQL，两个请求就能同时进到 `SELECT` 和 `UPDATE` 之间，
都看到「够」，都执行扣减，库存变负。

把判断放进 `WHERE` 就没这个窗口：

```ts
const updated = await tx.query<{ id: number }>(
  'UPDATE products SET stock = stock - ? WHERE id = ? AND stock >= ? RETURNING id',
  [item.quantity, item.productId, item.quantity],
)
if (updated.length === 0) {
  throw new HttpError(409, 'OUT_OF_STOCK', `商品 ${item.productId} 库存不足`)
}
```

`stock >= ?` 由数据库在**写的那一刻**判断并发不成立的情况，
行锁保证这个判断和写入之间没人插进来。0 行受影响就是没扣成。

**判断放在哪一层，决定了它在多进程下还对不对。**

## 7. 失败：库存不足整体回滚

买 99 件一个只有 3 件库存的商品（**会改数据**）：

::: request
```bash
curl -X POST http://localhost:3002/api/orders \
  -H "Content-Type: application/json" \
  --data-binary '{"userId":1,"items":[{"productId":2,"quantity":99}]}'
```

```http
{"error":{"code":"OUT_OF_STOCK","message":"商品 2 库存不足"}}
```
:::

对照第 2 节那个「半套数据」：现在三张表都回到了调用前的样子。

而且不只是失败的那一步。**两件商品里第二件失败，第一件的扣减也退回去了**——
这一条是「整体回滚」和「只回滚失败那一步」的分界线，也是订单这类操作
必须整体成功的原因。半截订单比没有订单更麻烦：它已经占用了库存。

## 8. 工具选型

### 事务边界：手写 vs 库

| 方案 | 它替你做了什么 | 代价在哪儿 |
| --- | --- | --- |
| **手写 + `AsyncLocalStorage`**（本项目） | 连接归属、排队、嵌套守卫 | 每一行都要自己判断 |
| `better-sqlite3` 的 `transaction()` | 同步事务体，天然不让出事件循环 | 换驱动不解决「共享连接 + 异步事务体」这个结构问题 |
| ORM 自带的事务 | 帮你开事务、帮你回滚 | 边界跟着 ORM 的抽象走，跨多张表时反而看不清 |
| PostgreSQL + 连接池 | 每事务独占一条连接 | 换库是另一章的事 |

**为什么手写**：第 3 节那个 bug 的本质是「共享一条连接 + 事务体是异步的」。
这四个选项里，只有把它俩拆开才真正解决——要么事务体同步，要么事务独占连接。
手写这道门是改动最小、且不牺牲上一篇那个 async 接口形状的做法。

**什么时候该换掉**：换成 PostgreSQL 之后，事务天然独占一条连接，
`withConnection` 这道门就没有存在的必要了（连接池负责隔离）。
到那时删掉它，不是「优化」，是**去掉一层已经没有用的抽象**。

### 事务体同步化：另一条路

把 `Db` 的三个方法全改成同步，事务体就无法 await 别的，
原子性由类型系统保证。这条路更彻底，但代价是上一篇「为换 PostgreSQL
预留 async 形状」的改动要全部回退一遍——**换库时每个 `await` 都要改回去**。

选门而不是选同步，理由是**改动量**：门是 40 行，异步化回退是全项目。
两个方案在 SQLite 上都成立，代价差一个数量级。

### 状态机：手写表 vs 状态机库

| 方案 | 适合 | 不适合 |
| --- | --- | --- |
| **转移表 + 一个 `canTransition`**（本项目） | 规则少、规则会改、要能一眼看懂 | 规则需要按数据动态计算时 |
| `xstate` | 状态多、要画图、要并行状态 | 五个状态的订单流程 |
| 数据库的 `CHECK` + 触发器 | 想在库这一层堵死 | 规则要复杂到触发器写不动时 |

`xstate` 能把状态画成图，这对**给人看**很有用。但订单状态只有五个状态、
七条边，一张表看得完，而看懂的门槛是「一个对象加一个函数」。
`001_init` 里的 `CHECK` 已经把值域交给数据库了，剩下的转移交给代码——
两层各管各的，不重叠。

### 建订单：一次操作改三张表

```bash
curl -X POST http://localhost:3002/api/orders \
  -H "Content-Type: application/json" \
  --data-binary '{"userId":1,"items":[{"productId":1,"quantity":2},{"productId":2,"quantity":3}]}'
```

```
{"id":1,"userId":1,"status":"pending","totalCents":118500,"createdAt":"2026-10-02T15:31:30.974Z","items":[{"productId":1,"quantity":2,"unitPriceCents":39900,"productTitle":"机械键盘"},{"productId":2,"quantity":3,"unitPriceCents":12900,"productTitle":"鼠标"}]}
```

`118500 = 39900×2 + 12900×3`。**全程整数分，没有一处浮点。**

再查一次库，三张表都变了：

```
表：users 1 行，products 2 行，orders 1 行，order_items 2 行

--- products ---
  #1 KB-87 机械键盘 39900分 库存 8
  #2 MS-01 鼠标 12900分 库存 2
--- orders ---
  #1 用户 1 pending 118500分
--- order_items ---
  订单 1 ← 商品 1 × 2
  订单 1 ← 商品 2 × 3
```

甲的库存 10 → 8，乙的 5 → 2，明细两行——**一次请求，三张表**。

### 整体回滚：一次操作三张表都不变

买 99 件只剩 2 件的鼠标（**会改数据**）：

```bash
curl -i -X POST http://localhost:3002/api/orders \
  -H "Content-Type: application/json" \
  --data-binary '{"userId":1,"items":[{"productId":2,"quantity":99}]}'
```

```
HTTP/1.1 409 Conflict
{"error":{"code":"OUT_OF_STOCK","message":"商品 2 库存不足"}}
```

和上面那份对比，**一个字都没变**：

```
表：users 1 行，products 2 行，orders 1 行，order_items 2 行

--- products ---
  #1 KB-87 机械键盘 39900分 库存 8
  #2 MS-01 鼠标 12900分 库存 2
--- orders ---
  #1 用户 1 pending 118500分
--- order_items ---
  订单 1 ← 商品 1 × 2
  订单 1 ← 商品 2 × 3
```

订单没多，明细没多，库存没少。对照第 2 节那个「半套数据」：
那时订单在、明细缺一行；现在要么都不变，要么都变。

::: tip 服务端日志也应该是空的
这一串请求打完，后端终端上除了启动那几行之外**不该有任何输出**。
有 `未处理的异常` 就说明某条错误没被错误中间件接住，
而那正是前面几章一直在消灭的那种失败。
:::

### 状态机：被拒绝的转移不能留下痕迹

`pending → paid → shipped → completed` 走通（**每一步都会改数据**）：

```bash
for to in paid shipped completed; do
  curl -X POST http://localhost:3002/api/orders/1/transition \
    -H "Content-Type: application/json" --data-binary "{\"to\":\"$to\"}"
done
```

```
{"id":1,"userId":1,"status":"paid","totalCents":118500,"items":[...]}
{"id":1,"userId":1,"status":"shipped","totalCents":118500,"items":[...]}
{"id":1,"userId":1,"status":"completed","totalCents":118500,"items":[...]}
```

然后从终态往回走（**不会改数据**）：

```bash
curl -i -X POST http://localhost:3002/api/orders/1/transition \
  -H "Content-Type: application/json" \
  --data-binary '{"to":"paid"}'
```

```
HTTP/1.1 409 Conflict
{"error":{"code":"ORDER_STATE_INVALID","message":"订单现在是 completed，不能变成 paid。现在可以变成：没有（终态）"}}
```

查库确认状态真的没动：

```
--- orders ---
  #1 用户 1 completed 118500分
```

**被拒绝的转移不能留下痕迹。** 错误信息里带着「现在可以变成」，
客户端不用再发一次请求来问。

### 变异测试：确认测试真的在守

改坏一处，跑测试看挂几条：

| 改坏的地方 | 挂掉的用例 |
| --- | --- |
| 去掉 `withConnection` 的排队 | **1 条**：并发请求的写入不会被事务回滚吞掉 |
| 转移表里 `completed` 加上 `paid` | **2 条**：终态没有任何出边 + 转移表和接口表现一致 |
| 转移表里 `pending` 加上 `completed` | **1 条**：非法转移不写库，状态保持原样 |

三次抓到的用例不重叠，说明这三处规则各自被独立守着。

## 10. 哪些是通用的

| 上面出现的东西 | 换个项目要改吗 | 说明 |
| --- | --- | :-: |
| **一次操作涉及的所有写放在一个事务里** | 不改 | **这一篇最值钱的一条** |
| 判断并发条件放进 `UPDATE ... WHERE` | 不改 | 改成先查后写，多进程下就错了 |
| 金额在内存里算完再落库 | 不改 | 落库和计算混在一起时回滚边界不清楚 |
| **价格存快照，不存外键** | 不改 | 改价不能改历史订单 |
| 状态机的值域交给 `CHECK`，转移交给代码 | 不改 | 两件事，数据库只管一件 |
| 非法转移 409，错误信息里带上现在能去哪儿 | 不改 | 少发一次往返 |
| **扣库存失败时前面的扣减也要退回去** | 不改 | 半截订单比没有订单更麻烦 |
| 事务体里不做 IO | 不改 | |
| 连接归属用 `AsyncLocalStorage` | 换库后删掉 | PostgreSQL 的连接池会接管这件事 |
| 嵌套事务直接报错 | 不改 | 加计数器只会让问题更晚暴露 |
| `ROLLBACK` 失败不顶替原始错误 | 不改 | 顶替了客户端就拿 500 |
| 转移表写成 `Record<Status, Status[]>` | 抄形状 | 换状态名 |

**能直接拿走的是右边那些「不改」的。** 表名、字段名、状态名随便换。

## 做到这一步，实际用的是什么

| 你在这一篇做的 | 对应哪一条 |
| --- | --- |
| 三张表的写放进一个事务 | `senior-fullstack-developer:fullstack-dev` **第 3 步：可逆的数据改动** |
| 回滚后查库确认三张表都没变 | 第 3 步的「验证改动真的生效」 |
| 状态机的规则先定成表再写实现 | **第 2 步：先定契约再写实现**——状态机是接口契约的一部分 |
| 变异测试确认三条规则各自被守着 | `superpowers:verification-before-completion` 的反向验证 |
| 工具选型逐条写清「不选它的理由」 | 第 2 步的边界意识：**先知道备选方案是什么** |

**「可逆」在这一篇换了形状。** 前面几章的回退靠 `git revert`——
代码错了改回来就行。这一章开始，**一次提交会同时改三张表的数据**，
回退它意味着要把已经发给客户的订单、已经扣掉的库存一起退回去。
所以这里的「可逆」不是「能 undo」，是「**失败时不留下半套状态**」。

事务做的正是这件事：把「可能留下半套」变成「要么全成、要么全不成」。

## 跑完之后

你现在有三条会同时改多张表的路径，每条都有明确的失败语义：
库存不足是 409，商品不存在是 404，非法转移是 409，
而**任何一条失败，三张表都回到调用前的样子**。

## 下一步

这一章那道门能成立，靠的是一个前提：**一个进程只有一条连接**。
只要这个前提在，事务就天然独占连接，别的请求排队等着。

但有两个东西会让前提消失，而它们都不是「等以后再说」：

**一、多个进程，或者一个连接池。** 池把连接发出去的那一刻，
「独占」就变成了一件要由别人保证的事——不再是进程内部的事实。

**二、SQLite 的单写入模型。** 到现在为止底层一直是 SQLite，
它把并发问题藏了很多章。**藏起来不是解决了，是没碰到。**
换成真正会并发的数据库，那些被藏起来的问题会一次全出来，
而它们在这套代码上跑不出一个失败。
