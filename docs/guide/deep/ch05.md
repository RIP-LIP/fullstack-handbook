# 迁移

> 目标：改表结构时，老库和新库跑同一份代码得到同一个结果；改错了历史会停下来而不是带着一个说不清的库继续跑。全程 45 分钟。

**前置**：[数据模型](/guide/deep/ch04)（四张表和它们的外键）。

上一篇结束时，代码和数据库是「恰好一致」的——你改代码的时候顺手把库也改了。**只要这个「顺手」断了，数据库就开始骗你。**

## 1. 怎么把代码拿到手

```bash
git checkout v1.1
npm install
npm run dev:api
```

**先记下你现在的库长什么样**（只读）：

```bash
node -e "
const {DatabaseSync} = require('node:sqlite');
const d = new DatabaseSync('apps/api/data/app.db');
console.log(JSON.stringify(d.prepare('PRAGMA table_info(products)').all().map(r => r.name)));
d.close();
"
```

```
["id","sku","name","price_cents","stock","created_at","description"]
```

最后那个 `description` 就是 `v1.1` 新加的列。

**接口还看不到它。** `products.ts` 的查询用的是 `SELECT *`，但 `rowToProduct` 只映射了 6 个字段，`description` 被丢掉了。

这是有意的：迁移先把列加上，代码以后再改。**这种「库已经变了、应用还没跟上」的中间态在真实项目里非常常见**——新版本还没全量发布时，老版本代码连着老库结构、新版本代码连着新库结构，两边都得能跑。这一篇讲的就是怎么让这种状态可管理。

`description` 在本项目里没有别的用途，它只是个载体。

## 2. 失败：改了建表语句，老库不变

上一篇的建表语句在 `db/sqlite.ts` 里，启动时跑一遍。你现在想给它加一列 `vendor`（供应商）——最自然的做法是把 `CREATE TABLE` 改掉：

```sql
CREATE TABLE IF NOT EXISTS products (
  id          INTEGER PRIMARY KEY AUTOINCREMENT,
  sku         TEXT    NOT NULL UNIQUE,
  name        TEXT    NOT NULL,
  price_cents INTEGER NOT NULL CHECK (price_cents >= 0),
  stock       INTEGER NOT NULL CHECK (stock >= 0),
  vendor      TEXT,                              -- 新加的
  created_at  TEXT    NOT NULL
)
```

**在你自己的机器上，这行代码是对的**——你跑 `npm run db:reset` 删掉库重启，新库有 `vendor` 列，一切正常。

::: warning `db:reset` 删的是整个开发库
它删 `apps/api/data/app.db` 这个文件，里面手工造的订单和库存一起没了。
脚本会先打印库名要你确认，加 `--yes` 才真删。
:::

在一个已经跑过 v1.0 的库上：

```js
const { DatabaseSync } = require("node:sqlite")
const d = new DatabaseSync("old.db")

// 老库是这么建的
d.exec("CREATE TABLE products (id INTEGER PRIMARY KEY, sku TEXT)")
d.prepare("INSERT INTO products (sku) VALUES (?)").run("OLD-1")
console.log("老库的列：", JSON.stringify(d.prepare("PRAGMA table_info(products)").all().map(r => r.name)))

// 你改完之后的新建表语句
d.exec(`CREATE TABLE IF NOT EXISTS products (
  id          INTEGER PRIMARY KEY,
  sku         TEXT,
  name        TEXT,
  price_cents INTEGER
)`)

console.log("重跑之后：", JSON.stringify(d.prepare("PRAGMA table_info(products)").all().map(r => r.name)))
console.log("表里的行：", JSON.stringify(d.prepare("SELECT * FROM products").all()))
d.close()
```

```
老库的列： ["id","sku"]
重跑之后： ["id","sku"]
表里的行： [{"id":1,"sku":"OLD-1"}]
```

**新加的列没有出现。** 启动不报错，测试不报错，接口不报错。

原因是 `IF NOT EXISTS` 只判断「这张表在不在」。表在，整句就跳过了——它不检查表长什么样。于是：

| 谁 | `products` 表 |
| --- | --- |
| 刚 `db:reset` 的你 | 有 `vendor` |
| 上周就在用的用户 | 没有 |

**同一个 tag，同一份代码，在两种机器上跑出两种结构。** 然后所有人开始遇到一种非常难查的问题：「在我这儿是好的」。

::: danger `IF NOT EXISTS` 什么时候有用，什么时候骗你
建表语句在**启动时**跑，这时候它有用——每次启动都执行一遍，靠它保证表存在。

建表语句在**决定表结构**的时候跑，它骗你——这时候你需要的是「把库改成我要的样子」，不是「表在就行」。

这两件事看起来都是「跑一条建表语句」，用途完全不同。
:::

## 3. 版本表

解决办法是：**让数据库也记一份自己该是什么样。**

`schema_migrations` 表长这样：

```sql
CREATE TABLE IF NOT EXISTS schema_migrations (
  version    INTEGER PRIMARY KEY,
  name       TEXT    NOT NULL,
  checksum   TEXT    NOT NULL,
  applied_at TEXT    NOT NULL
)
```

每改一次结构，就写一个迁移文件，按序号命名，放进 `apps/api/src/db/migrations/`：

```
001_init.ts
002_add_product_description.ts
```

**已提交的迁移文件永远不要改。** 改了就在末尾加一个新文件。

启动时 `db/sqlite.ts` 做这件事：

```ts
await migrate(db)
```

用模块顶层的 `await` 是有意的：模块没加载完，import 它的人就拿不到 `db`，于是「迁移还没跑完就开始收请求」在结构上就不可能发生。迁移失败会让这里直接抛，进程带着非 0 退出，**不会带着一个半成品库对外服务**。

跑完之后的库（只读）：

```bash
node -e "
const {DatabaseSync} = require('node:sqlite');
const d = new DatabaseSync('apps/api/data/app.db');
for (const r of d.prepare('SELECT version, name FROM schema_migrations ORDER BY version').all()) {
  console.log(JSON.stringify(r));
}
d.close();
"
```

```
{"version":1,"name":"init"}
{"version":2,"name":"add_product_description"}
```

## 4. checksum：有人改了历史会怎样

`version` 和 `name` 只能回答「跑过哪些」。真正要防的是另一种情况：**有人回头改了 `001_init.ts`。**

比如他觉得某个列定义写错了，直接改了那个文件。对一个**空库**来说这没问题——它会从头跑一遍新的 001。但对一个已经跑到 002 的库，001 会被跳过，库停在「按旧 001 建出来的结构」上，而代码里写的是新 001。**库和代码永远对不上，而且没有任何地方会告诉你。**

`schema_migrations` 里的 `checksum` 就是防这个的。启动时拿迁移文件的内容算一个指纹，和库里记的比：

```ts
export function checksumOf(migration: Migration): string {
  return createHash('sha256').update(migration.up.toString()).digest('hex')
}
```

**算的是 `up` 函数本身的源码**（`Function.prototype.toString`），不是文件字节。区别很实际：文件里加一行注释不会误报，而真的改了建表语句一定会被抓到。这比按文件哈希算更贴近「这段逻辑有没有变」这个问题本身。

对不上就抛错，进程退出。真实输出：

```
MigrationError: 迁移 001_init 已经应用过，但内容被改过。
  库里的 checksum：e982f89164819e45b6d00a5fb90841f698ba165196d129d56e056e2017f4da72
  现在的 checksum：671c175968cf6b56cec70ec8f2b26837f5abc5a012ed5b40f25818820b00e494

已经执行过的迁移不能改写——数据库此刻的状态只和当时那一版对得上。
要加新改动就写一个新版本的迁移。
```

**不自动重跑，也不自动跳过。** 两种「聪明」的处理都有害：

- 自动重跑 → 在已经按旧版本建好的表上再执行一遍新版本，运气好是错的，运气差是破坏性的。
- 自动跳过 → 你以为迁移跑过了，其实库还是旧的，而且以后每次启动都「正常」。

**停下来让人先想清楚，代价小得多。** 真需要改历史时，正确做法是写一个新迁移，或者干脆重建库。

::: warning `db:reset` 会删掉整个开发库
开发阶段重建库很方便，但它删的是 `apps/api/data/app.db` 这个文件本身。
里面有你手工造的订单和库存，删掉就没了。脚本会先打印库名要你确认，
加 `--yes` 才真删——别把 `--yes` 写进任何你可能会重复执行的脚本里。
:::

::: danger 迁移里的 `CREATE TABLE` 不写 `IF NOT EXISTS`
平时写建表语句习惯带 `IF NOT EXISTS`，迁移里**不要**。

迁移只跑一次，靠的是版本表判断，不是靠 `IF NOT EXISTS` 兜底。再套一层，等于把「这张表本来不该存在」这种情况悄悄咽下去——而那通常意味着版本表被清过、或者库被手工改过，正是最该停下来看一眼的时候。

迁移里让它炸。炸了会回滚，库不会被改坏。
:::

## 5. 每个迁移一个事务

```ts
await db.transaction(async (tx) => {
  await migration.up(tx)
  await tx.query(
    'INSERT INTO schema_migrations (version, name, checksum, applied_at) VALUES (?, ?, ?, ?)',
    [migration.version, migration.name, checksum, new Date().toISOString()],
  )
})
```

**每个迁移各自一个事务，不是整批一个。** 这需要 SQLite 的 DDL 本身是事务性的，实测确认（只读，不改任何数据）：

```js
const { DatabaseSync } = require("node:sqlite")
const d = new DatabaseSync(":memory:")
d.exec("BEGIN")
d.prepare("CREATE TABLE v (id INTEGER PRIMARY KEY)").all()
d.exec("ROLLBACK")
console.log(d.prepare("SELECT COUNT(*) AS n FROM sqlite_master WHERE name = 'v'").get())
d.close()
```

```
[ Object: null prototype ] { n: 0 }
```

回滚之后表没了。所以一个迁移执行到一半失败，**不会留下「建了一半的表」**。

整批套一个大事务当然更省事，但有两个代价：一个失败全白做；大库上长时间持锁。**按迁移粒度切，每个失败只需要重跑一个。**

顺序也重要：版本记录是在 `up()` **成功之后**、**同一个事务里**写的。所以迁移失败时版本表里不会留下那一行，重跑是干净的：

```
ℹ tests 47
ℹ pass 47
ℹ fail 0
```

其中一条用例专门盯这个：

```
✔ 迁移失败不留版本记录，重跑能干净地重来一次
```

### 版本号本身也要守法

版本必须从 1 开始连续递增，不重复、不跳号。跳号说明有人漏提交了一个迁移，按序执行会直接把库带到错误的版本——比如库里有 001 和 003，执行 003 时它以为前面的都做过了。

`migrate()` 会在跑之前先检查这一条，检查不过直接抛。

## 6. `ADD COLUMN` 的两条边界

写一个加列的迁移时最容易踩的一下，实测（**只读，不改任何数据**，都在内存库里）：

```js
const { DatabaseSync } = require("node:sqlite")

// 表里有 1 行
const d = new DatabaseSync(":memory:")
d.exec("CREATE TABLE t (id INTEGER PRIMARY KEY, title TEXT)")
d.prepare("INSERT INTO t (title) VALUES (?)").run("有一条数据")
try {
  d.exec("ALTER TABLE t ADD COLUMN owner TEXT NOT NULL")
  console.log("成功")
} catch (e) {
  console.log("失败 ->", e.message)
}
```

```
失败 -> Cannot add a NOT NULL column with default value NULL
```

**同一句，在空表上成功：**

```js
const e2 = new DatabaseSync(":memory:")
e2.exec("CREATE TABLE t (id INTEGER PRIMARY KEY, title TEXT)")
e2.exec("ALTER TABLE t ADD COLUMN owner TEXT NOT NULL")
console.log("成功")
```

```
成功
```

**带了默认值，有数据的表也成功：**

```js
d.exec("ALTER TABLE t ADD COLUMN owner TEXT NOT NULL DEFAULT ''")
console.log("现有列：", JSON.stringify(d.prepare("PRAGMA table_info(t)").all().map(r => r.name)))
```

```
现有列： ["id","title","owner"]
```

结论：**「能不能加」取决于表里有没有数据，不是语法允不允许。** 这一点在空库上开发时完全看不出来——你本地库是空的，加什么都成功；上线第一天表里有一百万行，同一句直接失败。

给已有数据的表加必填列，标准做法是分三步走：先加一个可空列或带默认值的列，把老数据按规则补齐，再把约束加上。**别指望一条 SQL 干完。**

::: details 中间那步最容易出事
「加列」和「加约束」都是元数据操作，毫秒级。慢的是**给一百万行老数据补默认值**——
一条 `UPDATE` 全表会长时间持锁，而且中途失败没法重来。

所以中间那步必须能中断、能重跑、能看到进度。判据是这三条：

- 每批一个事务，别整批套一个大事务
- 每批带 `WHERE 列 IS NULL`，重跑只会补剩下的
- 每批之后检查「剩余行数」有没有真的降，没降就停下来查

这三条怎么落到一个真脚本上，见 [零停机变更](/guide/deep/ch06)。
:::

## 7. 测试

这一章的机制全靠「停下来让人判断」，所以测试要盯的就是**它有没有真的停**。

```bash
npm test
```

```
ℹ tests 47
ℹ pass 47
ℹ fail 0
```

14 条用例在 `apps/api/test/migrate.test.ts`，盯的是五件事：每个版本各一行、
再跑一次不执行任何迁移、跑三次和跑一次行数一样、checksum 对不上要停、
中途失败不能留下建了一半的表。

### 用改坏代码的方式验证测试有效

测试全绿说明不了什么——**全绿也可能是断言根本没碰到被测的那段逻辑**。
所以把实现改坏一次，看有没有测试真的挂。做完恢复。

| 改坏的地方 | 挂掉的用例 |
| --- | --- |
| `migrate()` 里跳过 checksum 比较（`&& false`） | 2 条：`版本号在、内容不同，抛 MigrationError`、`停下的时候，后面的迁移一个都不会跑` |
| `checksumOf()` 直接返回常量，不算哈希 | 同上 2 条 |

两处改法不同——一处改的是**判断**，一处改的是**被判断的值**——但抓到的用例一样。
这说明它们测的是同一件事：**内容变了要能发现**。

改完恢复，14 条重新全绿。

**先提交再改坏。** `git checkout --` 恢复的是**已提交的版本**，
不是「一个字没动过的当前工作区」。没提交就改坏，恢复回来的是旧代码，
你以为自己恢复了，其实换了个版本。

## 8. 工具选型

迁移是所有后端项目里最容易「本来想手写，最后还是引了库」的地方。先看账。

### 迁移执行器：手写 vs 成熟的库

| 方案 | 它替你做了什么 | 代价在哪儿 |
| --- | --- | --- |
| **手写**（本项目，`migrate.ts` 153 行） | 版本表、顺序执行 | 多数据库要自己适配 |
| `node-pg-migrate` | 版本表、down 迁移、命令行、种子数据 | **只支持 PostgreSQL** |
| `Umzug` | 上面那些，且支持多种驱动 | 抽象层更厚，错误信息离 SQL 更远 |
| `Knex` 的 migrate | 上面那些，还顺带做查询构造 | 引入整个查询层，只为用它的迁移 |
| `Prisma migrate` | 上面那些，且从 schema 生成 | **历史迁移会被自动改写** |

**为什么手写**，有一个具体的技术原因和两个更重要的非技术原因：

1. **前三个是为 PostgreSQL 写的。** 现在底层是 SQLite，
   `node-pg-migrate` 直接不适用；Umzug 支持 SQLite 但它的多方言抽象
   在这里没有第二个方言可服务——为了将来可能的第二个方言先付成本，不划算。
2. **`checksum` 这一节的行为是手写才有的。** 上面四个库**没有一个**检查
   「已执行的迁移有没有被人改过」，它们默认信任你的 git 历史。
   而这一章第 4 节整节讲的正是这件事。
3. **`Prisma migrate` 与这一章的规则直接冲突。** 它为了让 schema 干净，
   会在某些情况下重写历史迁移文件——比如你给一个迁移加了个注释、
   调整了字段顺序。这正是 checksum 要拦的那种改动。

**什么时候该换**——出现下面任意一条：

- 迁移文件超过 30 个，`migrate.ts` 该拆了（拆法和换库无关，见下面「该拆的时候」）
- 同一份代码要跑在两种数据库上（那时 Umzug 的方言抽象才开始值钱）
- 团队里开始有人直接手改 `schema_migrations` 表
- 出现了 down 迁移的真实需求（回滚某一次上线）——手写确实做不了这个

到那时换 `node-pg-migrate` 成本最低，**前提是这时已经在 PostgreSQL 上**。

### checksum：源码指纹 vs 文件哈希

| 算法 | 算的是 | 加一行注释 | 真改了建表语句 |
| --- | --- | --- | --- |
| **源码指纹**（`up.toString()`，本项目） | 迁移函数本身的源码 | 不误报 | 一定报 |
| 文件哈希 | 整个 `.ts` 文件的字节 | **误报** | 报 |
| 迁移文件清单 | 文件名 + 行数 | 误报 | 可能漏报 |

选源码指纹是因为**它回答的是对的问题**：「这段逻辑有没有变」，
而不是「这个文件有没有被碰过」。为了一次无害的格式调整停掉整个服务是假警报，
假警报多了，这条检查就会被加 `--force` 绕过去。

**它的盲区要知道**：指纹只覆盖 `up` 函数本身的源码。如果 `up` 里调用的
另一个 helper 函数被改了，指纹**不会变**，因为 `up.toString()` 里只有那一次调用。
这一章的迁移都直接写 SQL，所以现在没有这个风险；
一旦开始抽公共的 SQL 片段，就必须改成「把依赖也纳入指纹」。

### `migrate.ts` 该拆的时候

153 行还不需要拆。**出现下面任意一条就拆**：

- 迁移文件数超过 30（`allMigrations` 的 import 列表会变成一堵墙）
- 第 1 步和第 3 步各自超过 60 行（校验、执行、记账该分开）
- 出现了「迁移需要读配置」这种需求（说明它想访问库之外的东西，该想想要不要）

拆的时候按**职责**拆（校验 / 执行 / 记账），不要按「每 10 个迁移一个文件」拆——
后者只是把一个文件换成五个文件，逻辑还是混在一起。

## 9. 场景问题

| 场景 | 怎么办 | 为什么 |
| --- | --- | --- |
| **本地开发想推倒重来** | 删库重建 | 开发库没有别人依赖，没有历史包袱。见第 2 节 |
| **生产上有人改了已执行的迁移** | 启动时直接退出，报出库里和现在的 checksum | 两个环境结构不一致时，**继续跑等于在不确定的状态上写数据** |
| **迁移跑到一半崩了** | 每个迁移一个事务，版本记录写在同一个事务里 | 重启后重跑是干净的。整批套大事务虽然省事，但大库上会长时间持锁 |
| **迁移文件里写了 `IF NOT EXISTS`** | 不写，让它炸 | 迁移靠版本表判断跑没跑过。套一层 `IF NOT EXISTS` 会把「这张表本来不该存在」悄悄咽下去 |
| **两个环境的版本号对不上** | 版本表是唯一的真相，不靠文件数量推断 | 文件可能被删、被重命名，版本表里记的是「实际跑过什么」 |
| **加字段时表里已经有几百万行** | 走 expand 流程分批回填，见 [零停机变更](/guide/deep/ch06) | 加列本身很快，慢的是给存量行填值 |

## 10. 哪些是通用的

| 上面出现的东西 | 换个项目要改吗 | 说明 |
| --- | --- | :-: |
| `schema_migrations` 这张表的结构 | 抄结构 | 列名可以变，`version` + 指纹这个组合别拆开 |
| **按序号命名的迁移文件** | 不改 | `001_` `002_` 让人一眼看出执行顺序 |
| **「已执行的迁移不修改」** | 不改 | **这一篇最值钱的一条** |
| **指纹对不上就停下** | 不改 | 换算法（整文件哈希、CRC）都行，别取消这个检查 |
| **每个迁移一个事务** | 不改 | |
| **版本记录写在同一个事务里** | 不改 | 顺序反了就会出现「跑过了但没记录」 |
| **版本连续递增、不跳号** | 不改 | |
| **迁移里不写 `IF NOT EXISTS`** | 不改 | |
| `migrate()` 的调用位置（模块顶层 await） | 抄思路 | 关键性质是「迁移没跑完，服务不会开始收请求」 |
| `MigrationError` 单独一个类型 | 抄思路 | 迁移失败和业务失败要能被分开处理 |
| `ADD COLUMN` 的三条边界 | 不改 | 换数据库也有一模一样的限制 |
| 迁移放在 `migrations/` 目录 | 抄思路 | 换数据库时换的是执行器，不是这个约定 |
| 拿 ORM 代替手写迁移 | 判断题 | 能用，但**要确认它默认不会改历史迁移**——很多 ORM 会为了对直模型直接改写旧迁移 |

**能直接拿走的是右边那些「不改」的。** 表名和文件命名可以换，规则不用。

## 做到这一步，实际用的是什么

| 你在这一篇做的 | 对应哪一条 |
| --- | --- |
| 迁移失败时进程退出，不带着半成品库服务 | `senior-fullstack-developer:fullstack-dev` **第 3 步：可逆的数据改动** |
| 每个迁移一个事务，失败只重跑一个 | 第 3 步的「改动要能退回」 |
| 指纹不匹配就停下，不自动重跑 | 第 3 步的边界：自动化不能替人做判断 |
| 先定好「库该是什么样子」再改代码 | **第 2 步：先定契约再写实现**——表结构也是契约 |
| 改坏代码确认测试会挂 | `superpowers:verification-before-completion` 的反向验证：**写 → 过 → 撤销修复 → 必须失败 → 恢复 → 过** |

**第 3 步的「可逆」在这一篇是最实在的一次落地。** 前面几章改的都是代码，改错了 `git revert` 一下就回来了。这一章开始改的是**已经存在的数据**——回退一个加列容易，回退一次写错了值的批量更新就难了。

所以这里加的那几条约束（一个迁移一个事务、失败不留记录、指纹不对就停），**本质上都是在保证「出错了还能退回去」**，而不是「不出错」。

## 跑完之后

你现在有四张表、两个迁移、一份能拦住改坏代码的测试。表结构可以安全地往前改了。

## 下一步

表结构能改，不等于改起来安全。给一个字段改名、给一个字段换类型，
