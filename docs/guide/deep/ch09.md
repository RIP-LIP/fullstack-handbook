# 幂等

> 目标：同一个请求来了两次，只做一次。全程 80 分钟。

上一篇解决的是「两个**不同**的请求同时改一行」。
这一章解决的是另一个问题：**同一个请求被送进来两次**。

两个请求内容一模一样，数据库看不出它们是一个意图还是两个意图，
于是建两笔订单、扣两次库存。

**这不是极端情况。** 用户网络卡住、连点两下、客户端自动重试、
网关重试超时请求——每一种都会产生两个一模一样的请求。
这不是「万一」，是「必然」。

## 2. 失败：同一个请求发两次

先看清楚要防的是什么。**这一章所有命令都会改数据。**

先造一件商品和一个用户：

```bash
curl -X POST http://localhost:3002/api/products \
  -H "Content-Type: application/json" \
  --data-binary '{"sku":"KB-87","name":"机械键盘","title":"机械键盘","priceCents":39900,"stock":10}'
```

```
{"id":1,"sku":"KB-87","name":"机械键盘","title":"机械键盘","priceCents":39900,"stock":10,"createdAt":"2026-10-02T16:33:10.947Z"}
```

然后**不带**任何幂等标识，把同一个请求发两次：

```bash
curl -X POST http://localhost:3002/api/orders \
  -H "Content-Type: application/json" \
  --data-binary '{"userId":1,"items":[{"productId":1,"quantity":2}]}'

curl -X POST http://localhost:3002/api/orders \
  -H "Content-Type: application/json" \
  --data-binary '{"userId":1,"items":[{"productId":1,"quantity":2}]}'
```

两次都是 201，两笔订单，**库存扣了 4 件而不是 2 件**：

```bash
node scripts/probe.mjs state
```

```
--- products ---
  #1 KB-87 机械键盘 39900分 库存 6
--- orders ---
  #1 用户 1 pending 79800分
  #2 用户 1 pending 79800分
```

::: danger 这里没有任何东西是坏的
每一行代码都是对的。校验过了，事务有了，扣减是原子的。
**两个请求就是两个意图**——服务端没有理由不执行两次。

问题不在「代码写错了」，在「请求的内容不足以判断意图」。
两个一模一样的 HTTP 请求，数据库看不出它们是同一个人按了两次，
还是两个人各买了一件。
:::

## 3. 客户端给一个键

办法很直接：**让客户端为「一次意图」生成一个唯一标识，重发时带上同一个。**
本项目用请求头：

```
Idempotency-Key: 7f3a9c21-...
```

服务端记下「这个键我用过了，对应的是这笔订单」，下次再见到就返回上次那笔。

**这个键是显式的，服务端不自动生成。** 这一点值得强调：
自动生成等于把幂等变成碰运气——客户端重发时服务器算出的是**另一个**键，
于是两次都成功，而你还以为幂等在工作。

## 4. 为什么不是「先查再插」

最直觉的写法是：先 SELECT 看这个键在不在，不在就 INSERT。

```ts
// ❌ 直觉写法
const existing = await db.one('SELECT * FROM idempotency_keys WHERE key = ?', [key])
if (existing !== undefined) return replay(existing)
await db.query('INSERT INTO idempotency_keys (...) VALUES (...)')   // 两个请求会同时走到这
```

**窗口就在那两条语句之间。** 两个并发请求同时查到「不在」，
然后同时 INSERT，第二个撞唯一键。

正确的做法是**反过来：先插，让唯一约束去撞。**

```ts
try {
  await db.query('INSERT INTO idempotency_keys (key, request_hash, order_id, created_at) VALUES (?, ?, NULL, ?)', [key, hash, now])
  return { kind: 'claimed' }          // 抢到了，这个请求是第一次
} catch (err) {
  if (!isConstraint(err, 'unique')) throw err
  // 撞了 = 有人比我先。去看那一行现在是什么状态。
  ...
}
```

唯一约束是**原子的**，所以「有没有人比我先」这个判断没有窗口。

::: tip 一个试过但没抓住的变异
写完这一章后做了一次变异：在 INSERT **之前**加一句「先 SELECT 看在不在」，
只作为快速路径，判据仍然是唯一约束。

**12 条测试全绿，一条都没挂。**

因为那次预查询不参与判据——查到了不等于「归我」，
不查也不影响（撞键之后 catch 里还是会去查那一行）。
它只是一次**多余的查询**，不是错误。

真正的错误做法是**拿那次查询的结果当判据**：
「查不到就直接 INSERT 并当成自己的」。那样两个并发请求
会同时查到「查不到」，然后同时当成自己的，窗口真实存在。

**所以判据在哪儿，比有没有那次查询重要得多。**
:::

## 5. 撞了键之后：四种情况，不是两种

`claim` 撞到唯一键之后要去读那一行，而那一行有几种状态。
把它们混在一起是这一章最容易出错的地方。

| 那一行的状态 | 这意味着 | 返回什么 |
| --- | --- | --- |
| `request_hash` 和这次不一样 | 客户端把两个意图用同一个键发了 | **409 `IDEMPOTENCY_KEY_REUSED`** |
| 指纹一样，`order_id` 有值 | 上一次做完了 | **200**，返回那笔订单 |
| 指纹一样，`order_id` 是空 | 上一次还在跑 | **409 `IDEMPOTENT_REQUEST_IN_PROGRESS`** |
| 读不到这一行 | 刚被清理脚本删了 | 当成「处理中」 |

**第一种不能返回上一次的结果。** 幂等的定义是「同一个意图重发多次」，
不是「不管发什么都返回上次那个」。把两个不同的意图合并成一个，
比不做幂等更糟——客户端会拿到一个和它想要的不一样的订单。

**第三种为什么不等，而是报错。** 等多久是不可控的：
第一个请求跑了 50 秒，这一个就等 50 秒，而客户端的超时可能只有 10 秒。
返回 409 让客户端自己决定什么时候重试，语义清楚得多。

## 6. 同一个键配不同内容

指纹是这么算的：

```ts
export function requestHash(payload: unknown): string {
  return createHash('sha256').update(canonicalize(payload)).digest('hex')
}
```

**为什么要先规范化。** JSON 的键顺序不影响语义，
但直接对原始字符串算哈希的话，键顺序一变哈希就变——
同一份内容会被判成不同，客户端白白收到一个 409。

```ts
// 这两个必须算出同一个指纹
{ userId: 1, items: [{ productId: 2, quantity: 1 }] }
{ items: [{ quantity: 1, productId: 2 }], userId: 1 }
```

**但数组不排序。** `[1, 2]` 和 `[2, 1]` 语义不同，
排序会把两个不同的请求变成同一个键，那比不做校验还糟。

实测（**只读，不改数据**）：

```bash
npx tsx --test --test-timeout=60000 apps/api/test/idempotency.test.ts
```

```
✔ 键顺序不同，内容相同，指纹相同
✔ 内容不同，指纹不同
✔ 数组顺序不同，指纹不同
✔ undefined 不参与指纹（它在 JSON 里不存在）
```

## 7. 失败时要把键还回去

这一节是整章最容易漏的一处，而且漏了不会立刻暴露。

键是先插进去的，然后才干活。**如果干活失败了，这行键还留在库里**，
而它的 `order_id` 是空的。于是下一次重试撞上它，
拿到的是「处理中」——**永远**。

一次失败，把这次意图彻底废了。客户端再怎么重试也拿不到结果，
而日志里那个错误早就过去了，没人知道有个键卡在那儿。

```ts
try {
  const order = await db.transaction(async (tx) => {
    const created = await createOrderInTx(tx, parsed.data)
    await complete(tx, key, created.id)
    return created
  })
  res.status(201).json(order)
} catch (err) {
  await release(db, key)     // ← 少了这一句，这个键就废了
  throw err
}
```

**`DELETE` 上带了 `order_id IS NULL`**：只删「还没完成」的那些。
如果一个键已经完成了（`order_id` 有值）而后面又出了别的问题，
删掉它等于让下一次重放重新执行一遍——那是比不幂等更糟的结果。

### 回填和建订单必须在同一个事务里

上面那个 `db.transaction` 里同时做了建订单和回填键。
为什么不能分开：

分开写的话，中间有一小段时间**订单已经存在、键却还是空的**。
并发的重放撞上这一行，看到 `order_id IS NULL`，
得到「处理中」——**明明已经做完了**，客户端却被告知再等等。

这也是为什么建订单的实现必须能接受一个**已经开好的**事务：

```ts
/** 三张表要改的东西，全部包在调用方给的事务里。 */
async function createOrderInTx(tx: Db, input: CreateOrderInput): Promise<Order> { ... }

/** 自己开一个事务建订单。幂等那层用的是上面那个。 */
function createOrder(input: CreateOrderInput): Promise<Order> {
  return db.transaction((tx) => createOrderInTx(tx, input))
}
```

幂等那层要包一个自己的事务（好让回填和建单原子），
而嵌套事务是本项目明确禁止的（见 `db/errors.ts`）。
所以建订单的逻辑必须拆出一个能复用别人事务的版本。

## 8. 重放返回 200 还是 201

**重放返回 200，不是 201。**

| | 状态码 | 为什么 |
| --- | --- | --- |
| 第一次 | `201 Created` | 真的创建了东西 |
| 重放 | `200 OK` | 第一次已经创建过，这一次没有 |

两种都「成功」，但语义不同。返回 201 等于告诉客户端
「我又给你建了一笔」，而客户端很可能拿两个 id 去对账。

## 9. 为什么存 order_id 而不是整份响应

幂等的经典做法是把**第一次的响应体**存下来，重放时原样返回。
本项目不这么做。

**响应是快照，订单是活数据。** 订单从 `pending` 走到 `paid` 之后，
存下来的响应体还停在 `pending`，重放就会返回一个过期状态。

所以存 `order_id`，每次重放时重新读那条订单。

实测（**会改数据**）：建一笔订单，把它推进到 `paid`，
然后用同一个键重放——

```bash
# 第一次
curl -X POST http://localhost:3002/api/orders \
  -H "Content-Type: application/json" -H "Idempotency-Key: demo-1" \
  --data-binary '{"userId":1,"items":[{"productId":1,"quantity":1}]}'
# -> 201，status 是 pending

# 推进状态
curl -X POST http://localhost:3002/api/orders/1/transition \
  -H "Content-Type: application/json" --data-binary '{"to":"paid"}'
# -> status 变成 paid

# 同一个键重放
curl -X POST http://localhost:3002/api/orders \
  -H "Content-Type: application/json" -H "Idempotency-Key: demo-1" \
  --data-binary '{"userId":1,"items":[{"productId":1,"quantity":1}]}'
# -> 200，status 是 paid，不是当初的 pending
```

**这就是存 order_id 的理由。** 存响应体会返回 `pending`，
而库里明明是 `paid`——那是在骗客户端。

## 10. 工具选型

### 幂等这件事本身有几种做法

| 方案 | 适合 | 不适合 | 什么时候该换 |
| --- | --- | --- | --- |
| **业务唯一键**（订单号由客户端生成） | 一次创建、永远不该重复的业务 | 客户端生成不了稳定唯一值的接口 | 业务上本来就有单号（订单号、工单号），直接拿它当键 |
| **唯一约束 + 记录表**（本项目） | 通用创建类接口 | 同一段逻辑要跨多个接口复用时 | 你的幂等逻辑要在一个中间件里统一处理时 |
| 幂等中间件库 | 想少写重复代码 | 库的行为和你的错误形状不一致时 | 已经在用那个库的生态里 |
| Redis `SETNX` | 多实例、要跨库共享 | 需要和数据库事务原子地绑在一起时 | —— |

**为什么不用 Redis**：本机没有 Redis，载体给不了验证条件，
写了就是名词堆砌。而更根本的原因是**它和数据库不在一个事务里**——
`SETNX` 成功之后建单失败，那个键就废了；要「一起回滚」就得两阶段提交，
那比这一章讲的东西复杂得多。

**为什么不用业务唯一键**：订单号是业务概念，
而「用户点了两次提交」不是业务问题，是传输问题。
让客户端为了幂等去生成一个业务单号，是把传输层的事漏到业务层。

### 幂等和并发是两件事，别混

| | 现象 | 机制 |
| --- | --- | --- |
| **并发**（上一篇） | 两个**不同**的请求同时改一行 | 锁、隔离级别、`UPDATE ... WHERE` 的原子判断 |
| **重复**（这一章） | 同一个请求来了两次 | 唯一约束 |

两者可能同时发生：一个请求被网关重试成两个，两个又恰好撞在一起。
所以这一章的并发测试断言的是「**两个请求只建一笔**」，
而不是「第二个返回什么」——后者可以是 200 也可以是 409，两种都对。

## 11. 场景问题

| 场景 | 怎么办 | 为什么 |
| --- | --- | --- |
| **客户端没传键** | 当普通请求处理，不报错 | 自动生成一个键等于把幂等变成碰运气：重发时服务器算出另一个键 |
| **键传了空串** | 同上，当没传 | 空串不是合法键，当成没传比当成「所有人都用同一个键」安全 |
| **同一个键，不同内容** | 409 `IDEMPOTENCY_KEY_REUSED` | 那不是重发，那是两个意图。合并它们比不做幂等更糟 |
| **第一个请求还在跑** | 409 `IDEMPOTENT_REQUEST_IN_PROGRESS` | 等多久不可控。返回 409 让客户端自己决定何时重试 |
| **键存多久** | 比**最长重试窗口**长。本项目给不出真实窗口，所以只给判据 | 给不出数字就不写数字。判据是：客户端会重试多久，就留多久 |
| **谁负责清理** | 一个定时任务删 `created_at` 早于窗口的键 | 忘了清理的话表会一直涨，而没人会注意到 |
| **清理会不会删错** | 只删「还没完成」的那些（`order_id IS NULL`） | 删掉一个已完成的键等于让下一次重放重新执行一遍 |
| **谁来保证只有一个请求在处理** | 没有登录态，只能全局唯一 | 拿到登录态之后，唯一键应该建成 `(user_id, key)` |

::: warning 唯一键只有 key，没有 user_id
这一组**还没有登录态**，拿不到「这个请求属于谁」，所以唯一性只能落在 key 本身。

代价是明确的：**任何人拿着别人的键重放，都能拿到别人的订单。**

真正的做法是把唯一键建成 `(user_id, key)`——
而那要等有了登录态之后才谈得上。这不是「以后再说」，
是一个**现在就存在的漏洞**，只是它被「没有登录态」这个前提限制着。
:::

## 13. 哪些是通用的

| 上面出现的东西 | 换个项目要改吗 | 说明 |
| --- | --- | :-: |
| **让唯一约束当判据，不让应用层判断当判据** | 不改 | **这一篇最值钱的一条**。约束是原子的，「先查再插」的窗口不是 |
| 同一个键配不同内容要报错 | 不改 | 幂等是「同一个意图重发」，不是「不管发什么都返回上次那个」 |
| 失败时把键还回去 | 不改 | 漏了不会立刻暴露，而且一次失败就废掉一次意图 |
| 还键时只删「还没完成」的 | 不改 | 删掉已完成的键等于让重放重新执行一遍 |
| 回填和干活在同一个事务里 | 不改 | 分开写会出现「明明做完了却说在处理中」 |
| 重放返回 200，第一次返回 201 | 不改 | 两种都成功，但语义不同 |
| 存 order_id 而不是响应快照 | 不改 | 快照会过期，订单不会 |
| 指纹先规范化，但数组不排序 | 抄思路 | 键顺序不影响语义，数组顺序影响 |
| 不带键就是普通请求 | 不改 | 幂等必须是显式的 |
| 幂等键表放在业务库还是 Redis | 判断题 | **要和数据库在同一个事务里**，否则建单失败时键废了 |
| `AsyncLocalStorage` 认领连接 | 抄思路 | 上一篇的，这一章直接用了 |
| 建订单拆成能接受已有事务的版本 | 判断题 | 需要在外层再包一层事务时（幂等、批量）就拆 |

**能直接拿走的是右边那些「不改」的。**
键的格式、清理任务的周期、幂等存多久，都按自己的业务定。

## 做到这一步，实际用的是什么

| 你在这一篇做的 | 对应哪一条 |
| --- | --- |
| 先列出「这个请求可能以哪几种状态重复到达」，再写代码 | `senior-fullstack-developer:fullstack-dev` **第 2 步：先定契约再写实现**——状态机是接口契约的一部分 |
| 把「撞键之后」拆成四种情况而不是两种 | 同上。四种情况就是四条规则，少写一条就有一条路径没人管 |
| 失败时还键，不留半截状态 | 第 3 步的「可逆的数据改动」：**幂等键也是数据**，失败的请求不能留下它 |
| 变更的内容往外挪（响应体 → order_id） | 第 2 步的「哪份数据是权威的」：订单是活数据，响应是它的快照 |
| 三次变异测试 | `superpowers:verification-before-completion` 的反向验证 |
| 记下那个**没挂**的变异 | 同上的另一面：**说「它是对的」也要有证据**。试过、全绿、写下为什么没坏——这是结论的另一半 |

**这一章的「可逆」又换了一个形状。**
前面是代码（`git revert` 回来）、数据（迁移能退回去）、
状态（事务要么全成要么全不成）。
这一章是**一次失败请求留下的痕迹**——
它不是错的数据，而是一行**永远不会被清掉、也不会自己好起来**的记录。

一次 `OUT_OF_STOCK` 之后，那个幂等键就废了。
客户端重试多少次都是「处理中」。
**它不影响任何一条业务数据，所以没有任何数据对账能发现它。**

所以这里的「可逆」不是「能 undo」，是「**失败时不留下半截状态**」——
和事务那一章、和 expand-contract 那一章，是同一条原则的第三次出现。

## 跑完之后

你手上有四个真实跑出来的失败：**两个请求建两笔订单**、
**同一个键配不同内容被合并**、**失败之后键被废掉**、
**并发重发建了两笔**。

前两个是「这一章要防的」，后两个是「这一章自己会犯的」。

还差两件事，都是**这一组刻意没做的**：

**一、幂等键的清理。** 表会一直涨，而没人会注意到。
`created_at` 上那个索引就是给清理任务用的，但这个项目里没有那个任务。
判据在上面给了，周期得按自己的重试窗口定。

**二、这个接口现在对所有人开放。** 建订单、查订单、改订单状态，
**没有任何身份检查**。这不只是幂等的问题——它是这一整组的前提：
从 ch04 到这一章，四张表、一个订单状态机、一套并发正确性，
全都没有「这个操作是谁做的」这一层。

而状态机之所以只能管值域和转移、不能管「谁有资格走这条转移」，
原因就在这里。补上那一层，这一组才算走完。
