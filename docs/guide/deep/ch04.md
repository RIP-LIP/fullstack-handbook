# 数据模型

> 目标：四张表能互相引用，商品接口能用，金额不丢精度，约束冲突不再伪装成服务端故障。全程 60 分钟。

上一篇只有一个 `tasks` 表。现在换成订单/库存的四个：用户、商品、订单、订单明细。**这一篇的难点不是建表，是建完之后撞上第一个跨表的约束冲突。**

## 1. 怎么把代码拿到手

```bash
git checkout v1.0
npm install
npm run dev:api
```

确认后端起来了（只读）：

```bash
curl -i http://localhost:3002/api/health
```

```
HTTP/1.1 200 OK

{"ok":true,"service":"api"}
```

## 2. 先看要得到什么

| 方法 | 路径 | 作用 | 成功返回 | 可能失败时 |
| --- | --- | --- | --- | --- |
| GET | `/api/products` | 列出所有商品 | `200` | |
| GET | `/api/products/:id` | 单个商品 | `200` | `400` id 不是正整数<br>`404` 商品不存在 |
| POST | `/api/products` | 新建 | `201` | `400` 字段校验不过<br>`409` SKU 已存在 |
| DELETE | `/api/products/:id` | 删掉 | `204` | `400` id 不是正整数<br>`404` 商品不存在<br>`409` 已被订单引用 |

失败码不是凑数的，每一个都是一句业务判断，客户端据此决定**该提示用户、该重试、还是该当服务端挂了**：

| 码 | 客户端该怎么做 |
| --- | --- |
| `400` | 我自己写错了，改参数 |
| `404` | 东西不存在，可能已经被人删了 |
| `409` | 请求没错，但**当前状态不接受**——SKU 撞了、商品被引用着 |
| `500` | 服务端出问题了，看日志 |

`500` 出现就说明翻译层漏了东西，这一篇的后半段全在讲怎么不出现 `500`。

端口是 3002，主线的任务清单占 3001，两个服务可以同时开着。

## 3. 四张表，和一个外键

建表语句在 `apps/api/src/db/migrations/001_init.ts`（v1.0 时它还在 `sqlite.ts` 里，讲迁移那篇会搬过去）。四张表之间是这么连的：

```
users ──┐
        ├──< orders ──< order_items >── products
        │                                      ↑
        └──────────────────────────────────────┘
```

真正的关系只有一条：`order_items.product_id` 指向 `products.id`。**它就是这一篇的全部主题。** 另外三条外键（`orders.user_id`、`order_items.order_id`、`order_items.product_id`）先建着，但只有这一条会在「删商品」时被触发。

```sql
CREATE TABLE order_items (
  id               INTEGER PRIMARY KEY AUTOINCREMENT,
  order_id         INTEGER NOT NULL REFERENCES orders(id),
  product_id       INTEGER NOT NULL REFERENCES products(id),
  quantity         INTEGER NOT NULL CHECK (quantity > 0),
  unit_price_cents INTEGER NOT NULL
)
```

**`unit_price_cents` 存的是下单那一刻的价格副本，不去 join `products.price_cents` 取现价。** 这一点是刻意定的：商品改价之后，历史订单里显示的必须是当时的价格，否则一张半年前的订单会跟着今天的调价一起变。

金额一律整数分这件事不是风格问题，下一节有实跑。

## 4. 金额为什么存分

在浏览器控制台或者任意一个 Node 窗口里跑这几句（**只读，不改任何数据**）：

```js
0.1 + 0.2          // 0.30000000000000004
8.2 * 3            // 24.599999999999998
4.35 * 100         // 434.99999999999994
```

第二行是购物车会做的事：按单价乘数量算总价。第三行是「元换分」这一步本身——**你以为存了分就没事了，可从元换到分这一步就已经偏了**。数据库里存的是 434.99999999999994，不是 435。

换成整数分，同样的两笔账：

```js
82 * 3             // 246
1000 + 2000        // 3000
```

整数运算是精确的，一个二进制位都不会偏。

所以本项目的规矩是：**接口收的、数据库存的、返回的，全程都是整数分。** `priceCents` 这个名字里带着单位，就是为了让「这里能不能用小数」在读代码时就有答案。全程没有出现过浮点数，就不存在「四舍五入在哪一步做」这个问题。

::: warning 有一组数是**不会**错的
本机实跑确认过：`0.999 + 1.5 + 0.501`、`19.99 * 3`、`9.99 + 0.01`、`29.9 + 10.1`、`1234.56 + 0.44` —— 结果都精确。

写教程或者写报告时最容易出的错，就是「随手挑几个数」来说明浮点有问题。挑到不会错的那组，整段话就废了。**要举例就现跑一遍。**
:::

## 5. 一个只有三个方法的数据访问层

`apps/api/src/db/index.ts` 里只有一个接口：

```ts
export interface Db {
  query<T>(sql: string, params?: readonly Param[]): Promise<T[]>
  one<T>(sql: string, params?: readonly Param[]): Promise<T | undefined>
  transaction<T>(fn: (tx: Db) => Promise<T>): Promise<T>
}
```

**三个方法，就这些。** 没有 `ProductRepository`，没有 `OrderRepository`。

理由是它只为一件具体的事存在：将来换成 PostgreSQL 时，只改 `db/sqlite.ts` 一个文件。如果这一层长出了按实体分的仓库类，它就变成了另一个东西——每个项目都要重新设计一次、重新调试一次的抽象层，收益抵不上成本。等到真的出现第二种数据访问需求时再加，那时才知道该长什么样。

**三个方法全部返回 Promise，尽管 `node:sqlite` 是同步的。** 换 PostgreSQL 之后底层一定要异步（网络往返），而那时业务代码已经全写好了。现在同步、将来改异步，要动每一个 `await` 链。

::: danger 这不等于并发安全
当前是**单进程单连接**，SQLite 的写入天然串行。`async` 只是给将来预留的接口形状，**不是并发方案**。真要同时处理多个写请求，那是换 PostgreSQL 之后才处理的事。
:::

### 连接初始化

`db/sqlite.ts` 里两行 pragma，顺序有讲究：

```ts
raw.exec('PRAGMA journal_mode = WAL')
raw.exec('PRAGMA foreign_keys = ON')
```

第二行看着像多余。**它不是。** 但理由不是你想的那个：

> `node:sqlite` 的外键**默认就是开的**。实测 `PRAGMA foreign_keys` 返回 `{"foreign_keys":1}`，`@types/node` 的类型声明里也标着 `@default true`。

那为什么还要显式写？三条：

1. **PRAGMA 按连接生效，不写进数据库文件。** 换一条连接就是另一个值。
2. **在事务里设置会静默失效。** 不报错，值就是没变。所以它必须写在任何事务之外——放模块顶层，不是放在迁移里。
3. **换客户端默认值不保证相同。** `sqlite3` 命令行、容器里的工具、别的迁移脚本，各有各的默认。代码里写死，行为就不依赖「谁在连」。

写「SQLite 默认关外键」是错的，会把读者引去查一个不存在的问题。

## 6. 失败：删一个已经被订单引用的商品

这是这一篇真正要解决的事。

先造出「这个商品已经卖出去过」的状态。三条命令都要写库（**都会改动数据**）：

```bash
# 建一个商品
curl -X POST http://localhost:3002/api/products \
  -H "Content-Type: application/json" \
  --data-binary '{"sku":"KB-87","name":"机械键盘","priceCents":39900,"stock":25}'
```

```
HTTP/1.1 201 Created
Content-Type: application/json; charset=utf-8

{"id":1,"sku":"KB-87","name":"机械键盘","priceCents":39900,"stock":25,"createdAt":"2026-10-02T12:39:52.234Z"}
```

::: warning PowerShell 里别用 `-d`
PowerShell 5.1 的 `curl.exe -d '{"k":"v"}'` 会把双引号吃掉，发出去的是 `{k:v}`，后端收到的是坏 JSON。

用 `--data-binary`，把 JSON 写进文件再发：

```bash
# 写文件（PowerShell）
'{"sku":"KB-87","name":"机械键盘","priceCents":39900,"stock":25}' |
  Out-File -Encoding ascii body.json

curl -X POST http://localhost:3002/api/products \
  -H "Content-Type: application/json" \
  --data-binary "@body.json"
```

`Out-File -Encoding ascii` 是为了不带 BOM。用 `utf8` 会写出一个 BOM 开头，JSON 解析器会在第一个字符上就失败。
:::

用户和订单不是接口建的（写订单要用到事务，那篇才做），这里直接往库里插（**改动数据**）：

```bash
node -e "
const {DatabaseSync} = require('node:sqlite');
const d = new DatabaseSync('apps/api/data/app.db');
const now = new Date().toISOString();
const u = d.prepare('INSERT INTO users (email,created_at) VALUES (?,?) RETURNING id').get('zhang@example.com', now);
const o = d.prepare('INSERT INTO orders (user_id,status,total_cents,created_at) VALUES (?,?,?,?) RETURNING id').get(u.id,'paid',39900,now);
d.prepare('INSERT INTO order_items (order_id,product_id,quantity,unit_price_cents) VALUES (?,?,?,?)').run(o.id,1,1,39900);
console.log('order '+o.id+' 引用了 product 1');
d.close();
"
```

```
order 1 引用了 product 1
```

现在删这个商品（**不可恢复**）：

::: request
```bash
curl -X DELETE http://localhost:3002/api/products/1
```

```http
HTTP/1.1 409 Conflict
Content-Type: application/json; charset=utf-8

{"error":{"code":"PRODUCT_IN_USE","message":"商品 1 已经被订单引用，删不掉"}}
```
:::

## 7. 这个 409 是怎么来的

上面是改完的样子。**改之前**它是这样的——把 `routes/products.ts` 里 `DELETE` 处理器的这两行删掉：

```ts
if (isConstraint(err, 'foreignkey')) {
  throw new HttpError(409, 'PRODUCT_IN_USE', `商品 ${id} 已经被订单引用，删不掉`)
}
```

同样的删除命令，真实输出：

::: request
```bash
curl -X DELETE http://localhost:3002/api/products/1
```

```http
HTTP/1.1 500 Internal Server Error
Content-Type: application/json; charset=utf-8

{"error":{"code":"INTERNAL_ERROR","message":"服务端出错了，请看服务端日志"}}
```
:::

客户端看到的是「服务端出错了」。服务端确实没出错——代码是对的，库是好的，**是这个业务规则不让删**。

真相在服务端日志里：

```
  code: 'ERR_SQLITE_ERROR',
  errcode: 787,
  errstr: 'constraint failed'
```

对照着看，问题的全貌是这样的：

| | 改之前 | 改之后 |
| --- | --- | --- |
| 状态码 | `500` | `409` |
| 客户端的判断 | 「服务挂了，重试」 | 「这个商品删不掉，提示用户」 |
| 真正的信息在哪 | 服务端日志 | 响应体 |
| 谁来读这条信息 | 写代码的人 | 调用方 |

`errcode 787` 是 SQLite 的扩展结果码，专指外键约束。`errors.ts` 里的 `constraintKind()` 把它取出来：

```ts
const SQLITE_CONSTRAINT = 19
if ((e.errcode & 0xff) !== SQLITE_CONSTRAINT) return null

switch (e.errcode) {
  case 787: return 'foreignkey'
  case 2067: return 'unique'
  case 275: return 'check'
  // ...
}
```

**低 8 位是主码，高位才是具体是哪一条约束。** 判错的后果分两向，都很贵：

- **漏判**（当成不是约束错误）→ 掉进 500 兜底，就是上面那个样子。
- **误判**（把普通 SQL 错误也当成约束冲突）→ 返回 400，客户端以为是自己请求写错了，换个参数重试同一个错误，真实故障被盖住。

### 还有第三种：自己抛的错被自己吃掉

`DELETE` 处理器里除了翻译约束，还有一行看起来多余：

```ts
try {
  const rows = await db.query<{ id: number }>('DELETE FROM products WHERE id = ? RETURNING id', [id])
  if (rows.length === 0) throw new HttpError(404, 'PRODUCT_NOT_FOUND', `商品 ${id} 不存在`)
  res.status(204).end()
} catch (err) {
  // 注意这里的顺序：HttpError 是我们自己抛的，不该被当成数据库错误再翻译一次。
  if (err instanceof HttpError) throw err
  if (isConstraint(err, 'foreignkey')) {
    throw new HttpError(409, 'PRODUCT_IN_USE', `商品 ${id} 已经被订单引用，删不掉`)
  }
  throw err
}
```

问题在于 `throw new HttpError(404, ...)` **就在这个 `try` 里面**。没有第一行那句 `if (err instanceof HttpError) throw err`，404 会掉进 `catch`，被当成数据库错误再走一遍翻译：

- 404 的 `code` 是 `PRODUCT_NOT_FOUND`，不带 `errcode` 字段，`isConstraint` 返回 `null`
- 于是走到最后那行 `throw err`——**还是抛出去了，但白绕一圈**
- 更糟的改法是：把 catch 写成「不是约束就归一成 400」，那 404 就会被改写成 400

**客户端拿 404 去判断「东西不存在」，拿到 400 会去判断「我请求写错了」，两者不是一回事。** 而一个本该是 404 的响应变成 400，比直接挂掉更难查。

`catch` 里先 `re-throw` 自己的错误，是这类「翻译层」的标准写法：**翻译器只处理它认识的东西，不认识的一律原样放行。**

### 路由里的 `throw` 是怎么到错误中间件的

上面所有 `throw new HttpError(...)` 都写在 `async` 路由里。而 `routes/async-handler.ts` 那个六行包装，就是为这件事存在的。

**Express 4 不会等 async 函数返回的 Promise。** 一个 `async (req, res) => { throw ... }` 抛出的错，会变成一次 **unhandled rejection**——没人接，错误中间件一次都收不到。

**这一步实测过，而且结果比「请求挂住」严重。** 把 `GET /api/products/:id` 的 `asyncHandler(...)` 拆掉，其余一律不动，起服务：

正常时，同一个 URL：

```bash
curl -i --max-time 5 http://localhost:3002/api/products/1.5
```

```
HTTP/1.1 400 Bad Request

{"error":{"code":"INVALID_PARAM","message":"id 必须是正整数"}}
```

22 毫秒返回，服务继续跑。

拆掉包装之后，同样一条命令（**改动只有 `asyncHandler` 那一层**）：

```
HTTP 000  耗时 0.031s
```

`000` 是 curl 的说法：**连接被关掉了，一个字节都没收到。** 随后 `curl /api/health` 也是 `000`，Node 进程已经不在了：

```
HttpError: id 必须是正整数
    at parseId (apps/api/src/routes/products.ts:54:11)
    at <anonymous> (apps/api/src/routes/products.ts:73:16)
  status: 400,
  code: 'INVALID_PARAM',
  fields: undefined
}

Node.js v24.16.0
```

（栈里的路径是本机绝对路径，这里缩成了仓库相对路径。）

**这不是「这个请求挂了」，是「整个服务没了」。** Node 15 之后 unhandled rejection 默认让进程退出，不是一个请求失败，是**当时在处理的所有请求一起死**。

::: danger 为什么这条特别值得单拎出来
一个 `throw` 写错位置，后果是**整个服务被一条非法参数请求打死**。而且它不会在测试里出现——测试是顺序发的，进程死了测试自然全红，你看不出「是谁打死的」。

而我们这一层的 `db.query` / `db.one` 全是 `async`（见第 5 节），等于**每一个路由都踩在这个坑上**。这不是「可能出错」，是「不包就一定错」。

六行代码换掉一整类事故，很划算：

```ts
export function asyncHandler(fn: (req, res, next) => Promise<void>) {
  return (req, res, next) => {
    fn(req, res, next).catch(next)
  }
}
```

`catch(next)` 把 reject 变成 `next(err)`，`next(err)` 才会进入 Express 的错误处理流程。

Express 5 会自己处理这件事。升版本是另一回事（要过一遍中间件兼容性），这里用六行解决，成本更低也更可控。
:::

### 别的约束也要分

「约束冲突」不是一种错误，是一族。每一族翻译出来的业务含义完全不同：

::: request
```bash
curl -X POST http://localhost:3002/api/products \
  -H "Content-Type: application/json" \
  --data-binary '{"sku":"KB-87","name":"机械键盘","priceCents":39900,"stock":25}'
```

```http
HTTP/1.1 409 Conflict
Content-Type: application/json; charset=utf-8

{"error":{"code":"PRODUCT_SKU_TAKEN","message":"SKU KB-87 已经存在"}}
```
:::

同一个 `409`，说的是「这个货号已经登记过了，换一个」。客户端的处理方式完全不同，所以 `code` 必须分开。

而校验不通过是另一回事，那是客户端自己的问题：

::: request
```bash
curl -X POST http://localhost:3002/api/products \
  -H "Content-Type: application/json" \
  --data-binary '{"sku":"BAD-PRICE","name":"带小数的价","priceCents":19.99,"stock":1}'
```

```http
HTTP/1.1 400 Bad Request
Content-Type: application/json; charset=utf-8

{"error":{"code":"VALIDATION_FAILED","message":"输入不符合要求","fields":{"priceCents":"价格必须是以分计的整数，不能是小数"}}}
```
:::

注意 `fields` 逐字段列出来。客户端可以把它直接标在对应的输入框下面，不用自己猜是哪个字段错了。

::: details 一个容易漏的细节：缺字段的消息
`zod` 有两套消息：`min` / `max` 管「给了但不合法」，`required_error` 管「这个键根本没给」。

只写前者的话，缺 `name` 的请求会返回 zod 默认的英文 `'Required'`，混在一堆中文提示里：

```json
{ "error": { "fields": { "name": "Required" } } }
```

每一种失败都该有自己的消息。见 `packages/shared/src/index.ts`。
:::

### 参数不合法也是 400，不是 404

::: request
```bash
curl -i http://localhost:3002/api/products/abc
```

```http
HTTP/1.1 400 Bad Request
Content-Type: application/json; charset=utf-8

{"error":{"code":"INVALID_PARAM","message":"id 必须是正整数"}}
```
:::

`/api/products/1.5` 也是同样的 400。写成 404 是个常见的偷懒——查不到就回 404，省事。但那会让客户端以为「这个商品不存在」，于是换个 id 再试，而真正的问题是请求本身就不合法。

`Number('1e3')` 是 1000，`Number(' 1 ')` 是 1，这些都会被悄悄接受。所以 `parseId` 用正则而不是 `Number()`：

```ts
if (raw === undefined || !/^[1-9]\d*$/.test(raw)) {
  throw new HttpError(400, 'INVALID_PARAM', 'id 必须是正整数')
}
```

不存在的 id 才是 404：

::: request
```bash
curl -i http://localhost:3002/api/products/999999
```

```http
HTTP/1.1 404 Not Found
Content-Type: application/json; charset=utf-8

{"error":{"code":"PRODUCT_NOT_FOUND","message":"商品 999999 不存在"}}
```
:::

## 8. 第二层：关掉外键会怎样

上面那个 409 是「数据库拦住了，接口翻译了」。反面是「数据库没拦住」。

有人会为了「让删除成功」去把外键关掉。这在 `node:sqlite` 里是支持的：

```ts
const db = new DatabaseSync(path, { enableForeignKeyConstraints: false })
```

这么建出来的库，外键约束**不生效**。同样的操作再来一次（**改动数据**）：

```js
const { DatabaseSync } = require('node:sqlite')
const d = new DatabaseSync('apps/api/data/nofk.db', { enableForeignKeyConstraints: false })

d.exec(`CREATE TABLE products (id INTEGER PRIMARY KEY, name TEXT);
        CREATE TABLE order_items (id INTEGER PRIMARY KEY, product_id INTEGER REFERENCES products(id))`)

d.prepare('INSERT INTO products VALUES (1, ?)').run('已下架的键盘')
d.prepare('INSERT INTO order_items VALUES (1, 1)').run()

d.prepare('DELETE FROM products WHERE id = 1').run()      // 这次没报错
console.log('foreign_keys =', JSON.stringify(d.prepare('PRAGMA foreign_keys').get()))
console.log('剩下的明细 =', JSON.stringify(d.prepare('SELECT COUNT(*) AS n FROM order_items').get()))
d.close()
```

```
foreign_keys = {"foreign_keys":0}
剩下的明细 = {"n":1}
```

删成功了。**订单明细还指着那个已经不存在的商品。** 没有报错、没有日志、没有任何地方告诉你出事了——这就是孤儿行。

在正常连接上（外键开着）查一遍，能发现它们：

```sql
SELECT oi.id, oi.product_id
  FROM order_items oi
  LEFT JOIN products p ON p.id = oi.product_id
 WHERE p.id IS NULL
```

`LEFT JOIN` 加 `WHERE p.id IS NULL` 是找孤儿行的标准写法。建了唯一索引的话，也可以直接试插一条重复的，看会不会被拒——**拒绝比查询可靠**，因为查询要求你记得去查。

::: danger 孤儿行是最贵的一种错
它不报错，所以没人会发现。等到有人发现的时候，报表已经错了几个月，回溯的时候你分不清哪一行是什么时候坏的、当时的数据是不是本来就该那样。

**约束在的时候它是负担，不在的时候它是唯一的防线。** 那个 409 麻烦吗？麻烦。但它把「这个商品删不掉」这件事从服务端日志里搬到了调用方面前。
:::

### 确认测试真的在跑

`package.json` 里的 `test` 是显式列出文件名的：

## 10. 哪些是通用的

订单和库存是编的载体。这一节切一下哪些要重写、哪些可以直接搬走。

| 上面出现的东西 | 换个项目要改吗 | 说明 |
| --- | --- | :-: |
| `products` / `orders` 这几张表 | 改 | 换成你自己的实体。这是最不值钱也最容易改的部分 |
| `order_items` 这张「关系表」 | 抄结构 | 任何多对多的关系都长这样，只是名字不同 |
| **`REFERENCES` 声明外键** | 不改 | 关系型数据库都这么写 |
| **`unit_price_cents` 存下单时快照** | 不改 | **凡是金额都可能变的字段，历史记录里都要存副本** |
| **金额用 `INTEGER` 存最小单位** | 不改 | 人民币分、日元円、美分，都是整数 |
| **`PRAGMA foreign_keys = ON` 显式打开** | 抄思路 | 换库之后不用了（PostgreSQL 永远强制外键），但「显式声明而不是依赖默认」这个习惯留下 |
| **约束冲突翻译成接口语义码** | 不改 | **这一篇最值钱的一条** |
| **`409` 用来表示「状态冲突」** | 不改 | 和 `400`（你写错了）、`404`（没有这个东西）是三件事 |
| **`400` 用于「id 不是正整数」** | 不改 | 参数不合法就是 400，不因为查不到就变 404 |
| **响应体里不漏数据库内部错误文本** | 不改 | 内部实现不是接口契约 |
| **`zod` 校验放在 `packages/shared`** | 不改 | 沿用主线的做法 |
| **数据层只有三个方法** | 抄思路 | 数量可以不同，**「只为换库而存在」这个理由要留着** |
| **四个接口的 `GET`/`POST`/`DELETE`** | 不改 | 增删改查永远是这几个 |
| **`DELETE` 返回 204 无响应体** | 不改 | |
| **`REAL` 存金额会丢精度** | 不改 | |

**能直接拿走的是右边那些「不改」的。** 表名和路径是每秒钟都要重写的东西，规则不是。

换个完全不同的领域——比如记账、拼单、课程选课——你会发现 `orders` 换成了 `enrollments`，`products` 换成了 `courses`，`quantity` 换成了 `credits`，**剩下的全部一样**。

## 做到这一步，实际用的是什么

这一篇做的事，对应到真实的工程 skill 上是这几条：

| 你在这一篇做的 | 对应哪一条 |
| --- | --- |
| 先把四个接口的形状和错误码定下来，再写实现 | `senior-fullstack-developer:fullstack-dev` **第 2 步：先定契约再写实现** |
| 决定金额权威在 `price_cents`、历史订单存快照 | 第 2 步的「**哪份数据是权威的，哪一层拥有哪个状态**」 |
| 把 787 翻译成 `PRODUCT_IN_USE` | 第 2 步的错误契约——**一个失败模式一个语义码** |
| 数据层只做到「够换库」为止 | 第 2 步的边界意识，第 3 步的「可逆的数据改动」 |

**「哪份数据是权威的」这一条在教程里只体现为一句话，但它是这一篇最值钱的部分。** 你可以现在把它换掉试：把 `unit_price_cents` 去掉，改成查订单时去 join `products` 取现价。功能能跑，测试也全绿——直到某天你给一个商品改了价，然后发现半年前的订单金额跟着变了。那时候要回溯的不只是数据，还有所有依赖「价格会变」这个假设的逻辑。

那一条为什么值钱？因为它是**你改了需求也不会被打破**的决定。表结构改错了能加列改回来，写错了权威归属，要回溯的是历史数据。

## 跑完之后

你现在有四张带外键的表、一个能正确处理约束冲突的接口、以及一份能抓住问题的测试。

还差一件很基础的事：**表结构还没法改。** 现在你往 `CREATE TABLE` 里加一列，本地库会变，老用户的库不会变——`IF NOT EXISTS` 看到表在，整句就跳过了。同一个版本号，两种结构。
