# 换 PostgreSQL

> 目标：把底下的数据库换掉，而 `routes/` 里的每一行调用都不用改。全程 90 分钟。

前面四章解决的都是「应用里的事」：表怎么建、结构怎么迁、字段怎么换、事务怎么划。
这一章第一次动**底下那一层**。

**它的核心不是「连接字符串换了」。** 连接字符串是最简单的部分，两分钟就完。
难的是三件不显眼的事：占位符的写法、数据库报错的编号、迁移里的建表语句。
还有两件更隐蔽的——读回来的值是什么类型、连接池满了会怎样。

---

## 2. 失败：两个请求抢最后一件库存

上一章那道排队门让你以为并发问题解决了。它没有——
它只是让「一个进程里两个请求」不打架。**两个进程、或者一个连接池，还是会打架。**

教科书上的写法是「先 SELECT 看看够不够，够就 UPDATE」：

```ts
// 错的
const p = await tx.one('SELECT stock FROM products WHERE id = ?', [id])
if (p.stock < qty) throw new HttpError(409, 'OUT_OF_STOCK', '库存不足')
await tx.query('UPDATE products SET stock = stock - ? WHERE id = ?', [qty, id])
```

`SELECT` 和 `UPDATE` 之间有一段时间差。这段时间差在 SQLite 上不存在，
因为 SQLite **整库只有一个写者**——第二个写语句会等第一个写完。

**所以这个 bug 在前面的载体上复现不出来。载体不支持，就教不了。**
这是换库的唯一理由：不是为了「PostgreSQL 更好」，是为了让这个失败真的发生一次。

在 PostgreSQL 上跑一遍。两条连接，用**显式 barrier** 让它们同时读到同一个 stock：

```bash
node scripts/race.mjs lost
```

```
============================================================
场景一：先查后写（教科书写法）
============================================================
  乙 读到了 stock = 1
  甲 读到了 stock = 1
  乙 按自己读到的值写回了 stock = 0
  甲 按自己读到的值写回了 stock = 0

  买到手的件数: 2     <- 两个请求都拿到了成功响应
  库存实际减少: 1     <- 库里的 stock 从 1 变成了 0

  **丢失更新。** 两个请求都拿到了成功响应，
  但库存只减了 1 件——有 1 个订单没有对应的发货。
  没有异常，没有日志，没有 409。仓库只能等发现超卖之后再回头处理。
```

::: danger 为什么这里不用 setTimeout
丢失更新要复现，必须让两个连接**同时**读到同一行。
用 `setTimeout` 去猜「该睡多久对方的写语句才会落下」，十次里有九次不并发——
而那一次没复现出来，你会以为「PostgreSQL 挡住了」。

**结论完全反了，而且你不会知道自己错了。**
所以 `race.mjs` 用一个显式 barrier：两边都 SELECT 完了，才一起放行去 UPDATE。
到齐才走，时序是确定的。
:::

## 3. 三种隔离级别，逐个看

`npm run race` 会把四个场景都跑一遍。第二个场景是本项目实际用的写法：

```bash
node scripts/race.mjs guarded
```

```
  甲 读到了 stock = 1（读了，但不用来做判断）
  乙 读到了 stock = 1（读了，但不用来做判断）
  甲 扣减成功
  乙 扣减失败（0 行受影响）-> 409 库存不足

  库存实际减少: 1     <- 只有一个请求成功
  库里的库存: 0
```

注意这里是**一个失败、一个成功**，不是「两个都成功」。
`stock >= 1` 这个判断不在内存里做，交给数据库在**写的那一刻**判断，
而判断和写入之间有行锁——所以它们之间插不进来。
业务代码靠 `RETURNING` 拿到 0 行受影响，就知道该回 409。

第三个场景是同样的先查后写，但把隔离级别提到 `SERIALIZABLE`：

```bash
node scripts/race.mjs serializable
```

```
  甲 读到了 stock = 1
  乙 读到了 stock = 1
  甲 提交成功
  乙 被拒绝：40001  could not serialize access due to concurrent update
```

**PostgreSQL 默认的读已提交（READ COMMITTED）挡不住这个。**
`SERIALIZABLE` 挡得住，但**不是靠提前拒绝，是靠提交时才发现**：
它在读的时候给这行打了快照锁，两个事务于是成了串行，
后一个提交时发现「你这笔依赖一个已经过期的快照」，报 40001。

也就是说：**数据库不阻止你写错，它在提交时拒绝你。**
所以调用方必须处理 40001——通常的做法是重试整笔事务，
而重试又要求写操作本身是幂等的。

## 4. 占位符：业务代码写 `?`，pg 只认 `$1`

换库的第一件事就是这个。`routes/` 里所有 SQL 都写着 `?`：

```ts
await db.one<ProductRow>('SELECT * FROM products WHERE id = ?', [id])
```

`pg` 不认。它要的是：

```sql
SELECT * FROM products WHERE id = $1
```

两个选择：把全项目的 SQL 逐处改成 `$1`，或者在数据层里改写。
本项目选后者——**这正是上一层只有三个方法存在的理由**。

`apps/api/src/db/placeholders.ts`：

```ts
export function toPlaceholders(sql: string): string {
  let out = ''
  let i = 0
  let n = 0

  while (i < sql.length) {
    const c = sql[i] as string

    if (c === "'") { const end = skipQuoted(sql, i, "'"); out += sql.slice(i, end); i = end; continue }
    if (c === '"') { const end = skipQuoted(sql, i, '"'); out += sql.slice(i, end); i = end; continue }

    if (c === '-' && sql[i + 1] === '-') {
      const nl = sql.indexOf('\n', i)
      const end = nl === -1 ? sql.length : nl
      out += sql.slice(i, end); i = end; continue
    }

    if (c === '/' && sql[i + 1] === '*') {
      const close = sql.indexOf('*/', i + 2)
      const end = close === -1 ? sql.length : close + 2
      out += sql.slice(i, end); i = end; continue
    }

    const tag = matchDollarTag(sql, i)
    if (tag !== null) {
      const close = sql.indexOf(tag, i + tag.length)
      const end = close === -1 ? sql.length : close + tag.length
      out += sql.slice(i, end); i = end; continue
    }

    if (c === '?') { n += 1; out += `$${n}`; i += 1; continue }

    out += c
    i += 1
  }

  return out
}
```

**它跳过五类区域**：单引号字符串、双引号标识符、`--` 行注释、块注释、
PostgreSQL 的 dollar-quoting。区域里的问号原样保留，区域外的依次编号。

::: danger 它是便利层，不是 SQL 解析器
**一旦出现扫描器覆盖不到的语法，改写就会静默错位。**
错位的症状是「参数绑到了别的列上」——语句照样成功，值全错，比直接报错难查得多。

所以 `apps/api/test/placeholder.test.ts` 那 17 条不是装饰，是这道闸的本体：

```bash
npx tsx --test apps/api/test/placeholder.test.ts
```

覆盖普通语句、字符串字面量里的问号、注释里的问号、dollar-quoting 里的问号、
转义的单引号，以及「本来就写着 `$1` 的语句不能被当成标签吃掉」。
少一条就是多一类静默错误。
:::

## 5. 迁移：给新库一份新历史

先说清楚**不能做什么**：不能改 `001_init.ts`。

不是因为规矩，是因为它做不到。那四个主键写的是 `AUTOINCREMENT`：

```sql
id INTEGER PRIMARY KEY AUTOINCREMENT   -- 四张表各一个
```

`AUTOINCREMENT` 这个关键字在 PostgreSQL 里**根本不存在**。
翻译这条路从第一步就是死的。

而改写已经跑过的迁移更是被自己的守卫挡着——
`migrate.ts` 会拿 `up` 函数算指纹，和版本表里记的比对：

```
迁移 001_init 已经应用过，但内容被改过。
  库里的 checksum：e982f891...
  现在的 checksum：3f9a2c14...

已经执行过的迁移不能改写——数据库此刻的状态只和当时那一版对得上。
要加新改动就写一个新版本的迁移。
```

所以换库的做法是：**给新库一份新历史。**

```
apps/api/src/db/migrations/
  sqlite/001_init.ts  002_…  003_…   冻结，只被 v1.3 及更早的 tag 用
  pg/001_pg_baseline.ts             新的，当前这套
```

`001_pg_baseline.ts` 建的是**当前**结构——`products` 同时有 `name` 和 `title`。
002（加 description）和 003（加 title）那两步被折叠进来了。
因为 PostgreSQL 这边是个空库，没有人经历过那两次变更。

版本号**从 1 重新开始**。这是有意的：版本表是给**这个库**看的，不是给代码看的。
两个库各有一份 `schema_migrations`，各记各的。

起一次服务就能看到：

```bash
docker exec fullstack-backend-db psql -U postgres -d orders \
  -c "SELECT version, name, left(checksum, 12) AS checksum FROM schema_migrations"
```

```
 version |    name     |   checksum
---------+--------------+---------------
       1 | pg_baseline  | 94fba612ae85
(1 row)
```

**一条，就一条。** 不是四条。

::: warning 这三个文件不许动，而且有东西拦着
`migrations/sqlite/` 里的三个文件不参与任何运行路径。
一份不参与运行的东西最容易被当成「反正没人用，改一下没关系」，
所以注释写一百遍「不许改」也拦不住一次顺手编辑。

`apps/api/test/frozen.test.ts` 把三个 `up` 函数的指纹写死了。
改动其中任何一个，那三条测试立刻挂，并告诉你是哪个版本对不上了。

真要删的话，先删那条测试。顺序反了这个约束就形同虚设。
:::

## 6. 错误码：787 和 2067 变成 23503 和 23505

这一处的位置出乎所有人意料：**它不在 `db/` 目录里，它在接口层。**

SQLite 的约束错误带一个数字 `errcode`，是「扩展结果码」：
低 8 位是主码，高位才是具体哪一条。所以要位运算：

```ts
if ((e.errcode & 0xff) !== 19) return null
switch (e.errcode) {
  case 787:  return 'foreignkey'   // SQLITE_CONSTRAINT_FOREIGNKEY
  case 2067: return 'unique'       // SQLITE_CONSTRAINT_UNIQUE
  ...
}
```

`pg` 的错误上 `code` **就是 SQLSTATE**，一个五字符的字符串。查表就行：

```ts
const code = (err as { code?: unknown }).code
if (typeof code !== 'string') return null
if (!code.startsWith('23')) return null      // 23 是完整性约束这一类

switch (code) {
  case '23503': return 'foreignkey'   // foreign_key_violation
  case '23505': return 'unique'       // unique_violation
  case '23514': return 'check'
  case '23502': return 'notnull'
  default:      return 'other'
}
```

**对外一个字节都没变**（**会改数据**）：

::: request
```bash
curl -X POST http://localhost:3002/api/products \
  -H "Content-Type: application/json" \
  --data-binary '{"sku":"KB-87","name":"另一个键盘","title":"另一个键盘","priceCents":100,"stock":1}'
```

```http
HTTP/1.1 409 Conflict
{"error":{"code":"PRODUCT_SKU_TAKEN","message":"SKU KB-87 已经存在"}}
```
:::

底下的编号从 `2067` 变成了 `23505`，客户端看到的还是同一句 `PRODUCT_SKU_TAKEN`。
这一条是**换库没改契约**的证据，`verify-tag v1.4` 里有对应断言：
它还会检查响应体里没有漏出 `23505` 或者 `unique_violation`。

外键冲突也一样（**不会改数据**，商品还在）：

::: request
```bash
curl -i -X DELETE http://localhost:3002/api/products/1
```

```http
HTTP/1.1 409 Conflict
{"error":{"code":"PRODUCT_IN_USE","message":"商品 1 已经被订单引用，删不掉"}}
```
:::

::: tip 主键冲突在 PG 上分不出来
SQLite 能靠 `1555` 把主键冲突单独分出来，PostgreSQL 做不到——
`23505` 同时覆盖唯一键和主键。要区分就得看 `err.constraint`（约束名）。

本项目不需要区分，所以 `ConstraintKind` 那一档 `primarykey` 直接去掉了。
**不是所有「更细的分类」都值得在换库时保留。**
:::

## 7. 取值：读回来的到底是什么类型

这一节是换库最隐蔽的部分。**它不会报错**，只是悄悄地变了形状。

`timestamptz` 取回来是 JS 的 `Date`，而接口契约里 `createdAt` 是 `z.string()`。
`COUNT(*)` 在 PostgreSQL 里是 `bigint`，`pg` 默认读成**字符串**。
`BIGINT` 列同理。

原始驱动的行为（不经过任何包装）：

```
=== timestamptz 读回来是什么 ===
typeof created_at : object
值                : 2026-10-02T16:34:19.350Z

=== COUNT(*) 读回来是什么 ===
typeof n          : string
值                : "3"
加了 ::int 之后   : number 3

=== int4 列 ===
typeof id         : number

=== BIGINT（int8）读回来是什么 ===
typeof n          : string
值                : "9007199254740993"
转成 number       : 9007199254740992
JS 认为相等的那个 : true
```

最后两行是这一节的重点。`9007199254740993` 转成 JS 的 number 之后变成
`9007199254740992`——**静默丢了一位**。因为 2^53 是 JS 的安全整数上限，
再往上就没法精确表示了。`pg` 默认返回字符串，正是为了不替你做这个决定。

::: danger 两条坑的解法不一样
**时间**：在驱动里归一。`db/postgres.ts` 里一行类型解析器：

```ts
types.setTypeParser(1184, (value: string) => new Date(value).toISOString())
```

归一放在驱动里，**不放路由里**。归一化属于「让底层适配上层契约」，
那是数据层这一层的职责；放到路由里的话每条查询都得自己记得转一遍，
漏一处就悄悄变了形状。

**整数**：本项目全表用 `INTEGER`（int4），取回来是 number，所以不受影响。
`COUNT(*)` 那几处显式写了 `::int`：

```sql
SELECT COUNT(*)::int AS n FROM products
```

**BIGINT 是故意不改的。** 哪天给金额换成 `BIGINT`，
`COUNT(*)`、`SUM()`、`bigserial` 主键会一起变成字符串，
症状是接口返回的 id 变成 `"1"`。两条出路：继续用 int4，
或者 `types.setTypeParser(20, Number)`——后者要自己承担精度损失。

这几条全部由 `apps/api/test/pg-types.test.ts` 钉住。
:::

## 8. 事务：删掉那道门，留着认领标记

上一章为了「一个进程只有一条连接」加了一道排队门 `withConnection`，
外加一个 `AsyncLocalStorage` 用来判断「这次读写是不是事务自己的」。

现在排队那一半**没有了**。池把连接发出去，事务天然独占它拿到的那一条：

```ts
async transaction<T>(fn: (tx: Db) => Promise<T>): Promise<T> {
  if (claimed.getStore() !== undefined) throw new NestedTransactionError()

  const client = await pool.connect()
  try {
    await client.query('BEGIN')
    const result = await claimed.run(client, () => fn(db))
    await client.query('COMMIT')
    return result
  } catch (err) {
    try {
      await client.query('ROLLBACK')
    } catch (rollbackErr) {
      console.error('[db] 回滚失败，事务状态可能已经不对了：', rollbackErr)
    }
    throw err
  } finally {
    client.release()
  }
}
```

**但归属标记还得留。** 它解决的是另一个问题——「这次 query 该用哪条连接」。
判断这件事代码不在栈上，中间隔着一个已经 await 出去的 Promise，
调用栈那套判断在这里失效。

> **删的是排队，留的是认领。** 两件事，别混。

`catch` 里 `ROLLBACK` 单独 try/catch、释放连接放 `finally`，
这两条是上一章的教训，原样照搬。`NestedTransactionError` 也不在驱动文件里了——
它和 SQLite 没有任何关系，说的是「你把事务边界画错了」，
换哪个数据库这句话都成立，所以它搬到了 `db/errors.ts`。

## 9. 连接池：耗尽时是排队，不是报错

`max` 该设多大？先看清它耗尽时长什么样（**只改本地连接池配置，不改数据**）：

```bash
node scripts/race.mjs pool
```

```
  借走了池里唯一那条连接，开始一个事务
  发第二个查询——它没有报错，也没有立刻返回，它在排队
  攥了 800ms 之后才放。
  放掉那条连接
  排队的那个查询这时才返回，拿到 {"n":1}

  它等了 823 ms。

  **池耗尽的表现是排队，不是报错。**
```

这就是为什么「连接池满了」这个故障很难查：日志里没有异常、没有 500，
只有一堆请求慢慢变慢，最后全堆在超时上，看起来像「数据库很慢」。

两条出路：把 `max` 调大，或者**把事务做短**。
调大 `max` 只是把排队往后推——每个连接都是一条到数据库的网络往返，
而数据库能同时处理多少是它自己的事，不是你池子大就行的。

## 10. 工具选型

### 驱动：pg vs postgres.js vs 查询构造器 vs ORM

| 方案 | 它替你做了什么 | 代价在哪儿 | 什么时候该换 |
| --- | --- | --- | --- |
| **`pg` + 手写 SQL**（本项目） | 什么都不替 | SQL 要自己写，占位符自己改写 | —— |
| `postgres.js` | 标签模板，SQL 直接内插，不用写 `$1` | 生态比 pg 小一档；企业里的运维经验多在 pg 上 | 团队里没人写过 `?` 改写，而且想彻底躲开占位符 |
| `Knex` / `Slonik` | 拼 SQL 但保持 SQL 形状，能换库 | 多一层抽象，调试时要看两层 | 需要同时支持两种数据库 SQL，且愿意接受那一层 |
| `Prisma` / `Drizzle` | 类型、迁移、关联加载 | 表结构不再是你能直接读懂的 SQL；迁移工具会重写历史文件 | 关联加载多到写不动手写 join，且团队接受工具生成的迁移 |

**为什么选 `pg`**：它是事实标准，招人好招，出问题搜得到答案。
本项目要教的是「SQL 和数据库行为」，那么**驱动越薄越好**——
`postgres.js` 的标签模板确实更顺手，但它把「占位符」这件事藏起来了，
而占位符正是这一章要教的东西之一。

### 迁移：为什么仍然是手写

上一篇的结论没变：四个方法够用，而且每一行都是教学内容。
换库之后多了一条**新的**理由：

| 方案 | 换库时会发生什么 | 判据 |
| --- | --- | --- |
| **手写**（本项目） | 自己决定「给新库一份新历史」，过程可见 | —— |
| `node-pg-migrate` | 面向 PG，SQL 文件直接放进去 | 已经只用一个数据库，且团队里有人只想写 SQL |
| `Umzug` | 框架重，但能接任意执行器 | 需要同时驱动多套迁移，且愿意接受它的抽象 |
| 用 ORM 生成 | 很多 ORM 会为了对直模型**重写历史迁移** | 绝不——那就是破坏 checksum |

**「绝对不要让工具重写已执行的迁移」这一条，换库之后从建议变成了硬约束**：
PG 那边如果照抄 SQLite 那三个迁移，第一次启动就会在 checksum 上退出。

## 11. 场景问题

| 场景 | 怎么办 | 为什么 |
| --- | --- | --- |
| **换库时老数据怎么办** | 本载体没有真实数据要搬，所以**不写数据搬迁** | 真要搬的话先问三个：能停机吗？老库和新库的结构差多少？搬错了怎么回滚？这三个问题答不上来就不该动手 |
| **老版本代码还在跑** | 这一章整篇都在处理这个 | 它不是「迁移」的问题，是「新旧两个版本怎么同时对着一套新结构跑」的问题 |
| **测试库和开发库怎么隔离** | 每个测试进程建一个自己的库，跑完删掉；库名必须含 `_test` | 见第 12 节，这一条是踩出来的 |
| **PG 连不上** | 先 `docker compose ps` 看 healthy 没有 | 服务在但没 ready 的时候，连接会被拒而不是排队 |
| **某个 tag 复现时该连哪个库** | `verify-tag` 按 tag 判方言 | `v1.0`–`v1.3` 走 SQLite，`v1.4` 起走 PG。按 tag 判，不按当前代码判 |

## 12. 测试：一进程一个库

换库之后测试夹具全部重写了，其中一条是踩出来的。

一开始的写法是「所有测试文件共用一个库，每个文件开头 `DROP SCHEMA public CASCADE`」。
结果**几乎每个文件都在报 `relation "products" does not exist`**。

原因很简单：**Node 的 test runner 并行跑各个测试文件**（默认并发度是 CPU 核数）。
十一个文件同时清空同一个库，于是它们互相把对方的表删了。

> **清空不是隔离。每个进程一个库才是。**

顺带一提：SQLite 时代之所以没这个问题，是因为那时候每个文件 `mkdtemp` 出一个自己的
`.db` 文件，隔离是白拿的。**换库把这个性质弄丢了，得显式补回来。**

还有一个安全闸。测试里要做 `DROP DATABASE` 这种事，连错库是**数据没了**，
不是目录脏了，所以库名必须含 `_test`，不满足直接抛错退出：

```
拒绝连接：orders 的库名里没有 _test。

测试会 DROP 整个数据库，连错一次开发数据就没了。
所以只允许连库名含有 _test 的库。
```

## 13. 验证

`npm run verify` 退出 0，**135 tests / 0 fail**（换库前是 81）。
换库带动的三组新测试：

```bash
npx tsx --test apps/api/test/placeholder.test.ts   # 17 条，占位符改写
npx tsx --test apps/api/test/pg-types.test.ts      # 10 条，取值规则
npx tsx --test apps/api/test/frozen.test.ts         #  4 条，历史迁移不许改
```

接口层的 409 契约在换库之后必须仍然成立，`verify-tag v1.4` 里有专门一条：

```
✔ 错误契约没变：同 SKU 仍然是 409 PRODUCT_SKU_TAKEN
✔ 外键冲突仍然是 409 PRODUCT_IN_USE（23503 而不是 787）
```

### 变异测试：确认测试真的在守

| 改坏的地方 | 挂掉的用例 |
| --- | --- |
| 去掉改写器对 dollar-quoting 的跳过 | **3 条**：匿名标签里的问号原样保留 / 带名字的标签里的问号原样保留 / 带名字的标签里可以有多行 |
| 删掉 `23505` 的映射 | **1 条**：sku 重复返回 409，不是 400 也不是 500 |
| 把 `client.release()` 从 `finally` 挪到成功分支 | **1 条**：事务失败后连接还能继续用，不会把池耗光 |

第三条第一次做的时候**挂住了而不是失败**——池被耗光之后 `pool.connect()`
永远不返回，你看到的只是一句「测试超时」，看不出是哪条规则坏了。

改法是给整段探测套一个超时，并给 `npm test` 加了 `--test-timeout`。
**一个会挂住的回归守卫比一个会失败的糟糕得多。**

## 14. 哪些是通用的

| 上面出现的东西 | 换个项目要改吗 | 说明 |
| --- | --- | :-: |
| **业务代码只见数据层那三个方法** | 不改 | **这一篇最值钱的一条**。换库时它把影响面从「每个文件」压到「一个文件」 |
| 换库前先问「哪些东西不是业务代码」 | 不改 | 占位符、错误码、DDL、测试夹具、脚本——五类，一类都躲不掉 |
| 金额用 `INTEGER` 存最小单位 | 不改 | 换库不改变金额该怎么存 |
| 外键冲突翻译成接口语义码 | 不改 | 编号变了，语义码不变 |
| `RETURNING` 拿受影响行数 | 不改 | 两个数据库都支持，而且它比「先查再判断」少一次往返 |
| 扣减的并发判断放进 `WHERE` | 不改 | 换个数据库照样是这一条 |
| **不把已执行的迁移翻译一遍** | 不改 | 给新库一份新历史 |
| 数据层在驱动里做取值归一 | 不改 | 归一属于「让底层适配上层契约」 |
| 占位符适配层 | 抄思路 | 便利层不是解析器，必须有测试钉住它的边界 |
| `AsyncLocalStorage` 认领连接 | 抄思路 | 排队那一半可以删，认领那一半不能 |
| 每个测试进程一个库 | 抄思路 | 并行跑测试时，清空不是隔离 |
| 库名安全闸 | 抄思路 | 连错库是数据没了 |

**能直接拿走的是右边那些「不改」的。**
表名、列名、约束名随便换；池的大小和隔离级别按自己的业务定。

## 做到这一步，实际用的是什么

| 你在这一篇做的 | 对应哪一条 |
| --- | --- |
| 先列出「换库要动哪几类东西」，再动手 | `senior-fullstack-developer:fullstack-dev` **第 2 步：先定契约再写实现**——数据层的形状就是契约 |
| 冻结 SQLite 那三个迁移，PostgreSQL 另起一份历史 | 第 3 步的「可逆的数据改动」：**改写历史迁移不可逆**，所以宁可不翻译 |
| 换库之后 409 的码不变，编号变 | 第 2 步的错误契约——**一个失败模式一个语义码**，语义码对外，编号对内 |
| 给适配层补 17 条测试钉住边界 | `superpowers:test-driven-development`：先写会失败的测试，再写实现 |
| 三次变异测试，每章都做 | `superpowers:verification-before-completion` 的反向验证：**写 → 过 → 撤销修复 → 必须失败 → 恢复 → 过** |
| 用 `git diff` 的文件清单证明业务代码没动 | 同上，「说法」和「证据」分开——本项目那条证据是每个业务文件只差一行 import |

**第 2 步在这里换了一个形状。** 前面几章的「契约」是接口和表结构；
这一章的契约是**数据层那三个方法的形状**。
`routes/` 一行没改，靠的就是它——而它在 ch04 建立的时候，
理由写的是「为换库预留 async 形状」，那时候还不知道要付三笔账。

**但那三笔账没有一笔能靠当初就设计好来避免。**
占位符的语法是 `pg` 定的，错误码的编号是 PostgreSQL 定的，
`AUTOINCREMENT` 不存在是事实。能在设计时做的只有一件事：
**把受影响的东西圈进一个边界，并且让那个边界的接口足够小。**

## 跑完之后

你手上有两个真实跑出来的失败：**丢失更新**（两个请求都拿到成功，库存少扣了一件）
和**连接池排队**（没有报错，只有一堆请求变慢）。
也手上有两个不响的静默陷阱：`COUNT(*)` 读回来是字符串、
`timestamptz` 读回来是 `Date`。

还有一件事这一章刻意没做：**数据搬迁**。
载体里没有真实数据要搬，所以写出来的搬迁方案没法验证，
写了就是名词堆砌。真要搬的时候先问那三个问题。

而换库这件事本身还有一半没解决：并发写现在能挡住了，
但**同一个请求被客户端重发两次**这件事还没处理——
两个一模一样的请求，各自都会建一笔订单、各自都扣一次库存。
幂等不是「加个字段」那么简单，它的关键在**什么时候判、谁来判**。

## 下一步

两个并发的请求同时进来，那是**竞争**；
同一个请求被重发两次，那是**重复**。
后者靠数据库的唯一约束判，前者靠锁判——两件事，两套机制。
