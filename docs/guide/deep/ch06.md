# 零停机变更

> 目标：把 `products.name` 换成 `products.title`，过程中**老版本代码和新版本代码同时对着一个库跑，两边都不报错**。全程 60 分钟。

上一篇有了迁移执行器，于是「改表结构」从「改代码里的建表语句」变成了「写一个新迁移」。这一篇接着往前走一步：**改了之后，老的那一版代码怎么办。**

## 1. 怎么把代码拿到手

```bash
git checkout v1.2
npm install
npm run dev:api
```

```bash
curl -i http://localhost:3002/api/health
```

```
HTTP/1.1 200 OK
Content-Type: application/json; charset=utf-8

{"ok":true,"service":"api"}
```

这一篇要做的变更：`products.name` → `products.title`。理由很朴素——`name` 太模糊，同一个库里商品有 name、用户有 name、订单也有 name，换成 `title` 之后只有商品这一张表用它，语义就清楚了。

## 2. 失败：直接改列名

最直觉的做法，一句话：

```sql
ALTER TABLE products RENAME COLUMN name TO title
```

跑之前先看清楚**它到底会怎样**。本机实测（**只读，不动任何库**）：

```js
const { DatabaseSync } = require('node:sqlite')
const d = new DatabaseSync(':memory:')
d.exec('CREATE TABLE t (id INTEGER PRIMARY KEY, name TEXT)')
// RENAME COLUMN 本机是支持的
d.exec('ALTER TABLE t RENAME COLUMN name TO title')
console.log(JSON.stringify(d.prepare('PRAGMA table_info(t)').all().map((r) => r.name)))
```

```
["id","title"]
```

语句成功了。**问题不在数据库，在老代码。**

老版本的 `rowToProduct` 里写着 `name: row.name`。改完之后 `row.name` 查不到了，是 `undefined`。接下来这一段是整篇最重要的地方：

```js
const row = { id: 1, sku: 'KB-87', name: undefined, price_cents: 39900, stock: 25 }
const mapped = { id: row.id, sku: row.sku, name: row.name, priceCents: row.price_cents, stock: row.stock }
console.log('映射对象里 name 的值:', mapped.name)
console.log('序列化后:', JSON.stringify(mapped))
```

```
映射对象里 name 的值: undefined
序列化后: {"id":1,"sku":"KB-87","priceCents":39900,"stock":25,"createdAt":"..."}
```

**`name` 这个键整个不见了。**

`JSON.stringify` 遇到值为 `undefined` 的属性会**直接把它从输出里删掉**，不是输出成 `null`。所以：

- 接口返回 `200`
- 响应体结构完好，只是少了一个字段
- 服务端日志干干净净
- 调用方拿到一个「成功但字段缺失」的响应，**通常要等它真的去读那个字段时才会炸**

| | 期望 | 实际 |
| --- | --- | --- |
| HTTP 状态码 | 200 | 200 |
| 日志 | 无异常 | 无异常 |
| 响应里的 `name` | `"机械键盘"` | **没有这个键** |

**这是比崩溃更糟的失败。** 崩溃会被监控发现，字段缺失要等下游报「undefined 读属性」才暴露，而那时候错误的现场早就没了。

::: danger 两种「静默」不是一回事，混起来会漏
| 情况 | 映射结果 | JSON 里 |
| --- | --- | --- |
| 列还在，值是 NULL | `null` | `"name":null` —— **键在**，看得出不对 |
| 列被改名/删掉 | `undefined` | **键整个消失** —— 看不出来少了东西 |

这一章的代码只守得住第一种（`??` 兜底），第二种靠的是**别去改列名**。
:::

## 3. expand：先加，不删

正确的第一步是**只加不删**。`apps/api/src/db/migrations/003_add_product_title.ts`：

```ts
export const m003: Migration = {
  version: 3,
  name: 'add_product_title',
  async up(db: Db): Promise<void> {
    await db.query('ALTER TABLE products ADD COLUMN title TEXT')
  },
}
```

只有一行。**这一章不删 `name`，也不改它。**

跑完之后库长这样（**只读**）：

```bash
node -e "
const {DatabaseSync} = require('node:sqlite');
const d = new DatabaseSync('apps/api/data/app.db');
console.log(JSON.stringify(d.prepare('PRAGMA table_info(products)').all().map(r => r.name)));
d.close();
"
```

```
["id","sku","name","title","price_cents","stock","created_at","description"]
```

两列并存。这时候**只有新代码会用 `title`**，老代码继续读 `name`，两边都正常。

## 4. 双写

只加列不写值，等于新老两个版本的数据开始分叉：新代码写进去的行 `title` 有值，老代码写进去的行 `title` 是 NULL。

所以写入时要**两个都写**：

```ts
// 允许只给 title 不给 name（反之不行，name 仍是必填），
// 这样新调用方可以只用新键，老调用方也不用改。
const name = parsed.data.name
const title = parsed.data.title ?? name

const rows = await db.query<ProductRow>(
  `INSERT INTO products (sku, name, title, price_cents, stock, created_at)
   VALUES (?, ?, ?, ?, ?, ?)
   RETURNING *`,
  [parsed.data.sku, name, title, parsed.data.priceCents, parsed.data.stock, now],
)
```

**只写一个值不是「省一次写入」，是给另一个版本埋雷。** 回填跑完之后有人删掉一个，另一个版本的数据就成了孤儿。两列同生共死，将来 contract 那一步才能一次删干净。

实跑（**会写库**）：

::: request
```bash
curl -X POST http://localhost:3002/api/products \
  -H "Content-Type: application/json" \
  --data-binary '{"sku":"DW-1","name":"双写测试","priceCents":100,"stock":1}'
```

```http
HTTP/1.1 201 Created
Content-Type: application/json; charset=utf-8

{"id":1,"sku":"DW-1","name":"双写测试","title":"双写测试","priceCents":100,"stock":1,"createdAt":"2026-10-02T14:01:14.343Z"}
```
:::

`name` 和 `title` 都在，值一样。

## 5. 双读

写入解决了「新代码写的行」，但**回填之前，老代码写的那批行 `title` 仍然是 NULL**。所以读的时候要兜底：

```ts
function rowToProduct(row: ProductRow): Product {
  return {
    id: row.id,
    sku: row.sku,
    name: row.name,
    title: row.title ?? row.name,
    priceCents: row.price_cents,
    stock: row.stock,
    createdAt: row.created_at,
  }
}
```

就那一个 `?? row.name`。少它的后果不是报错，是**响应里的 `title` 变成 `null`**——老数据全是这样。

## 6. 实跑：两个版本同时对着一个库

这是这一章真正要证明的东西。**说法不算数，两个服务同时起来才算。**

把 v1.1 的代码导出来，指向**同一个 `app.db`**，开两个端口：

```bash
# 终端 1：v1.2（新代码）连共享的那个库
DB_PATH=<共享库> PORT=3016 npm run dev:api

# 终端 2：v1.1 导出到临时目录、装好依赖，连同一个库
cd <v1.1 导出目录>
DB_PATH=<同一个库> PORT=3017 npm run dev:api
```

::: warning 两条命令都会改数据
它们往同一个库里写。每条命令前面用 `DB_PATH` 明确指向那个文件，别让它落到默认的开发库上。
:::

**新版本读：**

::: request
```bash
curl -s http://localhost:3016/api/products/1
```

```http
{"id":1,"sku":"OLD-1","name":"老商品1","title":"老商品1","priceCents":1000,"stock":5,"createdAt":"2026-10-02T13:57:19.819Z"}
```
:::

**老版本读同一行：**

::: request
```bash
curl -s http://localhost:3017/api/products/1
```

```http
{"id":1,"sku":"OLD-1","name":"老商品1","priceCents":1000,"stock":5,"createdAt":"2026-10-02T13:57:19.819Z"}
```
:::

对照着看：

| | `name` | `title` |
| --- | --- | --- |
| v1.2 | `"老商品1"` | `"老商品1"` |
| v1.1 | `"老商品1"` | **没有这个键** |

老版本少一个键，**但它自己没报错、新版本也没报错**。老版本那份响应本来就是它上线时的形状，调用方早就适配了。

**接下来是最关键的一步：让老版本写一条。**

::: request
```bash
curl -X POST http://localhost:3017/api/products \
  -H "Content-Type: application/json" \
  --data-binary '{"sku":"BY-OLD-1","name":"老版本写的","priceCents":200,"stock":3}'
```

```http
{"id":25,"sku":"BY-OLD-1","name":"老版本写的","priceCents":200,"stock":3,"createdAt":"2026-10-02T14:02:06.880Z"}
```
:::

库里那一行长这样（**只读**）：

```
{"sku":"BY-OLD-1","name":"老版本写的","title":null}
```

**老版本不知道 `title` 的存在，所以它写的那一行 `title` 是 NULL。** 新版本读它：

::: request
```bash
curl -s http://localhost:3016/api/products/25
```

```http
{"id":25,"sku":"BY-OLD-1","name":"老版本写的","title":"老版本写的","priceCents":200,"stock":3,"createdAt":"2026-10-02T14:02:06.880Z"}
```
:::

`"title":"老版本写的"` —— **`?? row.name` 把它兜住了。**

这一条就是双读存在的全部理由：**回填永远补不齐所有行**，因为在回填期间一直有老版本在写。补齐的那一刻之后老版本下线之前，还会有新的 NULL 行产生。**双读要一直留着，直到老版本确认不再被部署。**

## 7. 回填：分批、幂等、能中断

`scripts/backfill.mjs`。三个性质缺一不可：

| 性质 | 靠什么实现 |
| --- | --- |
| **幂等** | `WHERE title IS NULL`，跑两遍和跑一遍一样 |
| **可中断** | 一批一个事务，中途挂了只丢当前这批 |
| **进度可见** | 每批报「还剩多少行」，不然你不知道它是在跑还是卡住了 |

先造 23 行老数据（**会改数据**）：

```bash
node -e "
const {DatabaseSync} = require('node:sqlite');
const d = new DatabaseSync('apps/api/data/app.db');
const now = new Date().toISOString();
const ins = d.prepare('INSERT INTO products (sku,name,title,price_cents,stock,created_at) VALUES (?,?,NULL,?,?,?)');
for (let i=1;i<=23;i++) ins.run('OLD-'+i, '老商品'+i, 1000, 5, now);
console.log('插了 23 行 title 为 NULL 的老数据');
console.log('待回填:', d.prepare('SELECT COUNT(*) AS n FROM products WHERE title IS NULL').get().n);
d.close();
"
```

```
插了 23 行 title 为 NULL 的老数据
待回填: 23
```

先只看状态（**只读**）：

```bash

```

```

```


0 批、0 改动。抽查有没有补错的（**只读**）：

```bash
"
```

```

```

### 一条语句 UPDATE 全表

真实的项目里，回填常常是几百万行。那时候下面这条 SQL 会锁表锁到语句结束：

```sql
UPDATE products SET title = name WHERE title IS NULL;   -- 别这么干
```

几万行的库上你察觉不到，几百万行上就是**所有写请求排队等它跑完**。分批的意义不是「显得专业」，是**把一次长锁拆成很多次短锁**，中间让出机会给别的请求。

批大小按行宽和单行耗时调，没有万能值。

## 8. 这个脚本自己踩的两个坑

这一节是写这个脚本时真踩出来的，不是想出来的。**两个都是「不报错但不干活」那一类。**

### 坑一：db.exec() 不接受绑定参数

第一版更新语句这么写：

```js
db.exec(`UPDATE products SET title = name WHERE title IS NULL AND id IN (${placeholders})`)
```

`placeholders` 是 `?,?,?`——看起来对。**但 `db.exec()` 根本不能带参数**，那些问号被当成未绑定的占位符，值全是 NULL。于是 `id IN (NULL, NULL, NULL)` 匹配不到任何行。

本机实测（**只读**）：

```
初始 title 非空的行数: 0
用 exec() 跑完（不传参）后: 0 ← 仍然是 0，语句没报错但一行没改
用 prepare().run(3) 后: 1  changes = 1
```

**语句成功执行，0 行受影响，没有异常。** 换成 `prepare().run(...ids)` 立刻 `changes = 1`。

### 坑二：批处理没有「有没有真的推进」的检查

因为坑一，每批都是「处理 10 行，还剩 23 行」。而循环条件是 `while (total > 0)`——`total` 永远不降，于是**无限循环**。

这个脚本把日志刷到了 300 多行还没停。

比死循环更值得记的是它的**失败形状**：批处理脚本最坏的失败不是报错，是**不报错也不推进**。`while` 的条件一直成立，日志一直打印，人只看得到「好像在跑」。

修法是加一道进度守卫：

```js
const after = remaining()
if (after >= total) {
  console.error(`  第 ${batch} 批：语句报告改了 ${result.changes} 行，但待回填数仍是 ${total}，没有推进。`)
  console.error('  停下来，不继续空转。')
  process.exit(1)
}
```

**每批跑完都核对一次「剩余数真的少了」。没少就当失败处理。** 这一条对任何批处理脚本都成立——数据回填、批量改字段、分片上传的循环，通用。

### 双写

```bash
curl -X POST http://localhost:3002/api/products \
```

响应里 `name` 和 `title` 都在，值一样。

### 双读

库里造一行 `title IS NULL` 的数据，然后读它，**`title` 必须等于 `name`，不是 null**。

### 老版本兼容

导出 v1.1、指向同一个库、开两个端口，第 6 节那四条命令原样跑一遍，两边都不该报错。

### 变异测试：确认测试真的在守

改坏一处，跑测试看挂几条：

| 改坏的地方 | 挂掉的用例 |
| --- | --- |
| 双读里的 `?? row.name` 去掉 | **1 条**：老数据（title 为 NULL）读出来的 title 退回 name |
| `INSERT` 少写 `title` 一列 | **3 条**：双写两条 + 老代码视角一条 |

**两次抓到的用例不重叠**，说明双读和双写确实各自被独立守着，不是同一批断言在空转。

## 10. 哪些是通用的

| 上面出现的东西 | 换个项目要改吗 | 说明 |
| --- | --- | :-: |
| **expand / backfill / contract 三段** | 不改 | **这一篇最值钱的一条** |
| **双写：两个字段一起写** | 不改 | |
| **双读：新字段为空时退回旧字段** | 不改 | |
| **`?? 旧字段` 而不是 `?? 默认值`** | 不改 | 默认值是编的，旧字段是真数据 |
| 回填的 `WHERE 新字段 IS NULL` | 抄形状 | 换字段名 |
| 一批一个事务 | 不改 | |
| **每批核对「真的推进了」** | 不改 | 任何批处理脚本都要 |
| 不用 `exec()` 跑带参 SQL | 不改 | |
| `--batch` / `--status` 两个开关 | 抄思路 | |
| 用 `?? ` 而非 `|| ` | 不改 | `||` 会把空字符串也吞掉 |
| 迁移文件里只写 ADD COLUMN | 不改 | 删列永远是下一个迁移的事 |
| 「这一章不删任何东西」 | 不改 | **删和加混在一次发布里，就没有回退窗口了** |

**能直接拿走的是右��那些「不改」的。** 字段名、文件路径、批大小随便换，规则不用。

## 做到这一步，实际用的是什么

| 你在这一篇做的 | 对应哪一条 |
| --- | --- |
| 加列不删列，两列并存 | `senior-fullstack-developer:fullstack-dev` **第 3 步：可逆的数据改动** |
| 每一步都能被两个版本同时读 | 第 3 步的「保留可回退的中间状态」 |
| 契约里 `name` 和 `title` 都在 | **第 2 步：先定契约再写实现**——契约先行，两个调用方都照顾到 |
| 变异测试确认守卫有效 | `superpowers:verification-before-completion` 的反向验证 |
| 批处理的进度守卫 | 第 3 步的「边界情况」——**部分失败要有明确出口，不能让它静默循环** |

**「可逆」在这一篇有了具体形状。** 上一篇改的是结构，加错了就加回来；这一篇改的是**已经被别人依赖的接口**，多加一个字段可以随时撤，但**删字段的那一刻是不可逆的**——只要还有一个调用方在读它，删了就是生产事故。

所以 contract 阶段（未来的 004）不是「顺手清一下」，它有自己的前提：老版本确认下线、回填确认跑完（`title IS NULL` 归零）、没有调用方还在读 `name`。
