# 第3章 界面和数据不能各说各话

> 目标：后端接口调起来了，页面还没接上。这一章把两者接起来，并处理四种状态、乐观更新和请求竞态。约 40 分钟。

CRUD 那部分两小时就能会。**这一章讲的是「写得住」和「会写」的差别**：网络慢的时候界面显示什么、勾选失败了怎么恢复、快速连点几次怎么不出乱子。

## 1. 怎么把代码拿到手

```bash
git checkout v0.3
npm install
```

开两个终端起前后端，浏览器打开 `http://localhost:5173`。

## 2. 四种状态，缺一个就是 bug

大部分教程只写「有数据」和「没数据」两种。少了的两种，用户看到的是一片空白，无法分辨是**还在加载**还是**坏了**。

```ts
type State =
  | { status: 'loading' }                              // 正在请求
  | { status: 'error'; message: string }               // 请求失败
  | { status: 'ready'; tasks: Task[] }                 // 成功
```

`ready` 里面又分两种情况——有数据和空数组：

| 状态 | 界面上显示什么 |
| --- | --- |
| `loading` | 「加载中…」 |
| `error` | 错误信息 + 重试按钮 |
| `ready` 且有数据 | 任务列表 |
| `ready` 且空数组 | 「还没有任务」 |

::: danger 少了 loading 的真实代价
网络慢一秒，用户看到的是**完全空白**。他的第一反应是「这网站坏了」，然后刷新页面——刷新又发一次请求，慢的时候更糟。
:::

这四种状态在 `apps/web/src/App.tsx` 里：

```tsx
{state.status === 'loading' && <p className="loading">加载中…</p>}

{state.status === 'error' && (
  <div className="error" role="alert">
    <p>{state.message}</p>
    <button onClick={() => load()}>重试</button>
  </div>
)}

{state.status === 'ready' && (
  <TaskList tasks={state.tasks} onToggle={handleToggle} onDelete={handleDelete} />
)}
```

## 3. 断网时看到的是两种完全不同的错误

这是初学者最容易忽略、但一遇到就完全没头绪的地方。

| 情况 | `fetch` 表现 | 浏览器 Network 面板 |
| --- | --- | --- |
| 后端返回 500 | 正常拿到响应 | **有**这条请求，标红 |
| 后端进程没跑 | **抛异常** | **没有**任何记录 |

第二种情况下请求**根本没发出去**，不是发出去了被拒绝。两种错误的处理方式完全不同：

```ts
// apps/web/src/api.ts
async function request<T>(path: string, init?: RequestInit): Promise<T> {
  let res: Response

  try {
    res = await fetch(path, { ...init, headers: { ... } })
  } catch (err) {
    // fetch 抛异常只有一个原因：请求没发出去
    throw new RequestError(0, 'NETWORK_ERROR', '连不上后端。确认后端已启动、代理已配置。')
  }

  if (res.status === 204) return undefined as T

  const body = await res.json().catch(() => null)
  if (!res.ok) {
    // 这里才是「发出去但失败了」
    throw new RequestError(res.status, ..., ...)
  }
  return body as T
}
```

把这两条错误分开，用户看到的提示才准确。混在一起的话，用户会拿到一句「连不上后端」，然后去检查网络，而真实原因是服务端 500 了。

## 4. 为什么所有请求集中在 api.ts

组件里直接写 `fetch` 有三个必然出现的问题：

1. **URL 到处硬编码**。改一次地址要改十处
2. **错误处理重复**。每个组件各写一遍 `try/catch`，写法还不一样
3. **测不了**。组件和 HTTP 绑死，没法单独测渲染

所以本项目规定：**只有 `apps/web/src/api.ts` 一个文件能调 `fetch`**。

```ts
// 组件里只调这个，不碰 fetch
const tasks = await api.list()
await api.toggle(task.id, !task.done)
```

这不是洁癖。新增一个接口时，类型定义、错误处理、状态码判断只需要写一次。

## 5. 乐观更新：先改界面，失败再退回去

**这是本章最值得学的一节。**

### 朴素做法的问题

勾一个复选框，用户要等网络往返完才看到变化。局域网 20ms 感觉不出来，网络差或者后端在另一台机器上，300ms、500ms 都可能。

### 乐观更新的做法

不等了，**先假设会成功**，把界面改掉。真失败了再退回去。

```tsx
async function handleToggle(task: Task) {
  if (state.status !== 'ready') return
  const backup = state.tasks              // ① 存一份备份

  // ② 先改界面，不等网络
  setState({
    status: 'ready',
    tasks: backup.map((t) => (t.id === task.id ? { ...t, done: !t.done } : t)),
  })

  try {
    await api.toggle(task.id, !task.done) // ③ 后台发请求
  } catch (err) {
    setState({ status: 'ready', tasks: backup })   // ④ 失败，退回备份
    window.alert(`没能更新：${describe(err)}`)
  }
}
```

关键就是那句 `backup`。**只要改了界面，就得有备份。** 没有备份，失败时就不知道该退回到什么状态。

### 什么时候别用乐观更新

| 场景 | 建议 |
| --- | --- |
| 勾选、开关这类小操作 | 适合，用户几乎感觉不到失败 |
| 删除 | 可以用，但要给「撤销」的机会 |
| 提交表单 | **不适合**，用户需要明确知道提交成功没有 |
| 支付、删除账户 | **绝对不适合**，必须等结果 |

判断标准：**失败率高不高、用户能不能接受界面先变后回退。** 支付失败率低但代价高，绝不能乐观。

## 6. 请求竞态：连点两次，界面乱了

快速点两下复选框会发生什么？

```
时刻 1  界面变 ✓，请求 A 发出（done: true）
时刻 2  用户又点了一下，界面变 ✗，请求 B 发出（done: false）
时刻 3  请求 B 先回来（快）→ 界面 ✗
时刻 4  请求 A 后回来（慢）→ 界面 ✗   ← 界面对了，但数据库里是 true
```

**界面和数据库对不上了。** 原因不是代码写错了，是响应到达的顺序和发出的顺序不一致。

### 解法：取消过时���请求

```tsx
useEffect(() => {
  const ctrl = new AbortController()
  load(ctrl.signal)
  return () => ctrl.abort()        // 组件卸载时取消在途请求
}, [load])
```

`AbortController` 能做两件事：

1. **组件卸载时**取消请求。不取消的话，请求回来后 `setState` 会打到已卸载的组件上，React 会警告
2. **新请求发出时**取消旧请求。旧请求的响应到了直接丢掉，不碰界面

在 `api.ts` 里把 `signal` 透传给 `fetch`：

```ts
list: (signal?: AbortSignal) => request<Task[]>('/api/tasks', { signal }),
```

## 7. 验证

### 界面接通了

浏览器打开 `http://localhost:5173`，你应该看到：

- 输入框和「添加」按钮
- 第 2 章用 `curl` 建的「买牛奶」出现在列表里
- 勾选能改状态，删除能删掉

### 停掉后端，看 error 状态

**这是验证 error 状态的最直接办法：**

1. 在后端终端按 `Ctrl+C`
2. 刷新页面

应该看到「连不上后端」的错误提示和一个重试按钮，**不是一片空白**。

然后重启后端，点「重试」，数据回来了。

### 制造一次失败，验证回滚

1. 保持后端运行，页面正常
2. 在后端终端按 `Ctrl+C`（后端停了）
3. 在页面上点一下复选框

**预期表现**：复选框先变（乐观更新），然后弹提示并**弹回原来的状态**。

如果它变了但没弹回去，说明备份逻辑没生效。

### 空状态

把数据库清空：

```bash
npm run db:reset
```

重启后端，刷新页面。应该看到「还没有任务。上面加一条试试。」，不是空白。

## 8. 常见误区

::: details 「先请求成功再更新界面不就行了」

可以，代码简单一倍。但网络慢的时候界面有明显的延迟。

**这不是对错问题，是取舍问题。** 本项目选乐观更新，是因为勾选任务的失败率极低（网络断连才会失败），用户能接受偶尔弹回。

表单提交就不能这么干——用户点了「提交」，界面立刻显示「提交成功」，然后弹回「失败」，这是欺骗用户。
:::

::: details 「刷新一下就好了」

刷新能解决**竞态类**的问题（因为重新拉一遍数据），但解决不了：

- **四种状态缺 loading** → 刷新也是白的
- **校验没做** → 刷新后垃圾数据还在
- **数据库没落盘** → 刷新后数据还是没了

遇到问题先定位是哪一类，别用刷新当万能解法。
:::

::: details 「用 alert 提示错误太丑，要做个 Toast 组件」

接口和状态处理对了之后，弹窗换成 Toast 是十分钟的事。

**顺序不能反**：先把「失败了要回滚」这个逻辑写对，再去美化提示。反过来做的话，你会在一个不工作的逻辑上花时间调样式。
:::

## 9. 隐性规则

- **`role="alert"` 要加。** 屏幕阅读器用户听不到普通的视觉错误提示。
- **错误提示要说人话。** 「连不上后端。确认后端已启动、代理已配置。」比「Network Error」有用得多——前者告诉用户下一步做什么。
- **失败后不要吞掉异常。** `handleCreate` 里 catch 之后又 `throw err` 是刻意的：让表单知道这次失败了，不要清空用户已经输入的内容。
- **`optimistic update` 必须在 `api.ts` 之外做。** 收敛到组件里，别让数据层掺和 UI 状态。
- **列表项的 key 用 `id`，不要用数组下标。** 下标会随列表变化，导致 React 复用错误的 DOM 节点。
