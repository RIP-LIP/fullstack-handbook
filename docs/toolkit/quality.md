# 保证它是对的

四个 skill 各管一段，**咬合成一条链**：

```
TDD              →  新代码带着测试来
systematic-debugging  →  出错了，按四阶段查根因
verification-before-completion →  说「好了」之前必须刚跑过验证
code-review      →  查漏，Standards 和 Spec 两条轴分开
```

这四个都有一条「铁律」，而且**都明确说了违反字母就是违反精神**。这一点值得注意——它们不是建议，是硬约束。

## TDD

### 铁律

```
NO PRODUCTION CODE WITHOUT A FAILING TEST FIRST
```

它对这个铁律的注解是整份文档里最重要的一句：

> **如果你没有看着那个测试失败过，你不知道它在测对的东西。**

### 为什么「先写实现再补测试」不行

它的处理方式非常决绝：

> 先写了代码？**删掉，重新开始。** 没有例外：不要留着当「参考」，不要「边写边adapt」，不要「看着它写测试」。**删掉就是删掉。**

理由在「常见借口」那张表里：

| 借口 | 实情 |
| --- | --- |
| 「太简单了不用测」 | 简单代码也会坏。测试花 30 秒 |
| 「我之后再补测试」 | **事后写的测试立刻就过**——这什么都没证明 |
| 「我手动测过了」 | 手动测试是临时的，没有记录，你不会记得覆盖了什么 |
| 「先放着，以后再回来写测试」 | 你不会回来的 |
| 「代码已经写了，删掉太浪费」 | 沉没成本。那段时间已经花掉了 |

它对「事后补测试」的批评最锋利：

> 事后的测试**朝向你已经写好的代码**——你验证的是自己记得的那几个 case，而不是本该发现的那些。有覆盖率，但没有证据表明测试真的有用。

**这就是 TDD 唯一无法妥协的理由：测试的发现能力。** 覆盖率数字是假的，只有「看着它红过」是真的。

### 红-绿-重构

```
RED       写一个失败的测试
   ↓
验证红   确认它失败 ← 强制步骤
   ↓
GREEN     写刚好能通过的最少代码
   ↓
验证绿   确认它通过 ← 强制步骤
   ↓
REFACTOR  清理，保持绿
   ↓
下一个
```

两个「验证」步骤是**强制**的，不是建议。理由：

::: details 「验证红」这一步最容易被跳过，也最重要
它要求你确认三件事：
1. 测试**失败**了，不是**报错**了
2. 失败信息是预期的那个
3. 失败是因为功能缺失，不是因为拼写错误

- **测试直接过了** → 你测的是已有行为，测试写错了
- **测试报错**（不是断言失败）→ 先修错误，重跑到它**正确地失败**为止

**一个「因为 undefined 而报错」的测试，证明不了任何事。** 它只是没跑起来。
:::

### GREEN 要「刚好够」

它给的反例是过度设计：

```ts
// 反例
async function retryOperation<T>(fn, { maxRetries, backoff, onRetry }) { ... }  // YAGNI
```

「别加测试没要求的功能，别重构别的代码，别『顺便改进』。」

### 好测试的判据

| 维度 | 好 | 坏 |
| --- | --- | --- |
| 最小 | 一件事。名字里有「并且」就拆开 | `test('验证邮箱、域名和空白')` |
| 清楚 | 名字描述行为 | `test('test1')` |
| 有意图 | 展示想要的 API | 说明它「大概」该干嘛 |

它给了一条判断测试有没有用的操作性方法：

> **在写之前先说出「哪个生产代码的改动会让这个测试失败」。** 说不出，说明这个测试不测任何东西。

还有一条：**断言真实行为，绝不断言 mock 的行为。** 用 mock 断言，等于在测「mock 被调了」，不是「功能是对的」。

### 什么时候可以破例

它列了三个例外，但条件是**问过你的同伴**：

- 一次性原型
- 生成的代码
- 配置文件

然后立刻加了一句：

> 在想「就破例这一次」吗？停下。那是合理化。

## 排障四阶段

### 铁律

```
NO FIXES WITHOUT ROOT CAUSE INVESTIGATION FIRST
```

没做完第 1 阶段，就不许提修复方案。注解：**症状上的修复就是失败。**

四个阶段和成功标准：

| 阶段 | 做什么 | 成功标准 |
| --- | --- | --- |
| **1 根因调查** | 读错误信息、稳定复现、查最近改动、收集证据 | 理解**是什么**和**为什么** |
| **2 模式分析** | 找同一代码库里能工作的相似实现、完整对比 | 列出工作与不工作的**差异** |
| **3 假设与检验** | 提出**单个**假设，最小化验证 | 确认，或换一个**新**假设 |
| **4 实现** | 先写复现测试，再改一处 | 测试过，其他测试不坏 |

::: tip 第 2 阶段最实用的部分是「完整读参考实现」
> 如果在实现某个模式，**完整**读参考实现。不要略读——读每一行。不完全的理解必然导致改编。

以及那句常被忽略的：**「列每一个差异，无论多小，不要假设『那个不可能有关系』」。**

「那个不可能有关系」是漏掉真凶的头号原因。
:::

### 第 1 阶段：多组件系统要加探针

在 CI → 构建 → 签名，或者 API → 服务 → 数据库这种多层系统里，它的做法是**在每个边界打点，跑一次，然后看证据**：

```bash
# 第 1 层：工作流
echo "=== workflow 里能拿到 secrets 吗：==="
echo "IDENTITY: ${IDENTITY:+SET}${IDENTITY:-UNSET}"

# 第 2 层：构建脚本
env | grep IDENTITY || echo "IDENTITY 不在环境变量里"

# 第 3 层：真正的签名动作
security find-identity -v
```

**一次运行就能定位是哪一层断的。** 这比「改改看」快一个数量级。

### 第 3 阶段：一次只改一个变量

> 提出**单个**假设，写下来。「我认为根因是 X，因为 Y」。**一次改一处。不要一次修多个。**
>
> 没用？**形成新假设。不要在上面的基础上再叠加修复。**

最后半句是关键。**叠加修复会让你无法归因**——好了，但你不知道是哪一个起作用，下次遇到还是得从头猜。

### 最有价值的一条：修到第三次就要质疑架构

> 修了几次？少于 3 次 → 回到第 1 阶段，带着新信息重新分析。**≥ 3 次 → 停下，质疑架构。**
>
> 特征是：每个修复都在不同地方暴露出新的共享状态 / 耦合 / 问题；修复需要「大重构」才能落地；每个修复都在别处产生新症状。
>
> **这时候和人讨论，不要继续尝试第四次修复。**
>
> 这不是「假设错了」，**是架构错了。**

这一条能省掉大量时间。**三次修复都失败，说明你对问题的理解有结构性错误**，继续试第四次只是在加深错误。

### 「找不到根因」的说法基本不成立

> 如果系统调查发现问题是环境、时序或外部导致的：记录调查过程，实现合适的处理（重试、超时、错误信息），加监控。
>
> **但是：95% 的「找不到根因」是没查完。**

「环境问题」是最容易被滥用的借口。

## 验证门禁

### 铁律

```
NO COMPLETION CLAIMS WITHOUT FRESH VERIFICATION EVIDENCE
```

> **如果你没有在这条消息里跑过验证命令，你就不能说它通过。**

「fresh」是重点：**不是上一次跑过就行，是这条消息里跑过。** 对话里之前有一次成功输出，几十轮之后不算数。

### 五步门禁

```
1  IDENTIFY  哪个命令能证明这个说法？
2  RUN       完整地跑一次
3  READ      读完整输出，查退出码，数失败数
4  VERIFY    输出真的支持这个说法吗？
     ├─ 否 → 说明真实状态，附证据
     └─ 是 → 说出说法，附证据
5  说出说法
```

**跳过任何一步就是在撒谎，不是在验证。**

### 说法与所需证据

这张表可以直接当自检：

| 说法 | 需要的证据 | **不够的** |
| --- | --- | --- |
| 测试通过 | 测试命令输出：0 失败 | 上次跑过、「应该会过」 |
| lint 干净 | lint 输出：0 错误 | 部分检查、外推 |
| 构建成功 | 构建命令：exit 0 | lint 过了（lint 不查编译） |
| bug 修好了 | **原始症状**测过了 | 代码改了，假设修好了 |
| 回归测试有效 | 完整红-绿循环 | 跑通一次 |
| Agent 完成了 | **VCS diff** 显示改动 | Agent 报告「成功」 |
| 需求满足了 | 逐条对照清单 | 测试通过 |

两行值得单独看：

::: details 「bug 修好了」
> 需要：测试原始症状，通过。
> 不够：代码改了，假设修好了。

**「我改了代码」和「问题解决了」是两个事件。** 中间必须有一步真的去测了原来出错的那个场景。
:::

::: details 「Agent 完成了」
> 需要：查 VCS diff，验证改动，报告真实状态。
> 不够：相信 Agent 的报告。

**这条直接对应 [拆开并行](/toolkit/parallel)。** 五个 agent 报「成功」，你唯一能信的是 diff——因为 `status: succeeded` 只表示 agent 认为它做完了。
:::

### 回归测试的验证方法

> 写 → 跑（过）→ **撤销修复** → 跑（**必须失败**）→ 恢复 → 跑（过）

中间那三步是它的核心。**一个从没失败过的回归测试，不能证明它能抓住这个 bug。**

### 红旗

它列了几个词，碰到就停下：

- 「应该」「大概」「看起来」
- 表达满意（「好了！」「完美！」）
- 没验证就要提交 / 推送 / 建 PR
- 相信 agent 的成功报告
- 拿部分验证当全部

「我累了」也在红旗列表里，理由是「**疲惫不是借口**」。

## 两条轴审查

`mattpocock-skills:code-review` 的做法是一次审查跑**两条互相独立的轴**。

### 为什么要分两条轴

> 代码可能在一条轴上通过、另一条轴上失败：
> - 遵守了所有规范，但实现的是错的东西 → **Standards 过，Spec 挂**
> - 完整实现了 issue 要求，但破坏了项目约定 → **Spec 过，Standards 挂**
>
> 分开报是为了防止一条轴掩盖另一条。

这是它整份设计里最值得抄的一点。**一个综合评分一定会掩盖「规范满分但做错事」这种情况。**

它还有一条配套规定：**不要合并、不要跨轴重排两份报告。** 最后只给一句总结：每条轴各几条发现，各自最严重的那个是什么。**不要跨轴挑出一个总冠军**——那正是分轴要防的事。

### 固定点用三点 diff

```bash
git diff <fixed-point>...HEAD     # 三点，比的是 merge-base
git log <fixed-point>..HEAD --oneline
```

**先确认固定点能解析、diff 非空**，再派 agent。坏 ref 或空 diff 应该在这一步就失败，**而不是在两个并行 agent 里面才炸**。

### 规范来源的两层

1. 仓库自己文档化的规范（`CODING_STANDARDS.md`、`CONTRIBUTING.md`）
2. **Fowler 坏味道基线**（代码重构第 3 章）——**即使仓库什么都没写，这份基线也生效**

两条绑定规则：

::: details 「仓库优先」和「永远只是判断题」
> **仓库优先。** 文档化的仓库规范总是赢；它认可的东西即使基线会标记，也要压掉。
>
> **永远是判断题。** 每条坏味道都是带标签的启发式（「疑似 Feature Envy」），**绝不是硬性违规**。

第一条防的是「照着通用规范去改仓库里有意为之的写法」。第二条防的是**把风格偏好说成错误**。

写报告时的措辞区别是：文档化规范的违反可以是 hard，而基线坏味道**永远是判断题**。工具已经强制的东西一律跳过（lint 管的不用 review 再管一遍）。
:::

### 12 条坏味道基线

每条都是「**是什么** → **怎么改**」：

| 坏味道 | 是什么 | 怎么改 |
| --- | --- | --- |
| **神秘的名字** | 名字没揭示它做什么或存什么 | 改名；起不出诚实的名字，说明设计本身糊 |
| **重复代码** | 同一段逻辑形状出现在多处 | 抽出来，两边都调它 |
| **依恋情结** | 方法访问别的对象的数据多于自己的 | 把方法搬到它依恋的数据上 |
| **数据泥团** | 同样几个字段总是一起出现 | 打包成一个类型 |
| **基本类型偏执** | 用原始类型或字符串代替本该有自己类型的领域概念 | 给这个概念一个自己的小类型 |
| **重复的 switch** | 同一个类型上的 `switch` / `if` 级联反复出现 | 换多态，或抽一个两处共享的映射表 |
| **霰弹式修改** | 一个逻辑变更要改很多文件 | 把一起变的东西聚到一个模块 |
| **发散式变化** | 一个文件因为好几个不相关的原因被改 | 拆开，让每个模块只因一个原因变 |
| **夸夸其谈的通用性** | 为 spec 里没有的需求做的抽象、参数、钩子 | 删掉；内联回去，等真需求出现 |
| **消息链** | 调用方不该依赖的长串 `a.b().c().d()` | 藏在第一个对象的一个方法后面 |
| **中间人** | 一个类/函数大部分工作只是转发 | 砍掉，直接调真正的目标 |
| **被拒绝的遗赠** | 子类忽略或覆盖了大部分继承来的东西 | 去掉继承，用组合 |

::: tip 两条最值得贴在显示器上的
**发散式修改**和**霰弹式修改**是一对，方向相反：一个是「一个文件被太多原因改」，一个是「一次变更散到太多文件」。**两个都出现，说明模块边界划错了**，不是代码写得丑。
:::

### 两个轴各查什么

**Standards 轴**（发给 agent 的指令要点）：逐文件/逐块报告 (a) 所有违反文档化规范的地方——**要引用规范（文件 + 具体规则）**；(b) 发现的基线坏味道——**命名并引用代码块**。区分 hard violation 和判断题，仓库规范压过基线。跳过工具已强制的。**限 400 字。**

**Spec 轴**：(a) spec 要求了但缺失或只做了一半的；(b) diff 里**没被要求**的（scope creep）；(c) 看起来实现了但**实现方式可能不对**的。**每条都要引用 spec 的原文行**。限 400 字。

「引用原文」这条是关键——**没有引用就无法核对，review 就变成了信任问题。**

## 一起用

### 什么时候用哪个

| 情况 | 用 |
| --- | --- |
| 要写新功能 | [TDD](#tdd) |
| 已经能跑了，测也写了 | [验证门禁](#验证门禁) |
| 测试挂了 / 线上出问题 | [排障四阶段](#排障四阶段) |
| 要合并 / 建 PR | [两条轴审查](#两条轴审查) |
| 审查发现新 bug | 回到 TDD，**先写复现测试** |

最后一行是链条闭合的地方：`systematic-debugging` 第 4 步明确要求「先写复现测试」，用的是 TDD 那套。**修 bug 也在 TDD 循环里。**

### 和 [实现功能](/toolkit/build) 一起

`engineering-workflow` 的第 5、6 步分别对应这页的**验证门禁**和**两条轴审查**。

但有个顺序问题容易搞错：**TDD 在第 4 步（实现）之前就开始，不是第 5 步之后补。**

把 TDD 理解成「验证的一种」就会搞错时机——**它的作用是让实现阶段的代码自带测试，事后补是另一回事**（见上面「事后补测试」那条）。

### 什么时候不该用

::: details 「我这个项目一个测试都没有」
TDD 确实不适用于**你还没建立测试基础设施**的项目，直接上会让你先花一周搭环境。

务实做法：**先给最关键的那条路径补测试**（比如「非法输入必须被拒」），让它有回归保护，然后再逐步铺开。**从一条开始，不要先搭框架。**
:::

::: details 「一次性脚本 / 生成的代码 / 配置文件」
这三种是 TDD 明确列出的例外——但条件是**问过同伴**，不是自己决定。而且原型也要删，不是留着用。
:::

::: details 「审查就报 bug 吧，别给我两个轴」
两轴分开是刻意的设计。综合报告会掩盖「规范满分但做错事」。

你当然可以只看其中一条轴，但**别把它们混成一句总分**。
:::

## 跑完之后

你应该能回答三个问题：

- 我这次说「好了」，是哪条命令证明的？**在什么时候跑的？**
- 如果它坏了，**我能不能只靠测试重现出来**？
- 这次改动有没有超出 spec 要求？

第三个问题的答案如果是「有」，那不是缺陷发现了，是**范围蔓延**——两条轴审查专门有一项查这个。
