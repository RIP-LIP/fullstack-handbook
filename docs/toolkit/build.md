# 实现功能

四个 skill：**`ai-coder`** 是通才，**`engineering-workflow`** 是主流程，`fullstack-dev` 和 `frontend-dev` 是主流程路由进来的专项。

## 该选哪个

| 你的处境 | 选 |
| --- | --- |
| 需求自己都还没说清 | [ai-coder](#ai-coder) |
| 需求清楚，有仓库，知道要改哪些文件 | [engineering-workflow](#engineering-workflow) |
| 改动跨接口 / 数据库 / 鉴权 | `fullstack-dev` |
| 改动在界面：响应式、可访问性、交互状态、动效 | `frontend-dev` |

不确定就用 `engineering-workflow`——它会自己路由。

## ai-coder

它是**通才型**的：需求分析、方案设计、代码实现、代码审查、UI/UX 五块打包。

### 它的六步

```
需求澄清 → 方案设计 → 代码实现 → 代码审查 → UI/UX 设计 → 验证与交付
```

### 它真正的特点：先问

第 1 步是**需求澄清**，而且它用了「引导式提问」这个具体手法：

> 主动引导用户明确业务场景、技术栈偏好、性能要求、安全约束、部署环境等关键信息；当需求模糊时，通过引导式提问明确细节。

举的例子是「你需要适配的数据库是 MySQL 还是 PostgreSQL？」——**不是让对方写需求文档，是挑真正会改变实现的那一两个点问。**

这是它和 `engineering-workflow` 最大的区别：

| | `ai-coder` | `engineering-workflow` |
| --- | --- | --- |
| 起点 | **问用户要什么** | **读仓库已经有了什么** |
| 问什么 | 需求、技术栈、性能、安全 | 只问「会实质改变实现」的决定 |
| 适合 | 还没动手，探索阶段 | 已经在 codebase 里 |

::: tip 什么时候该用 ai-coder
**你还没想清楚要什么的时候。** 一旦需求定了、仓库也在手上，`engineering-workflow` 更准——它从代码里推断约定，比问出来的主观偏好更接近这个项目的真实规矩。
:::

### 方案设计：要多方案对比

它要求「针对复杂需求提供**多方案对比**，说明各方案优缺点与适用场景」，举的方向是单体 / 微服务、SQL / NoSQL、同步 / 异步。

关键在「适用场景」这三个字。**只给一个方案不算方案设计**，因为读者没法判断你是权衡过还是只想到了一个。

### 代码审查：带风险等级

它的审查分五个维度：代码质量、性能优化、安全风险、架构合理性、最佳实践。

输出规范是「分模块列出**问题点、风险等级、优化建议**，附修正后的代码示例」，并且「对关键问题（安全漏洞、严重性能问题）标注优先级，说明影响范围与修复方案」。

**风险等级是这个 skill 的特色。** 没有分级的话，一份列了 20 条意见的审查报告里，「SQL 注入」和「变量名不好」会平级，读者不知道先修哪个。

### 它的输出质量要求

> 所有输出内容需经过验证（代码可运行、方案可落地、设计符合规范）

这句话是**它自己的要求，不是保证**。见 [验证门禁](/toolkit/quality#验证门禁) 那一节怎么落实。

## engineering-workflow

它是**主流程**，七步固定顺序：

```
1  建立仓库契约    读现有的东西，不先设计方案
2  按需路由专项    该转给前端专项 / 跨层专项时才转
3  按比例做计划    多步任务用可见的待办列表
4  增量实现        复用已有库和模式，不做无关重构
5  在受影响面验证  ← 重点，下面单独讲
6  Code Review     只看本次 diff 和必要的调用方
7  诚实交付        说什么改了、验了什么、没验什么
```

### 第 1 步是「先读，后想」

措辞很硬：**在选方案之前先建立仓库契约。**

要读的：项目里的指令文件（`AGENTS.md` 之类）、`package.json`、邻近的同类实现、import 关系、测试、当前 git 状态。

从这些里**推断**技术栈、约定和验收标准。只在「某个决定会实质改变实现」时才问人。

::: tip 这一步省掉会怎样
你会写出「和这个项目别处不一样」的代码。不是错，是**漂移**。

项目已经用 `node:sqlite` 了，你新写一个 `better-sqlite3`；项目所有错误都走 `{ error: { code, message } }`，你新加一种 `{"msg": "..."}`。都能跑，但三个月后没人知道该跟哪种写法。
:::

### 第 2 步的判断是「要不要转」

| 情况 | 转给 |
| --- | --- |
| 实质的 UI 架构、响应式、可访问性、动效、设计系统、视觉资源 | `frontend-dev` |
| 跨层功能：接口、鉴权、数据库、事务、缓存、队列、上传、实时、生产加固 | `fullstack-dev` |

但它同时说了两句更重要的话：

- **不要重复加载已经加载过的专项 skill。**
- **专项做完回到第 5 步**，不要因为已经转出去就跳过验证和 Review。

::: danger 最容易犯的错
「这个任务很大，所以我转到专项 skill 去了。」

专项 skill 是**补充**，不是**替代**。它做完代码就结束了，第 5 步验证和第 6 步 Review 还在主流程上。少了这两步，你得到的只是一份没验过的代码。
:::

它还有一条兜底：**小而明显的改动直接做，不要加流程。** 改一个错别字、给一个函数加个参数，这种事套一遍七步是浪费。

### 第 3 步是「按比例」

- 多步工作用**可见的待办列表**，且**同一时刻只有一个是进行中**
- 用户要求先看计划时，**停在「方案 + 验证计划」这里**等确认；没要求就继续做，别自己加一道审批门

「按比例」这三个字是重点。它不要求所有任务都写计划，**改一个 CSS 变量不需要计划**。

### 第 7 步是「诚实交付」

要求可以抄下来当自己的交付清单：

- 改了什么
- 验了什么
- **什么没跑**
- 还剩什么风险

禁止项里最有用的一条：**本地预览服务交付后不要等它退出**，也别因为它还活着就把回合挂着。停预览服务之前，**先说明那个 URL 会失效**。

## 专项：fullstack-dev

跨层功能的八步里，有三条特别值得记住。

### 第 2 步：先定契约，再写实现

它要求在动手之前明确：请求/响应形状、校验、**鉴权、授权、错误语义、幂等性、分页、兼容性要求**，然后决定**「哪份数据是权威的，哪一层拥有哪个状态转移」**。

最后半句是它最值钱的地方：

> Decide where data is authoritative and which layer owns each state transition.

**「状态归谁」这个问题不定下来，后面的代码一定打架。** 「前端能不能改这个字段」「这个值以谁为准」——这些问题在写代码前回答，和写完之后发现，代价差十倍。

### 第 3 步：数据改动要可逆

> Prefer additive, reversible migrations and explicit transaction boundaries.

**additive（只加不改）** 是默认值。现存表的字段尽量加，不要改、不要删——因为所有还在跑的旧版本代码都在读这张表。

同时要想到：唯一性、索引、并发、保留期、**回填、回滚、部分失败**。

「部分失败」最容易漏：回填脚本跑到一半崩了，已经回填的行和没回填的行状态不同，这时候怎么继续？

### 第 4 步：按比例选架构

它明确反对一刀切：

> 保留仓库已有的结构；**不要把 controller/service/repository、feature-first、微服务或别的模式强加到每个 codebase 上。** 只有当新边界能减少具体耦合、厘清归属或保护契约时，才引入它。

这是一条容易被忽略但很实用的判断：**新边界不是免费的**。每加一层，读者就多一跳。

## 专项：frontend-dev

和视觉相关的部分在 [界面设计](/toolkit/design#frontend-dev-的第-3-步) 讲过了。这里是另外三条。

### 实现要切成小片

> 分成小片、可测试的片。把数据获取、状态归属、校验和错误渲染保持显式。**现有组件够用就不要加依赖。**

最后半句针对的是「顺手升级一下 UI 库」的冲动。**现有依赖够用时引入新依赖，收益是零，代价是锁文件变动、迁移风险、和别人项目的分叉。**

### 验证：先定最小清单

> Browser 验证之前，**先定义适用的最小检查清单。不要因为「还能多查点」就往上加场景。**

这条和「加第七个颜色」是同一种自律。**验证清单和设计 token 一样，有默认长度膨胀的倾向。**

### 验证：写路径要看结果

> 对于 CRUD 产品，**走一遍主要的写路径并检查可观察到的保存结果**，而不是只看静态页面。

页面能打开不代表数据存进去了。这个区分和主线的「curl 先确认后端活着」是同一条。

## 交出去

实现做完到能给别人看，中间有几件事。这一段的坑是**实跑踩出来的**，不是从哪个 skill 抄的。

### 本地预览不要用阻塞方式起

长驻服务如果用「等它结束」的方式启动，那个回合会一直挂着。正确做法是**分离进程 + 写日志 + 有界的就绪检查**（最多 30 秒），确认起来了就往下走。

端口冲突时换端口重试**一次**，不要去杀别的会话的进程。

### 推 GitHub 前先确认凭据是哪一套

`gh auth status` 会同时显示两行：一行是环境变量里的 token，一行是 keyring 里的。**active 的那行才决定能不能建仓。**

真实踩过的坑：环境变量里放的是 fine-grained PAT，**它没有「创建仓库」这个权限项**，换一个新令牌也解决不了——这是这类令牌的固有限制，不是配置问题。

```powershell
# 切到 keyring 里的 OAuth 令牌
$env:GH_TOKEN = $null; $env:GITHUB_TOKEN = $null
gh auth status
```

注意这个清空只对当前 PowerShell 进程有效，新开窗口会变回去。

### 代理要配到 repo 级

`git` 和 `gh` 都**不读 Windows 系统代理**（`PowerShell` 的 `Invoke-WebRequest` 会读，所以「PowerShell 能连」不能证明 git 能连）。

```bash
git config http.proxy http://127.0.0.1:7897
```

**用 repo 级，不带 `--global`**——代理没开的时候不会让其他项目全挂。

地址要从注册表读：

```powershell
(Get-ItemProperty 'HKCU:\Software\Microsoft\Windows\CurrentVersion\Internet Settings').ProxyServer
```

### PowerShell 会吃掉引号

```powershell
# 不行：双引号被吃掉，发过去的是 {title:x}
curl -X POST http://localhost:3001/api/tasks -d '{"title":"买牛奶"}'

# 行：写成文件再发
curl -X POST http://localhost:3001/api/tasks --data-binary "@body.json"
```

这条同时是分不清「PowerShell 问题」和「服务端 500」的元凶——见 [请求体不是合法 JSON](/guide/ch02#_7-常见误区)。

## 一起用

### 和 [界面设计](/toolkit/design) 一起

第一页定的 token 应该在**第 1 步就被读进来**，不是贴在墙上。

做法：token 落成 `tokens.css` 或设计文档，第 1 步的「读指令文件」自然就会读到它，改动自动对齐。

反过来，第 6 步的 Review 需要一条可判定的标准。**设计产出不落成文件，审查就只剩「不太好看」这种不可验证的意见。**

### 和 [保证它是对的](/toolkit/quality) 一起

它是**质量那一组的编排者**。第 5 步和第 6 步分别对应 [验证门禁](/toolkit/quality#验证门禁) 和 [两条轴审查](/toolkit/quality#两条轴审查)。

而 [TDD](/toolkit/quality#tdd) 应该在**第 4 步之前**就开始，不是第 5 步之后补。

### 和 [拆开并行](/toolkit/parallel) 一起

它是**准入判断**：

| 情况 | 走哪条路 |
| --- | --- |
| 一个会话能做完 | 走这个 skill 的七步，不要开编排 |
| 一个会话做不完，但改动高度耦合 | 拆分阶段，**串行**做，每阶段各自走一遍七步 |
| 改动互相独立，能同时进行 | 才是编排的适用场景 |

「独立」才是编排的**前提**，「量大」只是时机。

### 什么时候不该用

::: details 「我就是想让你解释一段代码」
`engineering-workflow` 的 description 明确排除了这种情况：微小的改动、纯解释、只做 code review、非编码工作。直接问就行。
:::

::: details 「它让我写的计划太啰嗦了」
第 3 步说的是「按比例」。小任务可以不写计划——但那是**你的判断**，不是默认。

你觉得它过度，直接说「这个改动很小，直接做不用出计划」。反过来，跨三层以上的改动主动要求计划，是划算的。
:::

## 跑完之后

你应该养成一个习惯：**说清楚「验了什么」和「没验什么」。**

这个习惯到了下一层会变得非常值钱——当你面对五六个同时在改的任务时，「哪个 Agent 真的验过了」是唯一能让你判断能不能合并的依据。
