# 工具怎么选

这一节讲本地装的十几个 skill 和插件：**各自管什么、什么时候该叫它、怎么组合**。

先说清楚一件事：这些**不是「AI 帮你写代码」的档位**，也不是互相替代的关系。它们按职能分成五类——

| 这一类 | 回答的问题 | 什么时候你会真的需要 |
| --- | --- | --- |
| [界面设计](/toolkit/design) | 这个界面应该长什么样 | 项目第一次有界面的时候 |
| [实现功能](/toolkit/build) | 具体这个功能怎么落地 | 你知道要做什么，但还没写 |
| [保证它是对的](/toolkit/quality) | 怎么确认没弄坏、出了错怎么查 | 改动开始互相干扰的时候 |
| [拆开并行](/toolkit/parallel) | 活多到一次会话干不完 | 单个会话开始反复跑满的时候 |
| [交出去](/toolkit/build#交出去) | 怎么提交、合并、发版 | 准备给别人看的时候 |

## 完整清单

按职能列，不按插件名。**同一个职能下的几个是互相替代或补充关系，按场景挑一个。**

### 界面设计

| skill | 类型 | 什么时候用 |
| --- | --- | --- |
| `frontend-design` | 纯推理，不调工具 | 定视觉方向。写代码前先定 token，自查有没有落进 AI 默认 |
| `superdesign` | 外部服务 + 画布 | 要出**视觉稿**给人看、或从一个真实网站借鉴风格。数据会出境到第三方 |
| `senior-fullstack-developer:frontend-dev` | 流程型 | 功能里的视觉部分要落地实现时，从主流程路由进来 |

三者的关键差别在第一行：`frontend-design` 什么都不产出，只产出判断；`superdesign` 产出可点可评论的画布；`frontend-dev` 产出代码。

### 实现功能

| skill | 类型 | 什么时候用 |
| --- | --- | --- |
| `ai-coder` | 全流程通才 | 需求还不清楚、或者一次要跨前后端 + 设计 + 审查 |
| `senior-fullstack-developer:engineering-workflow` | 主流程 | **默认选它**。有仓库契约、按比例做计划、增量实现、验证、Code Review、诚实交付 |
| `senior-fullstack-developer:fullstack-dev` | 专项 | 跨层功能：接口、鉴权、数据库、事务、缓存、队列、上传、实时 |
| `senior-fullstack-developer:frontend-dev` | 专项 | 界面部分：响应式、可访问性、交互状态、动效 |

后两个是 `engineering-workflow` 的**下游**，由它路由进来。直接单独叫也行，但会跳过验证和 Review。

### 保证它是对的

| skill | 铁律 |
| --- | --- |
| `superpowers:test-driven-development` | 没看着测试失败过，就不知道它在测什么 |
| `superpowers:systematic-debugging` | 没过根因调查不许提修复方案 |
| `superpowers:verification-before-completion` | 这条消息里没跑过验证命令，就不许说「好了」 |
| `mattpocock-skills:code-review` | 一次审查跑两条轴：Standards 和 Spec，分开报不合流 |
| `ai-coder`（审查部分） | 五个维度 + 风险等级分级 |
| `engineering-workflow`（第 6 步） | 看完 diff 再看一遍，只看必要的调用方 |

这一组是**互相咬合**的：TDD 保证新代码有测试，systematic-debugging 负责修，verification 负责别撒谎，code-review 负责查漏。见 [这一页](/toolkit/quality)。

### 拆开并行

| skill | 适用规模 | 特点 |
| --- | --- | --- |
| 自己写 todo 列表 | 2–5 步 | 最轻。默认选这个 |
| `superpowers:writing-plans` | 需要多人/多轮执行的计划 | 先出计划再执行 |
| `superpowers:subagent-driven-development` | 一个任务能切成几个独立子任务 | 用子 agent 逐个实现 |
| `superpowers:dispatching-parallel-agents` | 子任务之间**无依赖** | 真并行 |
| `mcode-dynamic-workflows` | 大批量、要预算和面板 | 可执行编排，有依赖图、并发上限、可中断恢复 |

::: tip 90% 的情况不需要最后两个
**「活多」和「该并行」是两件事。** 并行的前提是改动之间没有交集。

最后两个都要付出编排成本：写描述、审拓扑、盯结果、处理失败、合并。一个会话做得完的事，顺序做更快也更干净。
:::

## 为什么按这个顺序读

不按功能重要性排，按**你第一次会需要它的时刻**排。三个理由：

**1. 引入成本是递增的。** 「界面设计」的成本是几个变量和几条 CSS 规则，改错了立刻能看出来。「实现功能」的成本是你要接受「先读仓库再动手、按比例做计划」这个节奏，慢一点但返工少。质量那一组是纪律，成本是你要忍住不跳步。「并行」的成本是编排逻辑本身——怎么切任务、怎么传依赖、怎么判断某个 agent 到底有没有干对。

**2. 前一个不学会，后一个学了也用不对。** 不定设计方向就去定工程契约，契约里写出来的视觉规范就是空的。不建立验收习惯就去开多个 agent，五个并行出错你连从哪查起都不知道。

**3. 触发时机天然是递进的。** 顺着主线走，你的状态是这样变的：

```
项目启动  →  界面是「ok」两个字，没有设计问题
数据存储  →  接口通了，界面还是「ok」
前端交互  →  界面有四种状态了    ← 这里开始需要「界面设计」
   ↓
界面能用了 →  加功能、接收别人的改动，一个改崩三个  ← 这里需要「实现流程」和「质量」
   ↓
功能变多   →  后端、共享包、部署配置一起改，一个会话装不下  ← 这里才需要「并行」
```

**在「前端交互」之前引入任何一个都是浪费。** 那一章的界面是一句「ok」，谈设计方向没有对象；那时候的改动量也谈不上互相打架。

每篇的最后一节是「什么时候别用」，赶时间可以直接跳到那里。

## 三个共同限制

说在前面，省得你抱太高期待：

- **它们不替你验证。** 都能生成看起来合理的代码，但「看起来合理」和「跑得通」是两件事。所以每篇给的判据都是**你自己跑一遍、看和你预期的差多少**——差得多说明 skill 给的方案和你的项目不匹配，这时候该信你看到的。
- **它们不知道你的项目。** 没有你的代码库和需求，给出的是通用解，不一定合你的规模。
- **它们不是必需品。** 手写也能做完同样的事。你就想手动改三个文件，装一堆 skill 反而是负担。

## 从哪开始

| 你的情况 | 从这里进 |
| --- | --- |
| 主线还没走完 | 回去做 [前端交互](/guide/ch03) |
| 界面能用，想让它不那么难看 | [界面设计](/toolkit/design) |
| 需求不清楚，不知道从哪下手 | [实现功能 › ai-coder](/toolkit/build#ai-coder) |
| 有仓库了，按什么流程改 | [实现功能 › engineering-workflow](/toolkit/build#engineering-workflow) |
| 改一个地方崩三个地方 | [保证它是对的](/toolkit/quality) |
| 报错了，不知道该查哪 | [排障四阶段](/toolkit/quality#排障四阶段) |
| 改完了不敢说「好了」 | [验证门禁](/toolkit/quality#验证门禁) |
| 项目超过十个文件，改不动了 | [拆开并行](/toolkit/parallel) |
| 只想看一个完整项目 | [完整项目](/practice/index) |
