# 三个工具怎么分工

这一节讲三个本地插件：怎么用、各自管什么、**为什么按这个顺序读**。

先说清楚一件事：这三个不是「AI 帮你写代码」的三个档位，也不是互相替代的关系。它们管的是三件完全不同的东西——

- 决定**长什么样**
- 决定**怎么改才不塌**
- 决定**活多到一个人干不完时怎么拆**

## 三个工具

| 插件 | 回答的问题 | 什么时候你会真的需要它 |
| --- | --- | --- |
| [界面设计](/toolkit/design) | 这个界面应该长什么样 | 项目第一次有界面的时候 |
| [工程流程](/toolkit/workflow) | 改动怎么组织、怎么确认没弄坏别的 | 界面能用了，改动开始互相打架的时候 |
| [多 Agent 编排](/toolkit/agents) | 活多到一次会话干不完怎么办 | 单个会话开始反复跑满、上下文不够用的时候 |

## 为什么是这个顺序

不按「功能重要性」排，按**你第一次会需要它的时刻**排。三个理由：

**1. 引入成本是递增的。** 「界面设计」的成本是几个变量和几条 CSS 规则，改错了立刻能看出来。「工程流程」的成本是你要接受「先写计划再动手」这个节奏，慢一点但返工少。「多 Agent 编排」的成本是编排逻辑本身——你要想清楚怎么切任务、怎么传依赖、怎么判断某个 Agent 到底有没有干对。前两个是加法，第三个是另一件事。

**2. 前一个不学会，后一个学了也用不对。** 不定设计方向就去定工程契约，契约里写出来的视觉规范就是空的（那正是本站早期版本的毛病）。不建立验收习惯就去开多个 Agent，五个 Agent 并行出错，你连从哪查起都不知道。

**3. 触发时机天然是递进的。** 顺着主线三章走，你的状态是这样变的：

```
项目启动  →  界面是「ok」两个字，没有设计问题
数据存储  →  接口通了，界面还是「ok」
前端交互  →  界面有四种状态了    ← 这里开始需要「界面设计」
   ↓
界面能用了 →  接下来加功能、改样式，牵一发动全身  ← 这里需要「工程流程」
   ↓
功能变多   →  后端、共享包、部署配置一起改，一个会话装不下  ← 这里才需要「多 Agent」
```

**在「前端交互」之前引入任何一个都是浪费。** 那一章的界面是一句「ok」，谈设计方向没有对象；那时候的改动量也谈不上互相打架。

## 每篇的结构一样

三篇都按同样的四段写，方便横向对比：

| 段 | 讲什么 |
| --- | --- |
| **它是什么** | 机制层面它怎么工作，不是它能做什么 |
| **想清楚什么** | 这个工具在背后替你做的那个判断，以及为什么值得听它的 |
| **怎么用** | 可以直接复制的调用形式和参数 |
| **一起用** | 和前后两篇的组合方式，以及**什么时候不该一起用** |

第四段是这三篇的重点。三个工具各自都能独立用，但**组合起来才解决真实的协作问题**——这也是为什么它们要按这个顺序出现。

## 三个工具共同的限制

说在前面，省得你抱太高期待：

- **它们不会替你验证。** 三个都能生成看起来合理的代码，但没有验证步骤的工具链，产出的「看起来合理」和「跑得通」是两件事。本站每个示例都实跑过，这是底线。
- **它们不知道你的项目。** 没有你的代码库和需求，它们给出的方案是通用解，不一定适合你的规模。
- **它们不是必需品。** 手写也能做完同样的事。如果你就是想手动改三个文件，装三个插件反而是负担。

## 从哪开始

| 你的情况 | 从这里进 |
| --- | --- |
| 主线还没走完 | 先回去把 [前端交互](/guide/ch03) 做完 |
| 界面能用，想让它不那么难看 | [界面设计](/toolkit/design) |
| 改一个地方崩三个地方 | [工程流程](/toolkit/workflow) |
| 项目超过十个文件，改不动了 | [多 Agent 编排](/toolkit/agents) |
| 只想看一个完整项目 | [完整项目](/practice/index) |
