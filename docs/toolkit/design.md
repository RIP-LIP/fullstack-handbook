# 界面设计

三个 skill 分管一件事的三个阶段：`frontend-design` 产出判断，`superdesign` 产出稿子，`frontend-dev` 的第 3 步产出代码。

先把最容易搞混的一点说清楚：

| | 产出什么 | 是不是外部服务 |
| --- | --- | :-: |
| `frontend-design` | **只有判断**。定 token、定方向、定底线 | 否 |
| `superdesign` | 可点、可评论的**视觉稿** | **是**，数据会出境 |
| `frontend-dev` 第 3 步 | 真正落地的 CSS | 否 |

**先用 `frontend-design` 想清楚，再用 `superdesign` 出稿，最后用 `frontend-dev` 落代码。** 顺序反了就是返工。

## frontend-design

它不是 UI 库，也不产出组件。它是一份**决策顺序**：在你动手写 CSS 之前，先把「长什么样」想清楚。

### 想清楚什么

**核心动作是：在脑子里先定一套 token，再写代码。**

顺序反了会怎样——先写代码再补样式，你会得到一堆各自为政的 `#3b82f6`、三种圆角、两种间距。功能是对的，但没人愿意看第二眼。而且后期极难改，因为每一个内边距都被写死在了几十个地方。

它要你在写代码之前就有答案的四样东西：

| | 具体是什么 |
| --- | --- |
| **颜色** | 4–6 个命名色值，每个都要能说出它编码的是什么 |
| **字体** | 至少两个角色：标题一个、正文一个，必要时再一个给数据和标注 |
| **布局** | 一句话描述的概念，配 ASCII 线框 |
| **签名元素** | 整站唯一一个「被记住」的东西 |

#### AI 默认长相

它的第一条警告是：当下的 AI 生成设计会往三个样子上靠——

1. 暖奶油底（约 `#F4F1EA`）+ 高对比衬线标题 + 陶土色点缀
2. 近黑底 + 单一荧光绿或朱红点缀
3. 报纸版式：发丝分隔线、零圆角、密集分栏

这三种都不是错的，但它们**跟主题无关**。你做一个记账应用和一个做温度记录的工具，出来的东西长得一样——因为它们是默认值，不是选择。

它的说法很克制：需求指定了视觉方向就照做；**需求没指定的那部分自由度，不要花在这三种默认上。**

::: tip 一个判据
把配色和布局的描述念一遍，如果这句话同样能用在「咖啡店网站」和「医疗器械后台」上，那它就是默认值。
:::

#### 只在一个地方花力气

它明确说「把你的大胆用在一处」。签名元素之外的区域要安静、克制。

理由是注意力：你只有一个 memorable moment，多了就互相抵消，全都不 memorable。它借了 Chanel 的一句话做自查方法——**出门前照镜子，摘掉一件配饰。**

这和「多加几个动效」是反的。动效散在各处不会更强，只会让页面显得像生成的。

#### 结构要编码真实信息

编号、eyebrow 小标签、分隔线、栏标题——这些结构元素必须**表达关于内容的某个真实事实**，不能只是装饰。

它举的反例是 `01 / 02 / 03`：只有当内容真的是有顺序的（一个真实的过程、一条有先后的时间线）才配用，否则它就是装饰。

这条对文档站尤其重要，站点里到处是编号，编错一个就是在骗读者。

#### 文案是设计材料

这一条最容易被当成「设计不负责的事」。它的判断相反：界面上的词只有一个存在理由——让人看懂、进而用得动，所以它跟颜色和间距是同一层级的东西。

| 规则 | 例子 |
| --- | --- |
| 用用户的词，不用系统结构的词 | 「管理通知」而不是「配置 webhook」 |
| 主动语态，控件说清楚会发生什么 | 「保存修改」而不是「提交」 |
| 同一个动作全程同一个名字 | 按钮叫「发布」，toast 就得是「已发布」 |
| 报错不道歉、不含糊 | 「连不上后端。先确认后端已启动。」而不是「出错了，请稍后重试」 |
| 空状态是邀请，不是道歉 | 「还没有书签。上面加一条试试。」 |

界面词表就是一个人在产品里认路的路标。**今天叫「删除」明天叫「移除」，用户就得多花一次力气。**

### 怎么用

方法是**两遍**。

**第一遍：定 token，不写代码。**

```
颜色   --paper  #FAFAF8   纸面，全站底色
       --ink    #14161A   正文和标题
       --line   #E3E3DF   分隔线
       --wire   #2B5FD9   「发出去的东西」：链接、主按钮
       --fail   #B42318   出错
       --signal #B45309   需要注意但不是错误

字体   标题  系统无衬线
       正文  系统无衬线
       数据  ui-monospace

布局   单栏，正文限宽约 46rem
       代码块和响应左右对照

签名   ::: request 容器
       左边命令，右边真实响应，中间竖线用响应自己的语义色
```

**第二遍：自查，再写。**

逐条问：**哪一项换成任何别的项目也成立？** 成立的就是默认值，改掉它，并说清改成了什么、为什么。

这一站的第一轮和第二轮确实改了三处，你可以照这个思路自查：

| 第一遍写的 | 改成 | 为什么 |
| --- | --- | --- |
| 标题用等宽字体 | 标题用系统无衬线 | **中文没有等宽字形**。写 `font-family: monospace` 之后，中文标题会掉回衬线体，实际渲染出来是「衬线标题 + 等宽英文」的双重字体，比一开始就全用衬线更难看 |
| 每个状态一个颜色（成功绿、失败红、警告黄、进行中蓝） | 颜色**只按 HTTP 状态码分配**，`2xx` 绿 `4xx` 橙 `5xx` 红 | 颜色必须编码真实含义。为了好看再加第七个色，后面没人记得它代表什么 |
| 首屏放三个数字（章节数 / 代码行数 / 练习数） | 首屏只放标题 | 数字被从它证明的那件事里抽出来，就和所指之物脱钩了。数字应该留在它出现的上下文里（正文写「22 板块 · 104+ 章节」），不该在首屏单独立一个焦点 |

**第二遍没通过的项是必须改的，不是可选优化。**

### 克制的底线

不管方向多大胆，这三条不能破：

- **响应式**到手机宽度
- **键盘焦点看得见**（`:focus-visible`，别写 `outline: none` 了事）
- **尊重 `prefers-reduced-motion`**——用户系统里关了动效，你的动效就得跟着关

::: details 为什么第二条经常被忽略
视觉方向做得很满的页面，恰恰容易在这三处偷懒，因为它们不在截图里显眼。但这三样是**给不用鼠标的人和看不清的人准备的**，跟设计好不好看没关系，是底线不是加分项。
:::

### 签名元素怎么落地

这个站的签名元素是 `::: request` 容器，左边命令右边真实响应：

````markdown
::: request
```bash
curl -i http://localhost:3001/api/health
```

```http
HTTP/1.1 200 OK

{"ok":true,"service":"api"}
```
:::
````

关键不在容器本身，在**中间那条竖线的颜色就是这份响应的真实状态色**。写错状态码，竖线就变红——错误自己会指出来。

::: danger 动 CSS 的时候别改 shiki 的内部结构
高亮库会给每行加 `.line`，带 `display: block; width: 100%`。改这两个属性会让它后面的所有内容错位。长代码行的正确做法是容器上加 `overflow-x: auto` 横向滚动，别去动它生成的行。
:::

## superdesign

它是**工具型**的：跑一个 CLI，产物落在无限画布上，你可以点开看、留反馈。

### 和 frontend-design 的根本差别

| | frontend-design | superdesign |
| --- | --- | --- |
| 产物 | 一套 token 和一句理由 | 一张可交互的稿子 |
| 你的参与 | 读完自己定 | 在画布上点、评、改 |
| 适合 | 文档站、内部工具 | 需要别人拍板的界面 |

**如果没人需要看，superdesign 是纯浪费。** 它要消耗额度、要开画布、要你反复过一遍。

### 它有一道数据边界

这是用之前必须知道的一条：

> 它通过外部 CLI 和服务运行。第一次用之前，**必须解释这是第三方服务并取得用户同意**。prompt、你选中的源文件、设计系统上下文、HTML 模板和上传的资源都可能发给 Superdesign。**永远不要上传密钥、凭据、环境文件或无关的源文件。**

**什么时候别用它**：你要出的东西不需要别人拍板的时候。
自己写文档、只有自己看的界面，作者就是读者——**没有第二个人的意见，出稿这一步就没有意义**，还白搭一次额度上传。

### 一条容易漏的规则

它对「分析完成」的判定写得很死，值得抄：

> 只有当六个指定文件**全部存在且非空**时才算完成。缺任何一个，或者有一个是空的（比如初始化被中断），都**不算**完成——要重跑整个初始化，覆盖已有文件是预期行为。

这条值钱在它挡住了「上次跑过一半」的假完成。**判断一个步骤做完没做完，看产物完整性，不看你记不记得跑过。**

### 重试上限是 1 次

它对每类失败都给了明确的次数：命令失败**最多重试一次**。`extract-website` 会跑 60–120 秒，超时重试一次，还不行就**不要 extraction，继续从对话或现有设计系统往下做**。

「最多一次」是防止无限重试掩盖真问题的机制——**重试第三次通常不是运气问题，是方案错了。**

## frontend-dev 的第 3 步

`senior-fullstack-developer:frontend-dev` 整体是实现流程，这里只说和视觉相关的部分。

### 它列的 UI 状态

第 2 步要求先定出这些状态，缺一个就是漏：

> 主要任务、层级、导航、**加载、空、错误、成功、禁用、权限**。

这个列表的来历值得记一下——**「前端交互」那篇讲的四种状态，是从这份清单里挑出来的四个。** 区别是 tutorial 给你最小集（`loading` / `error` / `ready` / 空），而工程流程要求把全套列全。

最小集够教学用，工程上不够。**先知道全集存在，再决定这次要不要全做。**

### 视觉方向的来源

它的措辞是「从产品上下文推导排版、间距、颜色、密度和构图，**而不是把固定风格套到每个项目上**」。

跟 `frontend-design` 那三条 AI 默认是同一个判断，只是换成了工程侧的说法。两边对上，说明这不是某一个 skill 的偏好。

### 动效的选型顺序

它给了一个明确的优先级，**越靠前越优先**：

| 场景 | 用什么 |
| --- | --- |
| 简单状态变化 | CSS transition |
| 组件生命周期动效 | 框架的动画库 |
| 时间线编排 | GSAP |
| 真正的 3D 需求 | Three.js |

顺序本身就是建议：**大多数项目用第一档就够了，往上走一档要付的维护成本就上一个台阶。**

它还补了两条：尽量动 `transform` 和 `opacity`（不触发布局重排），以及尊重 reduced-motion、不阻塞交互。

## 一起用

### 和 [实现功能](/toolkit/build) 一起

设计决定的**成果必须落成文件**，不能留在对话里。

比如这个站的 token 表就落在 `docs/.vitepress/theme/custom.css` 的 `:root` 里。理由有两个：

1. 改样式时有人会读它，不用重新推导一遍
2. **Review 时才有可判定的标准**。「间距不一致」不可判定，「和 `--space-3` 不符」可判定

不落成文件的话，审查环节会空转——只能评论「不太好看」，而这种意见既不可验证也没法改。

### 和 [拆开并行](/toolkit/parallel) 一起

多个 agent 并行改不同页面时，**唯一保证它们不各写一套 CSS 的办法，是编排开始前就把 token 冻结成文件**，并且明确告知所有节点：只读，不许各自定义新颜色。

不这么做的话，五个页面并行做完，你会得到五套略微不同的灰——**这是并行放大「默认值」最典型的后果**，因为每个 agent 都在自己的上下文里独立决定「什么颜色合适」。

### 什么时候不该用

::: details 「我这个是后台管理系统，没人看设计」
后台系统恰恰是**最需要**把语义色定清楚的地方：哪列是错误、哪个按钮是危险的、状态徽章什么颜色。没人「欣赏」你的设计，但所有人都靠颜色区分状态。

例外是纯内部、一次性的脚本工具——那种确实不值得花时间定方向。
:::

::: details 「设计风格是产品定的，我只要实现」
那就把风格**写进 token 文件**再动手，不要凭「看几眼现有页面」去猜。猜出来的实现和设计稿之间的偏差，是最后验收时最花时间的部分。
:::

::: details 「功能都没做，界面先别管」
顺序反了。`frontend-design` 里那个「首屏放三个数字」的案例说明：**功能没定的界面，token 一定最后会落进默认值**，因为没有具体内容可以支撑具体的选择。
:::
