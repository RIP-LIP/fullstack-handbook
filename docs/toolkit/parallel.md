# 拆开并行

五个 skill 覆盖从「自己列个 todo」到「可视化编排面板」的全过程。

## 先问一个问题：该不该拆

::: danger 活多 ≠ 该并行
这是最容易搞错的一点。**并行的前提是「改动之间没有交集」，不是「活很多」。**

三个 agent 同时改三个文件，而这三个文件互相 import——它们会互相覆盖、互相读到对方写了一半的状态。**这时候并行比串行更慢也更脏。**

判断方法：把要改的文件列出来，**如果它们之间有交集，就别并行。**
:::

真的适合并行的样子：

- 五个页面各写各的
- 十个文件各查各的
- 二十条数据各审各的
- 两个互不依赖的服务各部署各的

## 五个层级

```
自己写 todo 列表              2–5 步
  ↓
superpowers:writing-plans     需要别人执行或反复执行的计划
  ↓
superpowers:subagent-driven-development    一个任务切成几个子任务
  ↓
superpowers:dispatching-parallel-agents     子任务无依赖，真并行
  ↓
mcode-dynamic-workflows      大批量，要预算和面板
```

**大多数项目停在第一层。** 往上每爬一层，编排成本就上一个台阶。

## 动态编排

`mcode-dynamic-workflows` 是唯一有**自己执行面板**的，也是唯一一个「用错比不用更糟」的。

它的本质是：**用一段 JavaScript 描述多步骤流程，运行时拉起多个 agent 分头做，在浏览器面板里看拓扑和进度。**

**这不是「写一段更长的 prompt」。** 区别是它是**可执行的编排**：有依赖图、有并发控制、有预算上限、有每个节点的独立状态、有可中断可恢复。

### 五个业务接口

只有五个，写的是**异步函数体，不能有 `import` / `export`**：

| | 作用 |
| --- | --- |
| `ctx.agent` | 派一个 agent，返回 `status` / `output` / `error` |
| `ctx.map` | 对一批数据并行处理，每项一个 agent |
| `ctx.phase` | 声明一个阶段，给节点分组 |
| `ctx.log` | 记一条事实性进度消息 |
| `ctx.checkpoint` | 存一个检查点值 |

`input` 是**冻结的 JSON**。

### agent 不会继承你的对话

> 每个 agent 必须有自包含的 prompt、必要的输入、稳定的 ID 和合适的输出 schema。
>
> **worker 不会隐式继承主对话。**

意思是 agent 不知道你刚才说过什么、不知道你的偏好、**不知道你前面否决过哪两个方案**。你在主对话里想了一分钟才定下来的拆分方式，不会自动传过去。

这直接决定 prompt 怎么写：把背景、已排除的路径、范围、验收标准全写进去。

### 依赖声明不等于已经等待

这一条很反直觉：

> `dependsOn` 声明**不会**等上游执行完。**必须显式 `await` 并检查 `status`。**

```js
// 错的：只声明了依赖，没等
const a = await ctx.agent({ id: 'a', ... })
const b = await ctx.agent({ id: 'b', dependsOn: ['a'], ... })  // 可能和 a 同时跑

// 对的：显式等，并检查状态
const a = await ctx.agent({ id: 'a', ... })
if (a.status !== 'succeeded') {
  await ctx.log(`上游 a 失败：${a.error}`, { stepId: 'b' })
  return { skipped: true, reason: a.error }
}
const b = await ctx.agent({ id: 'b', dependsOn: ['a'], ... })
```

它还有一条配套的：**验证失败的独立节点，不能反推原始发现是错的。** 覆盖不到的文件、没有验证的声明，要如实写进最终报告。

### 最小可用的形状

```js
await ctx.phase({ id: 'write', label: '并行写各章' })

const rows = await ctx.map(input.chapters, (chapter, i) =>
  ctx.agent({
    id: `write:${i}`,
    label: chapter.title,
    phase: 'write',
    prompt: `为「${chapter.title}」写这一章。
自包含要求：读者是谁、这一章的验收标准、允许改动哪些文件、明确禁止什么。
返回：{ markdown: string, commands: string[] }`,
    input: chapter,
  }),
)

const failed = rows.filter((r) => r.status !== 'succeeded')
await ctx.log(`${rows.length - failed.length}/${rows.length} 完成`, { phase: 'write' })

return { chapters: rows, failed: failed.map((f) => ({ id: f.id, error: f.error })) }
```

四个要点：

- `ctx.map` **不是**独立的 pipeline API，就是普通 JS 组合。每项内部可以串行做「审查 → 验证」，快的项不用等慢的
- `prompt` 必须自包含
- **`status` 一定要检查**，失败的**如实带回**
- 不要拿固定 demo 输出冒充真实产出

### 预算

| | 默认 | 可调 |
| --- | --- | :-: |
| 单工作流并发 | 4 个 agent | 1–16 |
| 服务级全局并发 | 8 个 | 面板 1–32 |
| 每 agent 模型步数 | 120 | `maxSteps` |
| 每 agent 超时 | 30 分钟 | `stepTimeoutMs` |
| 整个工作流超时 | 120 分钟 | `runTimeoutMs` |
| agent 调用总数 | — | `maxCalls` |

**模型步数和工作流 agent 调用数是两个不同的限制**，容易混。

轮询式分配：符合条件的工作流轮流拿空闲槽位。调低并发**不会**打断已在跑的 agent。

### 「排队」不等于「失败」

一个节点显示 queued，可能是它在等**服务级全局并发**（8），也可能是在等**自己工作流的并发上限**（4）。

要看 `workflow_status` 里的 `queueInfo` 才知道是哪个、谁占着槽位。**把它当失败排查，会花很多时间查一个根本没坏的东西。**

### 拓扑是静态推导的，不是运行结果

面板在批准之前就画出了完整节点图，但它标注得很清楚：

> 静态分析**从不执行脚本**。循环和回调是「组」，条件分支可能根本不会跑，**推导出来的边不保证是执行顺序**。

节点有七种状态，其中两种最容易被误读：

- **`not-executed`**：没被触发的计划节点。**它不会被标成成功或失败的 agent。** 它只是没发生
- **`dependency-blocked`**：上游挂了，它连跑都没跑

### 批准必须由人点

它反复强调：**不要通过 HTTP、shell、浏览器自动化或任何其他工具代为批准。**

另一半同样重要：**草稿处于待审状态时，不要轮询，也不要声称执行已经开始了。** 停下来等用户。

### 权限边界

::: danger 这不是只读沙箱
> MCode worker 使用 `smart` 权限。**这个插件不是只读的操作系统沙箱。**
>
> **不要用 `full` 或 `off` 来绕过审批。**
:::

worker 能做的事比你在主对话里以为的要大。这一点必须清楚。

### 失败要分类

> **不要把所有失败都说成超时。** 要区分：agent 步数上限、agent 超时、工作流超时、CLI / 认证失败、协议错误。

五类的处理方式完全不同。

「恢复」也不是「继续」——**失败节点从头重跑，不是它原来那个会话的延续。**

## 站内的一个真实决定

这个站的教程正文，第一版打算用编排并行写——一章一个 agent。

最后没有这么做，改为手写。理由两条：

1. **当时只有 5 篇。** 5 个 agent 的编排成本（写描述、传上下文、审结果、合并）大于手写。
2. **更重要的**：并行产出很容易出现「看起来合理但没实际跑过」的代码示例。而这个站的全部价值就是**每个示例都实跑验证过**——编排天然削弱这一点，因为你不可能同时盯五个节点的输出是否真跑过。

什么时候会用：章节涨到 7 篇以上，且**每章的验证能自动化**（比如有测试套件）。模式是「一章一个 agent + 一个专门验证的 agent」。

**注意第二个 agent 不是多余的。** [验证门禁](/toolkit/quality#验证门禁) 那页写过：`status: succeeded` 只表示 agent 认为它做完了，**你唯一能信的是 VCS diff 和真跑一遍**。

## 一起用

### 和 [实现功能](/toolkit/build) 一起

分工是清楚的：

| 问题 | 归谁 |
| --- | --- |
| 该不该拆 | 实现流程判断 |
| 拆成几个、怎么切 | 编排 |
| 做完后验没验 | **质量那一组** |

关键是第三行。**编排本身不保证验证。** 它只是把 N 个任务并发跑完。

正确接法：编排负责分发，**验证是独立节点或独立一步**，且必须检查它的 `status`。两者混在一起就失去意义了。

### 和 [界面设计](/toolkit/design) 一起

**编排开始前先把 token 冻结成文件**，并明确告知所有节点只读、不许各自定义新颜色。

不这么做，五个页面并行做完你会得到五套略微不同的灰——**这是并行放大「默认值」最典型的后果**，因为每个 agent 都在自己的上下文里独立决定「什么颜色合适」。

### 和 [保证它是对的](/toolkit/quality) 一起

对账的是 [验证门禁](/toolkit/quality#验证门禁) 里那两行：

| 说法 | 需要 | 不够 |
| --- | --- | --- |
| Agent 完成了 | 查 VCS diff，验证改动 | Agent 报告「成功」 |
| 需求满足了 | 逐条对照清单 | 测试通过 |

**并行放大了这两行的代价。** 串行时一个 agent 报错你能立刻看见；五个并行时，五个「成功」报告里混着一个假成功，如果没有 diff 复核就发现不了。

### 什么时候不该用

::: details 「我就想让它同时干三件事」
并行的收益多数情况下抵不过成本。三件事的编排需要：写描述、审拓扑、盯结果、处理失败、合并——加起来比顺序做完更费时间。

**先问：顺序做要多久？一个小时内就直接做。**
:::

::: details 「让它顺便帮我探索一下」
探索类任务用编排是合理的，因为每个探索项互相独立。

但**别把探索结果直接当结论交付**。它自己就要求：报告里写明覆盖范围和未验证的部分。
:::

::: details 「反正有面板，看着挺酷」
面板是给**已经决定要编排**的人用的。它不降低编排成本，只是让成本可见。
:::

## 跑完之后

你应该能回答这三个问题：

- 我这次为什么开编排？（**独立** + 量大，不是「显得专业」）
- 每个 agent 的 prompt 里，背景和验收标准写全了吗？
- **哪些节点的产出没有被独立验证过？**

第三个问题是这个工具最容易骗自己地方。
