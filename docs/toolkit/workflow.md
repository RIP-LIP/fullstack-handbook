# 工程流程

对应插件 `senior-fullstack-developer` 的主入口 `engineering-workflow`。

它管的是**改动怎么组织、怎么确认没弄坏别的东西**。界面能用了之后，这才是真正开始疼的地方。

## 它是什么

七步，固定顺序：

```
1  建立仓库契约    读现有的东西，不先设计方案
2  按需路由专项    该转给前端专项 / 跨层专项时才转
3  按比例做计划    多步任务用可见的待办列表
4  增量实现        复用已有库和模式，不做无关重构
5  在受影响面验证  这一步是重点，下面单独讲
6  Code Review     只看本次 diff 和必要的调用方
7  诚实交付        说什么改了、验了什么、没验什么
```

## 想清楚什么

### 第 1 步是「先读，后想」

它的措辞很硬：**在选方案之前先建立仓库契约。**

要读的东西：项目里的指令文件（`AGENTS.md` 之类）、`package.json`、邻近的同类实现、import 关系、测试、当前 git 状态。

从这些里**推断**技术栈、约定和验收标准。只在「某个决定会实质改变实现」时才问人。

::: tip 这一步省掉会怎样
你会写出「和这个项目别处不一样」的代码。不是错，是**漂移**。

项目已经用 `node:sqlite` 了，你新写一个 `better-sqlite3`；项目所有错误都走 `{ error: { code, message } }`，你新加一种 `{"msg": "..."}`。都能跑，但三个月后没人知道该跟哪种写法。
:::

### 第 2 步的判断是「要不要转」

它自己列了两条路由：

| 情况 | 转给 |
| --- | --- |
| 实质的 UI 架构、响应式、可访问性、动效、设计系统、视觉资源 | `frontend-dev` |
| 跨层功能：接口、鉴权、数据库、队列、缓存、上传、实时、生产加固 | `fullstack-dev` |

但它同时说了两句更重要的话：

- **不要重复加载已经加载过的专项 skill。**
- **专项做完回到第 5 步**，不要因为已经转出去就跳过验证和 Review。

::: danger 最容易犯的错
「这个任务很大，所以我转到专项 skill 去了。」

专项 skill 是**补充**，不是**替代**。它做完代码就结束了，第 5 步验证和第 6 步 Review 还在主流程上。少了这两步，你得到的只是一份没验过的代码。
:::

它还有一条兜底：**小而明显的改动直接做，不要加流程。** 改一个错别字、给一个函数加个参数，这种事套一遍七步是浪费。

### 第 3 步是「按比例」

两条具体要求：

- 多步工作用**可见的待办列表**，且**同一时刻只有一个是进行中**
- 用户要求先看计划时，**停在「方案 + 验证计划」这里**，等确认；没要求就继续做，别自己加一道审批门

「按比例」这三个字是重点。它不要求所有任务都写计划，**改一个 CSS 变量不需要计划**。

### 第 5 步是整条链最值钱的地方

它的原话是「在**受影响的**面验证」，展开来是四层：

| 验证什么 | 什么时候必须做 |
| --- | --- |
| 聚焦的单元 / 集成测试 | 行为变了 |
| 类型检查、lint、构建、schema、契约检查 | 碰了这些面 |
| **Browser 真实操作页面** | 有真实 UI 路径要验 |
| —— | —— |

Browser 那几条写得最重，因为它区分了两件事：

> **构建通过、curl 有响应、HTML 源码对了、单元测试过了，这些单独任何一项都不算 Browser 验收。**

要在**真实渲染出来的页面上走一遍用户路径，然后验证可观察的结果**。

它还列了几条禁止项：

- 不要用「反复重跑 flaky 的东西」代替诊断
- 如果 Browser skill / 工具 / 能力缺失或被禁用，**报告「浏览器验收未执行」和具体阻塞原因**，把不依赖它的检查做完，**但不要声称 UI 通过了**
- 被禁用的 Plugin 要让用户去 Plugin 管理里处理，**不要自己启用，也不要走旧的启用流程**

::: tip 最后一条对你有实际影响
这条约束是写给 AI 的，但它反过来保护你。**一个诚实的「这条我没验，因为工具不可用」，比一句「已全部验证通过」有用得多。**

浏览器不可用的时候，正确做法是明确说哪一环没验，而不是把它算进「已完成」。
:::

### 第 7 步是「诚实交付」

它的要求可以抄下来当自己的交付清单：

- 改了什么
- 验了什么
- **什么没跑**
- 还剩什么风险

禁止项：

- 除非真做完了，否则不许声称通过了浏览器验证、部署、测试、提交、推送或发布
- 本地预览服务交付后**不要等它退出**，也别因为它还活着就把回合挂着
- 停预览服务之前，**先说明那个 URL 会失效**
- 主机能力缺失时，**不要自己造一个 localhost 桥接**来假装能做

## 怎么用

这个 skill 的调用形式就是一句话：

```
@senior-fullstack-developer 把校验规则从后端挪到 packages/shared
```

它自己会走完七步。你要做的干预点只有三个：

**一、要不要转专项。** 直接说：

```
@senior-fullstack-developer 这个功能是跨层的（要加表、改接口、调前端），
按你的路由走 fullstack-dev，做完记得回到第 5 步验证。
```

**二、要不要先看计划。** 说：

```
@senior-fullstack-developer 先给方案和验证计划，我确认后再动手。
```

**三、验证到哪一层。** 说：

```
@senior-fullstack-developer 改完在浏览器里点一遍，
加一条、停掉后端看报错、勾完成看回滚。
```

::: tip 第三句值多少钱
这句「验证什么」写清楚，比事后问「这个验证过吗」省事得多。

上面那句里三个动作正好对应站内三篇不同章节的验证步骤——**照着抄就行**。
:::

## 一起用

### 和 [界面设计](/toolkit/design) 一起

上一轮定的 token 应该**在第 1 步就被读进来**，不是贴在墙上。

具体做法：token 表落到仓库里（`tokens.css` 或设计文档），第 1 步的「读指令文件」自然就会读到它，改动自动对齐。

反过来，**第 6 步的 Review 需要一条可判定的标准**。「间距不一致」不可判定，「和 `tokens.css` 里的 `--space-3` 不符」可判定。所以设计产出必须落成文件，否则审查环节会空转。

### 和 [多 Agent 编排](/toolkit/agents) 一起

它是**编排的准入判断**：

| 情况 | 走哪条路 |
| --- | --- |
| 一个会话能做完 | 走这个 skill 的七步，不要开编排 |
| 一个会话做不完，但改动高度耦合 | 拆分阶段，串行做，每个阶段各自走一遍七步 |
| 改动互相独立，能同时进行 | 才是编排的适用场景 |

这条判断很重要。**编排本身有成本**（写 DSL、传上下文、判断结果对不对），耦合的改动并行做只会互相踩。上一轮说的「单会话装不下」是个**量**的判断，但**独立**才是编排的**前提**。

### 什么时候不该用

::: details 「我就是想让你解释一段代码」
它的 description 里明确排除了这种情况：微小的改动、纯解释、只做 code review、非编码工作。

解释代码不需要七步流程，直接问就行。
:::

::: details 「它让我写的计划太啰嗦了」
第 3 步说的是「按比例」。小任务可以不写计划——但那是**你的判断**，不是默认。

如果你觉得它过度，直接说「这个改动很小，直接做不用出计划」。反过来，跨三层以上的改动主动要求计划，是划算的。
:::

## 跑完之后

你应该养成了一个习惯：**说清楚「验了什么」和「没验什么」。**

这个习惯到了下一层会变得非常值钱——当你面对五六个同时在改的任务时，「哪个 Agent 真的验过了」是唯一能让你判断能不能合并的依据。
